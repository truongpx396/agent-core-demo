## Patterns

### 59. A settings error must not print the secret it rejected
Pydantic's `ValidationError` prints the raw offending value (`input_value='...'`), a `Settings()` error is raised at import time, and the output goes to a terminal or container log. Checked: with an API key set to a value its validator rejects, the startup error repeated the key whole, and so would a credential pasted into the wrong variable.
- **One line closes it for every field:** `hide_input_in_errors=True` on the settings class. The error still names the field and the rule but not the value. A test per path (a rejected credential, a malformed map of secrets) fails without it, each checked against the mutant that removes it. It is class-wide, so every other settings error stops quoting its value too.
- **Credentials are `SecretStr`, and a blank is "not set".** A variable left in `.env` with no value arrives as an empty string, which would be an empty credential failing its format check with a confusing message. Only a blank is touched before wrapping; a real value is never inspected in the clear. The one mistake worth catching at startup is pasting the wrong kind of key.
- **A setting that nothing reads is a promise the code doesn't keep,** so when one was deliberately removed, a test pins its absence.
- **A warning that can go stale is pinned.** A `.env.example` comment saying "do not enable X until Y exists" has a test that fails the day Y exists, as the prompt to rewrite it.
- The billing package's credential settings (key-prefix checks, sandbox default, verification numbers, gaps): `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md".

### 60. A test that re-applies a migration to a shared database must be the one that gives up
A "this migration can be applied twice" test failed about one parallel run in seven, and once the victim was an unrelated test that failed with `DeadlockDetected` instead of its injected error. Tests re-apply migrations to the database other xdist workers are writing to, and re-running DDL isn't harmless there. Measured on a real Postgres: a no-op `ALTER TABLE … ADD COLUMN IF NOT EXISTS` takes an **ACCESS EXCLUSIVE** lock, `CREATE INDEX IF NOT EXISTS` a **SHARE** lock, `CREATE OR REPLACE TRIGGER` a **SHARE ROW EXCLUSIVE** lock, all on tables other tests hold row locks on.
- **Why the wrong test failed.** A concurrent transaction that holds a lock on one table and waits for another forms a cycle with the script, and Postgres aborts the session whose `deadlock_timeout` (1 s here) check runs first, the one that began waiting first: the DML test, not the DDL one. Retrying inside the DDL test wouldn't help: the victim was somebody else.
- **Fix: this session always gives up first.** `tests/integration/schema_reapply.py::reapply` sets a `lock_timeout` (300 ms) below `deadlock_timeout`, so the script abandons a wait and rolls back before any deadlock check runs; the cycle dissolves and the idempotent script is retried with jitter. `DeadlockDetected` is deliberately not retried: with the timeout it can't happen, and if it does the assumption is wrong. A test asserts the timeout stays below `deadlock_timeout`.
- **The cycle is built on purpose:** a test takes a lock the script needs, waits (via `pg_locks`) until the script is blocked on it, then asks for a lock the script already holds. Without the timeout that deadlocks within a second.
- **A hang is the worst failure.** The first mutant run hung (timeout removed, the "never released" test waits forever) and leaked a container. Every re-apply is now bounded by `asyncio.wait_for`, so a regression is a named failure, not a stalled job.
- **The same cause wore a second face:** `DID NOT RAISE UniqueViolation`, which looks like a missing unique index. The code under test never raises (a failure is returned as a value), the test discarded that outcome, and the deadlock had killed the FIRST write so the second "succeeded". Tests that set the stage with a bare call now go through a helper that asserts the setup didn't fail.
- **Verified:** real-Postgres tests of the helper; 5 mutants, 4 caught (the fifth, also retrying `DeadlockDetected`, is equivalent once the timeout exists); 16 of 16 parallel runs clean, against about 1 in 7 failing before.
- **Gaps:** other tests that run DDL against the shared database aren't covered unless they use the helper (`.claude/rules/testing.md` says so), and `lock_timeout` bounds only this session: a test holding a lock for tens of seconds would still fail the re-apply after its 60 tries.
- The package keeps its own copy of the helper (`packages/billing/tests/integration/schema_reapply.py`), since it can't import this repository's; its billing-specific parts are in `packages/billing/docs/PATTERNS.md`.

### 69. A model decision is made by a frozen evaluation, and a benchmark number is only valid on the hardware and the text it was measured on
Choosing an embedding, reranking or screening model by a blog post or model card ends with a model that is better on someone else's data. `make model-eval` (`scripts/model_eval/`, data in `evals/`, [`evals/README.md`](evals/README.md)) produces a report instead: the candidate next to the recorded result of the model in use, on this repository's own questions, with confidence intervals and a verdict. Building it surfaced five ways a measurement lies, each now enforced.
- **Frozen data, immutable baselines.** A dataset manifest records the sha256 of every file and a mismatch stops the run. `dev` (for tuning) is refused for reporting and is disjoint from `test` by id and near-duplicate text. A baseline can't be overwritten without `FORCE=1`, and one recorded against an unreviewed set is `provisional` (computed from the items' `reviewed` flags, not typed). Public sets are pinned by commit and per-file hash, carry a licence from a short allow-list, and are never redistributed.
- **Controls, because a harness that can't tell a model from itself is worse than none.** Every report carries the baseline against itself (must be `no_difference`) and a useless model (must be `worse`); if either fails, the report is `INVALID` and the command exits 5. Real data corrected the first design: a screen scoring at random flags about half of everything at 0.5, so its *recall* (~0.5) matches the real screen's (0.47), and judging it "worse" on recall made `make model-eval-verify` fail on the committed baseline. A control must be judged on the metrics that mean "it works" for that kind of uselessness: ranking and false alarms for a random scorer, detection for a screen that flags nothing. `tpr@1%fpr` is judged for neither (with a few dozen benign items the cap allows zero false positives, and a random scorer can reach a non-zero rate by luck).
- **A classifier's controls can fail because of the labels, and the report must say so.** The routing head was judged on labelled outcomes (what a local and a stronger model each scored on a prompt, by a judge). The first real run showed a mean advantage of the strong model of +0.032 on a 0–1 scale, so even a PERFECT router couldn't be told from a random one; the report was `INVALID` and said only "a control did not come out as expected", which reads as a harness bug. It now adds a `WHY:` warning with the measured advantage. Both trained heads then scored at the never-escalate accuracy, below a random router's curve, and stayed unaccepted. The lesson is upstream: before training anything, check the stronger model wins clearly on a meaningful share of prompts, with a judge that isn't the model being judged.
- **`inconclusive` is not "equal".** `better` or `worse` only if the paired-bootstrap interval excludes zero (2,000 resamples over queries, fixed seed, candidate and baseline resampled with the SAME indices: two independent intervals throw away the pairing). An interval that merely touches zero is `inconclusive` and says how many more items would settle it (`needed_n`, an estimate).
- **Hardware is part of the number.** Latency is stored keyed by a hardware id and never compared across ids. On an ARM laptop CPU fastembed's int8 bge-small was *slower* than the official fp32 file (35.8 vs 17.1 ms per chunk); fp32 ONNX nomic on CPU is 3–5x slower than Ollama on Metal; a baseline recorded on a busy machine (load 19–23 on 12 cores) is stored with that warning. Quality numbers don't depend on load and are never discounted.
- **Measure the text the system really sees.** A 110-token synthetic paragraph understated the real 259-token markdown chunks by 2.4x, so the first cost per chunk was 2.7x too high. The retrieval set is chunked by the app's own chunker.
- **Verified:** metrics are checked against hand-computed values in the tests (recall, MRR, NDCG with its discount, ROC-AUC with ties, TPR at a fixed FPR, macro-F1, ECE, the routing curves), and the harness is hermetic (a socket-guard test). **23 mutants, all caught in the end; 5 survived first** and were real gaps: the inclusive false-positive cap in `tpr_at_fpr` (`<=` vs `<`), an interval that only touches zero called significant, the confidence-interval percentile, a "worse" control accepting `inconclusive`, and the sha256 check of a cached public file.
- **Gaps:** the repository-own sets are small (tens of chunks, ~100 questions, 67 screening items) and unreviewed by a person, so they separate a good model from a useless one but can't rank two good ones within a point; questions were written by a 7B model and skew toward factual lookups; latency is measured on one machine; the random-scorer control is judged on three metrics because a fourth flips with the seed at this size.

### 72. A security gate that cannot be satisfied gets a dated, reasoned exception, and tests that keep the reasons true
On 2026-10-21 CI's `trivy` job went red on every PR without any touching a dependency: its database had learned of CRITICAL findings in packages `requirements-lock.txt` already pinned (certifi 2026.7.22, pillow 12.3.0). A hard gate red for everyone is ignored by everyone, so it must be fixed or deliberately and visibly excepted, never worked around.
- **Fix what can be fixed, where it lives.** certifi had no cap: a one-line lock bump (GHSA-6q48-6c7w-9gw2, a CA bundle trusting compromised emSign intermediates), checked with `pip install --dry-run` against an environment mirroring the lock. The image scan also reported a SECOND certifi the lock can't reach, `pip/_vendor/certifi` inside the base image's pip (26.2.1 vendored 2026.6.17); only a newer pip (26.2.2) cleared it, so the Dockerfile upgraded pip first (later replaced by removing pip: 76). Found by reading the scan's output and then the image, not by assuming the lock was the whole story.
- **Read what the gate says, then check it again where it will run.** CI's scan on 10-21 listed one pillow finding; the same scan locally the next day listed three, because the database moved. The scan that decides is run with the official image (`aquasec/trivy`, the hard-gate flags) before pushing.
- **When the only fix can't be installed, say so and bound it.** pillow's three findings were fixed only in 13.0.0, and fastembed (every release through 0.9.0) declared `pillow<13.0` on Python 3.13. Forcing 13 would override a declared constraint untested, and `pip` would refuse the lock. `.trivyignore.yaml` carried one entry per CVE, each with a `statement` of why it was safe (what the vulnerable call needs, and the evidence nothing here makes it: no `thumbnail()`/`draft()`, no TIFF `save()`, no Ghostscript in the image) and an `expired_at` that brings it back and fails the gate again. Checked with the real scanner: 3 findings without the file, 0 with it, 3 again with the dates in the past.
- **The reasons are tests, not prose.** While the exception existed, `tests/core/test_trivy_ignore.py` failed if first-party code imported PIL or called `thumbnail`/`draft`, if the Dockerfile installed Ghostscript, or if the lock moved to pillow 13 (the entries were then dead weight hiding the next finding with the same ids). It still fails if an entry has no statement or expiry, if the lock goes back to a vulnerable certifi, if the Dockerfile stops removing pip, or if a hard gate stops reading the file. Each mutation was run against a copy and caught by the intended test.
- **Only the hard gates read the exception;** the full-report steps (Security tab, `make trivy`) don't, so an accepted risk stays on the list of everything.
- **Gap (while it lasted):** this made pillow not-reachable-today, not safe. A new first-party Pillow use would have broken the premise (the test caught that); a dependency starting to decode images in-process would not have been caught.
- **Resolved 2026-10-28: the exit was taken and the exception deleted.** fastembed 0.9.1 (2026-10-24) widened its cap to `pillow<14`, so the lock moved to Pillow 13.0.0, with brotli 1.2.1 for GHSA-9v8h-qqgm-4m35 (a CRITICAL the same scan reported); `requirements.txt` raised its fastembed floor to 0.9.1 so a loosened range can't pull Pillow back, and the ML image's own pin moved with it. `.trivyignore.yaml` stays, empty, with its guard tests. Before bumping a retrieval library **the outputs were compared, not assumed**: 11 varied texts through fastembed 0.8.0 and 0.9.1 gave bit-identical BM25 vectors and MiniLM rerank scores differing by exactly 0.0, so no indexed sparse vector is stranded and no rerank baseline moves. With the hard-gate flags the old lock fails with 6 CRITICAL, the new with 0.
- **What the five red days taught.** The gate was red for 16 consecutive runs until 2026-10-28, and the exit (a fastembed release with a wider cap) had been available for four of those days. The `expired_at` (2026-12-01) was too far off to prompt a look, and two NEW Pillow findings were never added, so the exception hid nothing while the gate stayed red regardless. A dated exception needs its exit condition **checked whenever the gate next goes red**, not only when the date arrives; and a gate red for a week has stopped being read, which is how a second, unrelated red (the `test-live` regression of 2026-10-24) went unnoticed behind it.

### 75. A topic matcher's cutoff belongs to a model, its examples to their text, and what it does with the unmatched is measured on real prompts
Spec 015 added label sets: a reviewed file of choices with example sentences, matched to a text by embedding centroid (`docker/ml-service/labelsets/`, `POST /v1/decide`), used by the model router and by any agent step that must pick among a few predefined choices. Four things went wrong or nearly did; each is now a rule.
- **A similarity cutoff is a property of the model that produced the similarities.** The same set needed 0.709 for bge-small and 0.247 for MiniLM (chosen on the same dev split), and the service's fallback IS the other model. One app-side threshold would be right for one and meaningless for the other, with no error. So the cutoff lives in the set, per model, and a model without an entry doesn't serve the set; there is no default. (Same reasoning as binding an artefact to a model revision, 68.)
- **Store the examples as text, not vectors.** A stored vector is valid for one model revision only and fails as confident nonsense; text can't go stale. The service embeds a set's examples with the model serving the request, and again when that model reloads under a different revision (a test mutates the revision and asserts the stale index never answers).
- **A claim about what the matcher does with text it shouldn't match must be measured before it is written.** A draft said the unmatched sentences "almost always land on `smalltalk`"; counted, they land on six labels. A property measured on the author's sentences didn't carry to users': the margin to the runner-up was 0.010 for wrong labels against 0.068 for right on the authored set, but 0.029 against 0.028 on the repository's real prompts. The first look showed the signal sending 11% of ordinary knowledge-base questions up a tier (a pricing question read as `reasoning`, a runbook question as `code`). Read the router's output on the traffic it will see before turning it on; that is what `ROUTER_MODE=shadow` is for.
- **Choose the cutoff on one split, report on another, and say which sentences informed an example.** `make labelset-calibrate` reads only `dev`; after errors were read on the real prompts' dev split and ten examples added, the held-out split went from 7 of 91 routed up to 5 of 91, reported as a small effect on 91 prompts, not a fix. A test fails if an example is a near-duplicate of any of those prompts.
- **Tests that pass the first time are suspect.** The 407 policy tests and all but one label-set test passed first run (the one was the author's miscount). A mutation check then found seven real gaps: the cutoff's inclusive edge, the centroid's renormalisation and the normalisation of long examples, the `failed` state after a model error, unreadable files, a word-boundary test whose text held only one would-be match, and the clamp on the logged similarity band. The evaluation data's tenant-name guard also rejected a draft sentence ("Globex"): the guard doing its job.
- **Gap:** the label table and the rules are policy; nothing measured says the tiers they pick give better answers (`specs/015-label-sets-and-tiered-routing/research.md`).

### 76. The images are built in stages with uv and a cache mount, carry no installer, and run hardened
On 2026-10-23 rebuilding the app image after a lock change (#181) spent 347.7 s in `pip install` on the maintainer's laptop. The Dockerfile was one stage running `pip install --no-cache-dir -r requirements-lock.txt`, so any cache miss re-downloaded every package; the image still carried pip, whose vendored certifi Trivy reads as a second certifi the lock can't reach (72); the Python base floated, so two builds of one commit could differ; and nothing restricted how the containers run. This covers both images production pulls (the app image for the api and worker roles, and the ML service image) and how they are published and run. A cache without a faster installer still pays the install; a faster installer without a cache still downloads; neither changes what ships or how it runs.
- **Four stages in both Dockerfiles, the shipped one last.** `base` (the Python image), `uv` (the installer), `builder` (installs dependencies into `/opt/venv`; thrown away) and `runtime` (the base, the OS packages, the virtualenv copied in at the same path because a virtualenv's scripts name their interpreter by absolute path, and the app). Both build on the one `base`, so the interpreter the virtualenv links to is the one it was built for. Compose builds and `deploy.yml` name `target: runtime`, so a reordered Dockerfile fails a build instead of shipping the builder.
- **Pinned by digest, bumped by a bot.** `base` is the multi-architecture index of `python:3.13-slim` (amd64 and arm64) and `uv` is `0.12.24` (the 0.13 line was days old), each its own `FROM` line so Dependabot can propose bumps. `.github/dependabot.yml` has a `docker` entry for both Dockerfiles: weekly, 14-day cooldown, Python minor never moved (3.13 is what the lock was resolved for). Compose files are deliberately not read (the ecosystem would also propose postgres majors), so the LiteLLM digest stays a hand bump with `make gateway-check` (74). Freshness comes from that weekly proposal, `apt-get upgrade` on rebuild, and CI's Trivy image gate failing if the pinned base ages into a fixable CRITICAL. `tests/core/test_dockerfile_build.py` fails if the two files' digests differ.
- **A cache mount for uv's wheel cache, a bind mount for the dependency file.** The wheel cache lives in the builder, never in an image; the file is bind-mounted so no layer holds it, and BuildKit keys the step on its content, so it reruns exactly when the file changes and downloads only what changed. `UV_LINK_MODE=copy` (the cache is another filesystem) and `UV_COMPILE_BYTECODE=1` (a non-root container can't write .pyc files under a root-owned virtualenv and would compile on every start). The two images share the cache.
- **No installer in what ships.** The runtime stage runs `python -m pip uninstall -y pip setuptools wheel` and never copies uv; the virtualenv has no pip. Nothing in the running app installs anything. The vendored certifi and any future pip finding leave with it (replacing 72's "upgrade pip first"); `tests/core/test_trivy_ignore.py` pins the form. So `docker exec <container> pip install ...` no longer works; to debug with tools, build the builder stage (`docker build --target builder`).
- **Hardened at runtime, in both compose files.** The api, the agent workers, the ingest worker and the ML service get `init: true` (a real PID 1 that reaps the sandbox bridge's children and forwards SIGTERM so `stop_grace_period` is honoured), `no-new-privileges`, `cap_drop: ALL` and `read_only: true`, with remaining writes going to size-capped tmpfs (counted against the container's memory limit). One anchor, merged service by service, never applied to third-party services whose write paths nobody has checked. **Running it this way found two things reading the code did not:**
  1. `crawl4ai` creates `~/.crawl4ai` the moment it is IMPORTED (`OSError: Read-only file system`), a third-party write a search of first-party code can't see. `$HOME` itself is therefore a tmpfs owned by the app user (`uid=1000,gid=1000`), which also covers the next library's dot-directory.
  2. A tmpfs `/tmp` is wrong for uploads: the multipart parser spools every file to `/tmp` before the handler runs, limits allow 5 x 25 MB per request, and a 128 MB tmpfs stops at 128 MiB while holding the spool in RAM against the prod api's 512 MB limit. The api, the only role that receives uploads, gets a disk-backed anonymous volume at `/tmp`, tmpfs only for `$HOME`; `tests/core/test_compose_hardening.py` pins that, and that no tmpfs covers the ML service's model volume.
- **Published with an SBOM and provenance.** `deploy.yml` builds the app image from `target: runtime` and attaches `sbom: true` and `provenance: mode=max` to both images. **Not run:** the workflow only runs on `main` after CI, so these inputs are pinned as text by `tests/core/test_deploy_workflow_images.py` and will first run at the next deploy.
- **Measured** (arm64 laptop, one run each; not a controlled comparison with the 347.7 s): app image cold with an empty uv cache, install step **29.8 s**; one lock pin changed (certifi), install step **11.4 s** ("Prepared 1 package", the other 169 from the cache mount). Sizes: app 1.67 GB against 1.69 GB before, ML 529 MB against 531 MB: about what pip and its leftovers weighed.
- **Run on the built images** under the exact flags compose renders: the api healthy on the dev network (`/health/ready` 200 with qdrant, both Postgres databases, redis and the ML service reachable); uid 1000, `CapEff` 0, `NoNewPrivs` 1, PID 1 `docker-init`; `/app`, the interpreter's directory and `/opt/venv` read-only, `/tmp` and `$HOME` writable; a 4 MB spooled upload; `pip`, `python -m pip` and `uv` absent. The ML service: `/health` 200 within 20 s with an empty model volume, port 80 bound as uid 1000 with no capability, rerank, prompt-guard and bge-small `ready` in ~30 s (my output was cut off before the rest), no read-only, permission or capability errors.
- **CI found what no local run could: the test harness built the ML image with the Docker SDK's legacy builder.** `tests/containers.py` called `docker.from_env().images.build(...)`, which rejects `RUN --mount` ("the --mount option requires BuildKit"); `test-integration` and `test-live` failed on that alone (the PR's first version hadn't touched the ML Dockerfile). The harness now builds with the Docker CLI (BuildKit) through `_build_image`, and a test fails if any test calls `images.build(`. **The lesson:** a build feature is only as portable as the least capable builder anyone uses; grep for every way an image is built (SDK, CLI, compose, workflow actions) before adopting one.
- **Verified:** 36 new hermetic tests (`test_dockerfile_build.py` 21, `test_compose_hardening.py` 8, `test_deploy_workflow_images.py` 7), and **49 mutants, all caught** (each hardening flag, the home tmpfs and its ownership, the api's disk-backed `/tmp`, build targets, deploy inputs, each Dependabot setting, the ML pins, curl and cache directory). Four first survived and were real test gaps: a bind-mount check that tested only the source, not that the install reads from the target; a check that picked the wrong `RUN` chunk; a `curl` assertion satisfied by the word in the HEALTHCHECK; patterns made ambiguous by the api override.
- **Gaps:** CI gets the smaller image but not the cache-mount speed-up (a fresh runner has an empty builder; the gha cache stores layers, not cache mounts). The SBOM scanner is BuildKit's default, a floating image. Images aren't signed and nothing on the droplet verifies a signature; no Dockerfile linter (Checkov covers part); the lock has no hashes. `ensurepip`'s bundled pip wheel remains in the standard library directory (not an installed pip; CI's image gate found nothing there). The tmpfs sizes (128 MB `/tmp`, 64 MB `$HOME`) were chosen, not measured under production load; the hardening ran on the dev stack, not the droplet. The api's anonymous `/tmp` volume survives a restart, so a crash that leaves a spool file leaves it there. Dependabot's docker entry and cooldown haven't run yet.

### 77. An interface you may swap for a hosted one: speak its wire shape, declare every deviation, and never fill a field you cannot honestly fill
Spec 016 made the ML service answer typed decisions in the request and answer shape of the TypeSafe System One / Jev interface, so the app asks a question once and a hosted implementation can answer it later without changing any caller. Four rules came out of it.
- **Match the documented fields exactly and give every extra a prefix** (`x_served_by`, `x_evidence`, `x_labelset_version`), so a reader of the documented fields never meets one by accident. The client reads documented fields only: a test feeds it an answer built from the hosted documentation (no `x_` field) and checks it's understood.
- **A required field you can't honestly produce is left out and listed, not filled with something that looks right.** The hosted `choice` carries `confidence` and `probabilities`; ours is a cosine similarity to a centroid, which is neither, and a number in the right range under the right name invites a threshold that means nothing. Absence is loud (a caller that needs it can't swap on that question); a pseudo-probability is quiet. The same reasoning made `choice` nullable (the cutoff is the point of a topic matcher), with the difference in a table in the contract.
- **What isn't implemented is a 4xx that names it.** `score`, `noul`, `assets` and an object `state` are 422, so a caller written against the hosted interface learns at once what this implementation doesn't do. Where an input is required for the shape and unused (`instructions`, option descriptions), the contract says so, and the one thing checkable is: the options must equal the label set's labels, catching a question and a set that drifted apart.
- **Say what was not observed.** The hosted interface was never called successfully: the key authenticated and the evaluation endpoint answered 402 until the account has a card. Every hosted field in the contract is the documentation's, the contract says so on its first page, and recording one real response is a listed task. A paragraph that reads like a measurement but is a reading of a manual is how a swap breaks on a field name nobody saw.
- **Gap: nothing proves the two implementations agree.** The local one is judged on `evals/datasets/route-topics`; the hosted one hasn't been. The swap checklist (privacy of the user's text, spend the meter can't see, abstention policy, one recorded response, an evaluation) is a list of decisions, not a feature.

### 83. Compose interpolates the whole file on every command, so a required variable in an opt-in profile breaks every other command
The MCP gateway stack (specs/017, GRAPH_PATTERNS.md 82) needs two generated passwords, and its first compose services wrote `${CASDOOR_DB_PASSWORD:?run make mcp-gateway-up}` so starting it by hand would say what to do. That passed every hermetic test and was caught only when the stack was started for real: **`docker compose config`, `make up` and every other compose command failed with "required variable CASDOOR_DB_PASSWORD is missing a value" for everyone who never starts that stack.** Compose interpolates the entire file before it looks at profiles or at which services a command names, so a `:?` anywhere makes the variable required everywhere.
- **The rule:** the dev compose file requires nothing to be set. A secret defaults to empty (`${VAR:-}`) and the service fails loudly on its own (Postgres refuses to initialise without a superuser password; Casdoor says its admin password isn't set). `main`'s dev file had none; the only existing `:?` is in `docker-compose.observability.prod.yml`, a file a person starts deliberately.
- **Where the value comes from instead:** `make mcp-gateway-up` generates the passwords once into a private directory outside the repo (`~/.cache/agent-core-demo-mcp-gateway/secrets.env`, mode 0600 in a 0700 directory, never overwritten) and hands it to compose as a second `--env-file`, after `.env` when that exists.
- **The test:** `tests/core/test_compose_gateway.py::test_the_dev_compose_file_requires_no_variable_to_be_set` reads the parsed YAML (comments aren't values) and fails on a `${NAME:?` anywhere.
- **Generalises to** anything in a compose file evaluated for the whole file rather than per service, i.e. every `${...}`: a message that helps the person starting one service is a regression for everyone who isn't.

### 86. A smoke check that shares state with its previous run passes once and fails the second time, and a mutation list kept runnable finds the test a review missed
Two lessons from building the authlimit service (specs/018), both about proving a security claim rather than asserting it.
- **State that outlives a run.** `make authlimit-smoke` asserts exact counts against a per-tenant token bucket (the 6th request is limited, a colleague still gets 5). The bucket lives in Redis and refills at half a token a second, so a run 20 seconds after another found the tenant half empty and failed on a count that was correct a minute earlier. The service was right; the check had an input it didn't control. The stage now waits for the refill (22 s) and was run twice back to back to prove it. **Generalises to** any end-to-end check of something with memory (rate limiter, cache, counter): reset it, wait it out, or give each run its own key.
- **A mutation list you can re-run finds what a review doesn't.** `scripts/authlimit_mutants.py` applies 26 deliberate defects (no audience check, an algorithm taken from the token, revocation checked after the limiter, the limiter keyed on a header, a stale key set that never goes stale, …) one at a time and requires a test to fail. The first run caught 22; three didn't compile (the edit, not the code) and **one survived:** trusting a duplicated `X-Forwarded-Uri`. The test appended the forged value AFTER the real one, so reading the first value happened to be right; a forged value arriving first is now a test. The list is a file in the repo because "every deliberate bug is caught" is only as good as the next person's ability to check it; a stale target fails loudly instead of being skipped.
- **Use when:** a security property is claimed in a spec ("a forged header never changes who the caller is") and the only evidence is that the tests pass.

### 87. A live test that rests on what a 3B model infers fails for the model, not the code; a count of OK replies cannot see a call that is valid and wrong
`test-live` was red on `main` from 2026-10-24 (the merge of #194) on one gate test, `test_a_read_only_tool_call_returns_real_data`. Asked "Who is Ecorp's Support Lead?", CI's `qwen2.5:3b` called `query_employees` with `name_contains="Support Lead"`: a job title in a name filter. The call is valid, the tool correctly finds nobody, and the model correctly reports that. Nothing in the app was wrong.
- **A reproduction has to use the Ollama CI uses, and even then it shows a direction, not a CI result.** The fixture pulls `ollama/ollama:latest` (unpinned: 0.40.11 when measured, my host 0.32.15) with no gateway, so the model sees Ollama's own prompt format and no sampling options. Two early attempts reproduced nothing (the host Ollama with the dev alias's options; a hand-rendered Qwen template, where the 3B wrote the right call with the official spaced JSON but `{"department: "Engineering"}`, a key with no closing quote that Ollama's parser discards silently, with Ollama's compact JSON: 73). CI's exact wrong call (`department=None, name_contains="Support Lead"`) reproduced only via `/api/chat` on CI's image with the cached weights mounted, while the **same request through `/v1/chat/completions` on the same server returned no call at all**. Greedy decoding at temperature 0 isn't a fixed outcome for a borderline case: the machine differs (arm64 here, x86 in CI) and so can the prompt-cache state.
- **Measure the levers before changing anything, and keep the ones that don't move.** On the 3B, role questions ("who is the Support Lead?"): 0 of 9 phrasings right, 7 dropped as malformed JSON. A larger context did nothing; `repeat_penalty 1.1` made it worse; clearer argument descriptions helped the 3B (0 → 2 of 9) and slightly hurt the production 7B (7 → 6 of 9), so **the product's tool descriptions were not changed**; the pre-#194 optional-argument schema was worst on name questions (3 of 8 against 7 of 8 now), so #194 isn't what broke the test. What was fragile was the test's question.
- **Ask the question the tool answers.** The test's purpose is the browser → tool → Postgres round trip, not inferring a department from a title. "Is there anyone named Dana at Ecorp?" maps a word in the question onto `name_contains`: 8 of 8 variants called the tool correctly, and the answer named "Dana Whitfield" in all 8. The surname exists only in the database row, so seeing it in the answer still proves the round trip.
- **Why the probe never saw it.** `make probe-tools` reported 13 of 19 and then 14 of 19 for the 3B around #194, and an aggregate pass count can't tell a call that satisfies the schema from one that answers the question. It now compares the arguments a question demands (`Probe.args`), with a role question (department, no name filter) and a name question; the 7B passes all 22 tool-needing prompts. A test shows the job-title call is classified `bad_args`, and that disabling the comparison fails it.
- **Gaps:** the fixture's Ollama is still unpinned, so the parser can change under the test again. The 3B still can't map a title to a department, so that behaviour is covered only for the 7B, by the probe. The two multi-step tests (`skill`, `subagent`) stay in the non-blocking advisory step because a 3B doesn't chain calls reliably.
- **Use when:** a gate test fails on a small model's answer while the tool call itself ran: reproduce under CI's Ollama before reading anything into the prompt, change one lever at a time against more than one phrasing, and fix the question or the tool only for the lever that moved.

### 88. Four ways a check passes without checking, found while proving the API side of the front door
Each was caught because something else forced a look, and each is cheap to guard.
- **A reading that returns a default for "nothing".** `metric_value` answers 0 for a series with no point, and an OpenTelemetry gauge reports a point once per set and then nothing until set again, every call collecting anew. A test that read the gauge's two series with two calls found the first and read the second as 0, the value a wrong implementation would also give. Read every series from ONE collection and assert the side that isn't zero (`tests/api/test_auth_mode_announcement.py::_modes`).
- **A filter over a set that may be empty.** The smoke selected the API's log lines by container name; compose prefixes them `api-1  |`, so the set was empty and "no JWT-shaped string in the API's logs" passed. A check over a selection needs a check that the selection isn't empty.
- **A double that can't know what the real thing wants.** The page's sign-in tests ran against a DOM stub and passed while a real browser got a 400: the authorization server wanted `resource` on the code exchange too. The stub tests now pin the field, but only the real run could find it, so the real run is a tier of its own (`make authlimit-web-check`).
- **A comparison against a series that doesn't exist yet.** `errors > 0 and increase(ok) == 0` is an empty result before the first success, so the alert stayed silent in the case it exists for (the API has never been able to fetch the keys). `errors > 0 unless increase(ok) > 0` fires. (The alert test asserts the operator, since the expression isn't evaluated here.)
- **Use when:** a test, smoke or alert was written to prove something is absent and has never been seen to fail.

### 90. A dependency rule that is not an import scan is a wish
The repository said where things belong ("`app/core` imports nothing from `agent`, `domains` or `api`") and no test read an import. One AST pass over `app/`, written to answer "is this hexagonal?", found 40 violations in 26 files: the cost policy opened Postgres, the graph built its own OpenAI client, the shared tools called Qdrant, the security kernel imported `qdrant_client` because `Policy.lower` returned its filter type, the guard that makes a side effect happen once (Principle IV) talked to Postgres itself. Every one of them was reasonable on the day it was written.
- **State the rule as a list of imports, and keep the list as a ratchet.** `tests/core/test_architecture_layers.py` names the rings, the infrastructure clients and the adapter modules. The violations that existed went into a `LEDGER` that may only shrink (a new violation fails; a listed one that is gone also fails, so the list is deleted from, not left to rot). It started with 40 entries and ended empty, and each change that removed some said which.
- **A scanner needs its own tests.** The table in that file feeds the scanner source strings and asserts exactly which imports it flags, including a function-local `import psycopg` and `from app.core import sql_store`, which a top-level scan of module names would miss.
- **An unbound port fails closed.** A default adapter inside the slot would put the application back in the business of knowing which adapter is the real one. `Slot.get` raises `PortNotBound` naming the port; `tests/core/test_entrypoints_wire.py` fails the build for an entrypoint that never wires, and `tests/core/test_bootstrap.py` for a port with no adapter.
- **A fake is trusted only if it is checked.** `tests/fakes/conformance.py` holds every adapter and every fake to its Protocol (names, async-ness, parameters). A test double that quietly drifts is the same failure as a mock that passes while the code is wrong.
- **Move code, do not rewrite it.** The SQL and HTTP moved verbatim and the adapter classes look the module function up at call time, so the existing SQL-shape tests kept their meaning; the diff to review is where things live and what imports them.
- **Use when:** a rule about what may depend on what is only written in prose, or a new external system is about to be imported from the inside.
