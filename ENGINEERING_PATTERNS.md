# Engineering patterns: lessons about this repository's settings, tests and measurements

Four lessons that are not about the agent: what a settings error must not print, how a test may re-apply a migration to a shared database, when a measurement of a model may be believed, and what to do when a security gate and a dependency's own cap cannot both be satisfied (59 and 60 came from billing). They
were written in `GRAPH_PATTERNS.md` (as patterns 59 and 60) and moved here so that file stays about the graph. They keep their ORIGINAL numbers, so every earlier reference still
resolves; a pattern number is never reused or shifted. The billing-specific parts of each are in [`packages/billing/docs/PATTERNS.md`](packages/billing/docs/PATTERNS.md).

## Patterns

### 59. A settings error must not print the secret it rejected
Pydantic's `ValidationError` prints the raw offending value (`input_value='...'`), a `Settings()` error is raised at import time, and the output goes to a terminal or a container log. Checked, not assumed: with an API key set to a value its validator rejects, the startup error repeated the key whole, and so would a credential pasted into the wrong variable.
- **One line closes it for every field.** `hide_input_in_errors=True` on the settings class: the error still names the field and the rule and no longer repeats the value. A test per path (a rejected credential, a malformed map of secrets) fails without it; each was checked against the mutant that removes it. It is class-wide, so every other settings error also stops quoting its value (the field name and rule remain).
- **Credentials are `SecretStr`, and a blank is "not set".** A variable left in `.env` with no value arrives as an empty string, which would otherwise be a credential that is empty and fail its format check with a confusing message. Only a blank is touched before wrapping; a real value is never inspected in the clear. The one mistake worth catching at startup is pasting the wrong kind of key.
- **A setting that nothing reads is a promise the code does not keep**, so when one was deliberately removed a test pins its absence.
- **A warning that can go stale is pinned.** A comment in `.env.example` that says "do not enable X until Y exists" has a test that fails the day Y exists, as the prompt to rewrite the comment.
- The billing package's own credential settings (the key-prefix checks, the sandbox default, the verification numbers and the disclosed gaps) are in `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md".

### 60. A test that re-applies a migration to a shared database must be the one that gives up
A test that checks "this migration can be applied twice" failed about one parallel run in seven, and in one full integration run the victim was an unrelated test that failed with `DeadlockDetected` instead of its injected error. Tests re-apply migrations to the database the other xdist workers are writing to, and re-running DDL is not harmless there. Measured on a real Postgres rather than assumed: a no-op `ALTER TABLE … ADD COLUMN IF NOT EXISTS` takes an **ACCESS EXCLUSIVE** lock, `CREATE INDEX IF NOT EXISTS` a **SHARE** lock and `CREATE OR REPLACE TRIGGER` a **SHARE ROW EXCLUSIVE** lock, all on tables other tests hold row locks on.
- **Why the wrong test failed.** A concurrent transaction that holds a lock on one table and waits for another forms a cycle with the script, and Postgres aborts whichever session's `deadlock_timeout` (1 s here) runs its check first. That is the session that began waiting first, so it was the unlucky DML test, not the DDL one. Catching and retrying inside the DDL test would not have helped: the victim was somebody else.
- **The fix makes this session always give up first.** `tests/integration/schema_reapply.py::reapply` sets a `lock_timeout` (300 ms) shorter than `deadlock_timeout`, so the script abandons a wait and rolls back before any deadlock check can run; that dissolves the cycle, the other transaction continues, and the idempotent script is tried again with jitter. A `DeadlockDetected` is deliberately not retried: with the timeout in place it cannot happen, and if it does the assumption is wrong and the test should say so. A test asserts the timeout stays below `deadlock_timeout`.
- **The cycle is built on purpose, not hoped for.** A test takes a lock the script needs, waits until the script is actually blocked on it (read from `pg_locks`), then asks for a lock the script already holds. Without the timeout that is a deadlock within a second.
- **A hang is the worst way for a test to fail.** The first mutant run hung (with the timeout removed, the "never released" test waits forever) and the harness timed out, leaking a container. Every re-apply in the tests is now bounded by `asyncio.wait_for`, so a regression is a failure with a name, not a stalled CI job.
- **The same cause wore a second, misleading face.** A later failure was `DID NOT RAISE UniqueViolation`, which looks like a missing unique index. It was not: the code under test never raises (a failure is recorded and returned as a value), the test discarded that outcome, the deadlock had killed the FIRST write, and so the second one "succeeded". The tests that set the stage with a bare call and could fail the same way now go through a helper that asserts the setup did not fail, with a test that it does.
- **Verified:** real-Postgres tests of the helper itself. **Mutation check: 5 mutants, 4 caught** (no `lock_timeout`, a timeout longer than the deadlock check, no retry, giving up silently); the fifth, also retrying `DeadlockDetected`, is **equivalent** once the timeout is in place (nothing can deadlock), and is not counted as a gap. **16 of 16 parallel runs of the affected files were clean**, against about one failure in seven before.
- **Gaps (disclosed):** other tests that run DDL against the shared database are not covered unless they use the helper; `.claude/rules/testing.md` says so. `lock_timeout` bounds this session only: a test that holds a lock for tens of seconds would still make the re-apply fail after its 60 tries.
- The billing-specific parts (the migration whose lock order the cycle test depends on, the webhook test that was the victim) are in `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md". The package keeps its own copy of the helper (`packages/billing/tests/integration/schema_reapply.py`), because it cannot import this repository's.

### 69. A model decision is made by a frozen evaluation, and a benchmark number is only valid on the hardware and the text it was measured on
Choosing an embedding, reranking or screening model by a blog post or a model card is how a deployment ends up with a model that is better on someone else's data. `make model-eval` (`scripts/model_eval/`, data in `evals/`, [`evals/README.md`](evals/README.md)) exists so the answer is a report: the candidate next to the recorded result of the model in use, on this repository's own questions, with confidence intervals and a verdict. Building it surfaced five ways a measurement lies, each now enforced rather than remembered.
- **Frozen data, immutable baselines.** A dataset's manifest records the sha256 of every file and a mismatch stops the run; `dev` (for tuning) is refused for reporting and is disjoint from `test` by id and by near-duplicate text; a baseline cannot be overwritten without `FORCE=1`, and one recorded against an unreviewed set is `provisional` (computed from the items' `reviewed` flags, not typed). Public sets are pinned by commit and per-file hash, carry a licence from a short allow-list, and are never redistributed.
- **Controls, because a harness that cannot tell a model from itself is worse than none.** Every report carries the baseline against itself (must be `no_difference`) and a useless model (must be `worse`); if either fails the report is `INVALID` and the command exits 5. Real data corrected the first design: a screen that scores at random flags about half of everything at the 0.5 threshold, so its *recall* (about 0.5) is as good as the real screen's (0.47), and judging it "worse" on recall made `make model-eval-verify` fail on the committed baseline. A control must be judged on the metrics that mean "it works" for that kind of uselessness: ranking and false alarms for a random scorer, detection for a screen that flags nothing (whose false-positive rate is perfect). `tpr@1%fpr` is judged for neither: with a few dozen benign items the cap allows zero false positives and a random scorer can reach a non-zero rate by luck.
- **`inconclusive` is not "equal".** A verdict is `better` or `worse` only if the paired-bootstrap interval excludes zero (2,000 resamples over queries, fixed seed, the candidate and the baseline resampled with the SAME indices, because comparing two independent intervals throws away the pairing and widens the answer to nothing); an interval that merely touches zero is `inconclusive` and says how many more items would settle it (`needed_n`, labelled an estimate). A few hundred items cannot resolve a one-point difference, and the report says so.
- **Hardware is part of the number.** Latency is stored keyed by a hardware id and never compared across ids. On an ARM laptop CPU fastembed's int8 bge-small was *slower* than the official fp32 file (35.8 vs 17.1 ms per chunk), nomic as fp32 ONNX on CPU is 3-5x slower than Ollama on Metal while a small model is on par, and a baseline recorded while the machine was busy (a 1-minute load of 19-23 on 12 cores, the first time they were recorded) is stored with that warning and makes every later comparison against it say so. Quality numbers do not depend on load and are never discounted.
- **Measure the text the system really sees.** A 110-token synthetic paragraph understated the real 259-token markdown chunks by 2.4x, and the first reported cost per chunk was 2.7x too high. The retrieval set is chunked by the app's own chunker.
- **Verified:** the metrics are checked against hand-computed values written out in the tests (recall, MRR, NDCG with its discount, ROC-AUC with ties, TPR at a fixed FPR, macro-F1, ECE, the routing curves); the whole harness is hermetic (a socket guard test). **Mutation check: 23 mutants, all caught in the end, and 5 survived first**, which were real gaps rather than equivalent mutants: the inclusive false-positive cap in `tpr_at_fpr` (`<=` vs `<`), an interval that only touches zero being called significant, the percentile of the confidence interval, a "worse" control accepting `inconclusive`, and the sha256 check of a cached public file. Each now has a test that fails without it.
- **Gaps (disclosed):** the repository-own sets are small (tens of chunks, about a hundred questions, 67 screening items) and unreviewed by a person, so they can separate a good model from a useless one and cannot rank two good ones within a point; questions are written by a 7B local model and skew toward factual lookups of the passage; latency is measured on one machine; and the control for a random scorer is judged on three metrics because a fourth would flip with the seed on this set size.

### 72. A security gate that cannot be satisfied gets a dated, reasoned exception, and tests that keep the reasons true
On 2026-10-21 CI's `trivy` job went red on every PR without any of them touching a dependency: its vulnerability database had learned about CRITICAL findings in packages `requirements-lock.txt` already pinned (certifi 2026.7.22, pillow 12.3.0). A hard gate that is red for everyone is ignored by everyone, so it has to be fixed or deliberately and visibly excepted, never worked around.
- **Fix what can be fixed, at the place it lives.** certifi had no cap: a one-line lock bump (GHSA-6q48-6c7w-9gw2, a CA bundle that trusts compromised emSign intermediates), checked with `pip install --dry-run` against the environment that mirrors the lock. The image scan reported a SECOND certifi that the lock cannot reach: `pip/_vendor/certifi`, inside the base image's own pip (26.2.1 vendored 2026.6.17). Only a newer pip (26.2.2 vendors 2026.10.19) clears it, so the Dockerfile upgrades pip before installing the lock. Found by reading the scan's output block and then the image, not by assuming the lock was the whole story.
- **Read what the gate says, then check it again where it will run.** The scan CI ran on 10-21 listed one pillow finding; the same scan locally the next day listed three, because the database moved. Fixing "the finding in the log" would have gone red again. The scan that decides is run with the official image (`aquasec/trivy`, the same hard-gate flags) before pushing.
- **When the only fix cannot be installed, say so and bound it.** pillow's three findings are fixed only in 13.0.0, and fastembed (every release through 0.9.0) declares `pillow<13.0` on Python 3.13, which the app uses for sparse retrieval. Forcing 13 would be overriding a declared constraint on an untested combination, and `pip` would refuse the lock outright. `.trivyignore.yaml` carries one entry per CVE, each with a `statement` of why it is safe to carry (what the vulnerable call needs, and the evidence that nothing here makes it: no `thumbnail()`/`draft()` call, no `save()` of TIFF, no Ghostscript binary in the image) and an `expired_at` that brings it back and fails the gate again. Checked with the real scanner: 3 findings without the file, 0 with it, 3 again with the dates in the past.
- **The reasons are tests, not prose.** `tests/core/test_trivy_ignore.py` fails if first-party code imports PIL or calls `thumbnail`/`draft`, if the Dockerfile installs Ghostscript, if the lock moves to pillow 13 (the entries are then dead weight and would hide the next finding with the same ids), if an entry has no statement or no expiry, if the lock goes back to a vulnerable certifi, if the Dockerfile stops upgrading pip, or if a hard gate stops reading the file. Each of those mutations was run against a copy and caught by the intended test.
- **Only the hard gates read the exception.** The full-report steps feed the Security tab and `make trivy` is the local view; neither reads `.trivyignore.yaml`, so an accepted risk stays on the list of everything.
- **Gap: this does not make pillow safe, it makes it not-reachable-today.** A new first-party use of Pillow, or a dependency that starts decoding images in-process, breaks the premise; the test catches the first and not the second (it cannot see inside a dependency), and a fourth Pillow finding published before fastembed allows 13 would need a fourth entry or a decision to override the cap. The exit is a fastembed release with a wider cap, then bump the lock and delete the file's entries; the dates (2026-12-01) are there so that is looked at, not forgotten.
