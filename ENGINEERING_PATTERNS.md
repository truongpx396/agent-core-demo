# Engineering patterns: lessons about this repository's settings, tests and measurements

Six lessons that are not about the agent: what a settings error must not print, how a test may re-apply a migration to a shared database, when a measurement of a model may be believed, what to do when a security gate and a dependency's own cap cannot both be satisfied, how to trust a topic matcher, and how the container image is built and what it must not contain (59 and 60 came from billing). They
were written in `GRAPH_PATTERNS.md` (as patterns 59 and 60) and moved here so that file stays about the graph. They keep their ORIGINAL numbers, so every earlier reference still
resolves; a pattern number is never reused or shifted. The billing-specific parts of each are in [`packages/billing/docs/PATTERNS.md`](packages/billing/docs/PATTERNS.md).

## Patterns

### 59. A settings error must not print the secret it rejected
Pydantic's `ValidationError` prints the raw offending value (`input_value='...'`), a `Settings()` error is raised at import time, and the output goes to a terminal or a container log. Checked, not assumed: with an API key set to a value its validator rejects, the startup error repeated the key whole, and so would a credential pasted into the wrong variable.
- **One line closes it for every field.** `hide_input_in_errors=True` on the settings class: the error still names the field and the rule and no longer repeats the value. A test per path (a rejected credential, a malformed map of secrets) fails without it; each was checked against the mutant that removes it. It is class-wide, so every other settings error also stops quoting its value (the field name and rule remain).
- **Credentials are `SecretStr`, and a blank is "not set".** A variable left in `.env` with no value arrives as an empty string, which would otherwise be a credential that is empty and fail its format check with a confusing message. Only a blank is touched before wrapping; a real value is never inspected in the clear. The one mistake worth catching at startup is pasting the wrong kind of key.
- **A setting that nothing reads is a promise the code does not keep**, so when one was deliberately removed a test pins its absence.
- **A warning that can go stale is pinned.** A comment in `.env.example` that says "do not enable X until Y exists" has a test that fails the day Y exists, as the prompt to rewrite the comment.
- The billing package's own credential settings (the key-prefix checks, the sandbox default, the verification numbers and the disclosed gaps) are in `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md".

### 60. A test that re-applies a migration to a shared database must be the one that gives up
A test that checks "this migration can be applied twice" failed about one parallel run in seven, and in one full integration run the victim was an unrelated test that failed with `DeadlockDetected` instead of its injected error. Tests re-apply migrations to the database the other xdist workers are writing to, and re-running DDL is not harmless there. Measured on a real Postgres rather than assumed: a no-op `ALTER TABLE … ADD COLUMN IF NOT EXISTS` takes an **ACCESS EXCLUSIVE** lock, `CREATE INDEX IF NOT EXISTS` a **SHARE** lock and `CREATE OR REPLACE TRIGGER` a **SHARE ROW EXCLUSIVE** lock, all on tables other tests hold row locks on.
- **Why the wrong test failed.** A concurrent transaction that holds a lock on one table and waits for another forms a cycle with the script, and Postgres aborts whichever session's `deadlock_timeout` (1 s here) runs its check first. That is the session that began waiting first, so it was the unlucky DML test, not the DDL one. Catching and retrying inside the DDL test would not have helped: the victim was somebody else.
- **The fix makes this session always give up first.** `tests/integration/schema_reapply.py::reapply` sets a `lock_timeout` (300 ms) shorter than `deadlock_timeout`, so the script abandons a wait and rolls back before any deadlock check can run; that dissolves the cycle, the other transaction continues, and the idempotent script is tried again with jitter. A `DeadlockDetected` is deliberately not retried: with the timeout in place it cannot happen, and if it does the assumption is wrong and the test should say so. A test asserts the timeout stays below `deadlock_timeout`.
- **The cycle is built on purpose, not hoped for.** A test takes a lock the script needs, waits until the script is actually blocked on it (read from `pg_locks`), then asks for a lock the script already holds. Without the timeout that is a deadlock within a second.
- **A hang is the worst way for a test to fail.** The first mutant run hung (with the timeout removed, the "never released" test waits forever) and the harness timed out, leaking a container. Every re-apply in the tests is now bounded by `asyncio.wait_for`, so a regression is a failure with a name, not a stalled CI job.
- **The same cause wore a second, misleading face.** A later failure was `DID NOT RAISE UniqueViolation`, which looks like a missing unique index. It was not: the code under test never raises (a failure is recorded and returned as a value), the test discarded that outcome, the deadlock had killed the FIRST write, and so the second one "succeeded". The tests that set the stage with a bare call and could fail the same way now go through a helper that asserts the setup did not fail, with a test that it does.
- **Verified:** real-Postgres tests of the helper itself. **Mutation check: 5 mutants, 4 caught** (no `lock_timeout`, a timeout longer than the deadlock check, no retry, giving up silently); the fifth, also retrying `DeadlockDetected`, is **equivalent** once the timeout is in place (nothing can deadlock), and is not counted as a gap. **16 of 16 parallel runs of the affected files were clean**, against about one failure in seven before.
- **Gaps (disclosed):** other tests that run DDL against the shared database are not covered unless they use the helper; `.claude/rules/testing.md` says so. `lock_timeout` bounds this session only: a test that holds a lock for tens of seconds would still make the re-apply fail after its 60 tries.
- The billing-specific parts (the migration whose lock order the cycle test depends on, the webhook test that was the victim) are in `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md". The package keeps its own copy of the helper (`packages/billing/tests/integration/schema_reapply.py`), because it cannot import this repository's.

### 69. A model decision is made by a frozen evaluation, and a benchmark number is only valid on the hardware and the text it was measured on
Choosing an embedding, reranking or screening model by a blog post or a model card is how a deployment ends up with a model that is better on someone else's data. `make model-eval` (`scripts/model_eval/`, data in `evals/`, [`evals/README.md`](evals/README.md)) exists so the answer is a report: the candidate next to the recorded result of the model in use, on this repository's own questions, with confidence intervals and a verdict. Building it surfaced five ways a measurement lies, each now enforced rather than remembered.
- **Frozen data, immutable baselines.** A dataset's manifest records the sha256 of every file and a mismatch stops the run; `dev` (for tuning) is refused for reporting and is disjoint from `test` by id and by near-duplicate text; a baseline cannot be overwritten without `FORCE=1`, and one recorded against an unreviewed set is `provisional` (computed from the items' `reviewed` flags, not typed). Public sets are pinned by commit and per-file hash, carry a licence from a short allow-list, and are never redistributed.
- **Controls, because a harness that cannot tell a model from itself is worse than none.** Every report carries the baseline against itself (must be `no_difference`) and a useless model (must be `worse`); if either fails the report is `INVALID` and the command exits 5. Real data corrected the first design: a screen that scores at random flags about half of everything at the 0.5 threshold, so its *recall* (about 0.5) is as good as the real screen's (0.47), and judging it "worse" on recall made `make model-eval-verify` fail on the committed baseline. A control must be judged on the metrics that mean "it works" for that kind of uselessness: ranking and false alarms for a random scorer, detection for a screen that flags nothing (whose false-positive rate is perfect). `tpr@1%fpr` is judged for neither: with a few dozen benign items the cap allows zero false positives and a random scorer can reach a non-zero rate by luck.
- **A classifier's controls can fail because of the labels, and the report must say so.** The routing head is judged on labelled outcomes (what a local and a stronger model each scored on the same prompt, by a judge). The first real run had a mean advantage of the strong model of +0.032 on a coarse 0-1 scale, so even a PERFECT router (the oracle-based derived control) could not be told from a random one: the report was `INVALID` and said only "a control did not come out as expected", which reads as a harness bug. It now adds a `WHY:` warning with the measured advantage. The harness was right and the data could not support a claim; both trained heads then came out at the never-escalate accuracy and below a random router's curve, and stayed unaccepted. The lesson is upstream of the router: before training anything, check that the stronger model wins clearly on a meaningful share of the prompts, with a judge that is not the model being judged.
- **`inconclusive` is not "equal".** A verdict is `better` or `worse` only if the paired-bootstrap interval excludes zero (2,000 resamples over queries, fixed seed, the candidate and the baseline resampled with the SAME indices, because comparing two independent intervals throws away the pairing and widens the answer to nothing); an interval that merely touches zero is `inconclusive` and says how many more items would settle it (`needed_n`, labelled an estimate). A few hundred items cannot resolve a one-point difference, and the report says so.
- **Hardware is part of the number.** Latency is stored keyed by a hardware id and never compared across ids. On an ARM laptop CPU fastembed's int8 bge-small was *slower* than the official fp32 file (35.8 vs 17.1 ms per chunk), nomic as fp32 ONNX on CPU is 3-5x slower than Ollama on Metal while a small model is on par, and a baseline recorded while the machine was busy (a 1-minute load of 19-23 on 12 cores, the first time they were recorded) is stored with that warning and makes every later comparison against it say so. Quality numbers do not depend on load and are never discounted.
- **Measure the text the system really sees.** A 110-token synthetic paragraph understated the real 259-token markdown chunks by 2.4x, and the first reported cost per chunk was 2.7x too high. The retrieval set is chunked by the app's own chunker.
- **Verified:** the metrics are checked against hand-computed values written out in the tests (recall, MRR, NDCG with its discount, ROC-AUC with ties, TPR at a fixed FPR, macro-F1, ECE, the routing curves); the whole harness is hermetic (a socket guard test). **Mutation check: 23 mutants, all caught in the end, and 5 survived first**, which were real gaps rather than equivalent mutants: the inclusive false-positive cap in `tpr_at_fpr` (`<=` vs `<`), an interval that only touches zero being called significant, the percentile of the confidence interval, a "worse" control accepting `inconclusive`, and the sha256 check of a cached public file. Each now has a test that fails without it.
- **Gaps (disclosed):** the repository-own sets are small (tens of chunks, about a hundred questions, 67 screening items) and unreviewed by a person, so they can separate a good model from a useless one and cannot rank two good ones within a point; questions are written by a 7B local model and skew toward factual lookups of the passage; latency is measured on one machine; and the control for a random scorer is judged on three metrics because a fourth would flip with the seed on this set size.

### 72. A security gate that cannot be satisfied gets a dated, reasoned exception, and tests that keep the reasons true
On 2026-10-21 CI's `trivy` job went red on every PR without any of them touching a dependency: its vulnerability database had learned about CRITICAL findings in packages `requirements-lock.txt` already pinned (certifi 2026.7.22, pillow 12.3.0). A hard gate that is red for everyone is ignored by everyone, so it has to be fixed or deliberately and visibly excepted, never worked around.
- **Fix what can be fixed, at the place it lives.** certifi had no cap: a one-line lock bump (GHSA-6q48-6c7w-9gw2, a CA bundle that trusts compromised emSign intermediates), checked with `pip install --dry-run` against the environment that mirrors the lock. The image scan reported a SECOND certifi that the lock cannot reach: `pip/_vendor/certifi`, inside the base image's own pip (26.2.1 vendored 2026.6.17). Only a newer pip (26.2.2 vendors 2026.10.19) clears it, so the Dockerfile upgrades pip before installing the lock. Found by reading the scan's output block and then the image, not by assuming the lock was the whole story.
- **Read what the gate says, then check it again where it will run.** The scan CI ran on 10-21 listed one pillow finding; the same scan locally the next day listed three, because the database moved. Fixing "the finding in the log" would have gone red again. The scan that decides is run with the official image (`aquasec/trivy`, the same hard-gate flags) before pushing.
- **When the only fix cannot be installed, say so and bound it.** pillow's three findings are fixed only in 13.0.0, and fastembed (every release through 0.9.0) declares `pillow<13.0` on Python 3.13, which the app uses for sparse retrieval. Forcing 13 would be overriding a declared constraint on an untested combination, and `pip` would refuse the lock outright. `.trivyignore.yaml` carries one entry per CVE, each with a `statement` of why it is safe to carry (what the vulnerable call needs, and the evidence that nothing here makes it: no `thumbnail()`/`draft()` call, no `save()` of TIFF, no Ghostscript binary in the image) and an `expired_at` that brings it back and fails the gate again. Checked with the real scanner: 3 findings without the file, 0 with it, 3 again with the dates in the past.
- **The reasons are tests, not prose.** `tests/core/test_trivy_ignore.py` fails if first-party code imports PIL or calls `thumbnail`/`draft`, if the Dockerfile installs Ghostscript, if the lock moves to pillow 13 (the entries are then dead weight and would hide the next finding with the same ids), if an entry has no statement or no expiry, if the lock goes back to a vulnerable certifi, if the Dockerfile stops upgrading pip, or if a hard gate stops reading the file. Each of those mutations was run against a copy and caught by the intended test.
- **Only the hard gates read the exception.** The full-report steps feed the Security tab and `make trivy` is the local view; neither reads `.trivyignore.yaml`, so an accepted risk stays on the list of everything.
- **Gap: this does not make pillow safe, it makes it not-reachable-today.** A new first-party use of Pillow, or a dependency that starts decoding images in-process, breaks the premise; the test catches the first and not the second (it cannot see inside a dependency), and a fourth Pillow finding published before fastembed allows 13 would need a fourth entry or a decision to override the cap. The exit is a fastembed release with a wider cap, then bump the lock and delete the file's entries; the dates (2026-12-01) are there so that is looked at, not forgotten.

### 75. A topic matcher's cutoff belongs to a model, its examples to their text, and what it does with the unmatched is measured on real prompts
Spec 015 added label sets: a reviewed file of choices with example sentences, matched to a text by embedding centroid (`docker/ml-service/labelsets/`, `POST /classify task=label`), used by the model router and by any agent step that must pick among a few predefined choices. Four things went wrong or nearly went wrong while it was built, and each is now a rule.
- **A similarity cutoff is a property of the model that produced the similarities.** The same label set needed 0.709 for bge-small and 0.247 for MiniLM (chosen on the same dev split), and the service's fallback IS the other model. A single app-side threshold would have been right for one and meaningless for the other, with no error anywhere. So the cutoff lives in the set, per model, and a model without an entry does not serve the set; there is no default to fall back to. The same reasoning that binds a head to a model revision (pattern 68).
- **Store the examples as text, not as vectors.** A stored vector is valid for one model revision only and its failure is confident nonsense; text cannot go stale. The service embeds a set's examples with the model that serves the request, and again when that model reloads under a different revision (a test mutates the revision and asserts the stale index never answers).
- **A claim about what the matcher does with text it should not match must be measured before it is written.** A draft of the research notes said the unmatched sentences "almost always land on `smalltalk`"; counted, they land on six different labels. And a property measured on sentences the author wrote did not carry to sentences users write: on the authored set the margin to the runner-up was 0.010 for wrong labels against 0.068 for right ones, on the repository's real prompts it was 0.029 against 0.028. The first look at those prompts showed the label signal sending 11% of ordinary knowledge-base questions up a tier (a pricing question read as `reasoning`, a runbook question read as `code`). Read the router's output on the traffic it will see before turning it on; that is what `ROUTER_MODE=shadow` is for.
- **Choose the cutoff on one split and report on another, and say which sentences informed an example.** `make labelset-calibrate` reads only `dev`; after errors were read on the real prompts' dev split and ten examples added, the held-out split went from 7 of 91 routed up to 5 of 91, which is stated as a small effect on 91 prompts and not as a fix, and a test now fails if an example is a near-duplicate of any of those prompts.
- **Tests that pass the first time are suspect.** The 407 policy tests passed on their first run, and all but one of the label-set tests did (the one was the author's miscount, not a bug); a mutation check (deliberate bugs, one at a time) then found seven real gaps in the two sets of tests together: the cutoff's inclusive edge, the centroid's renormalisation and the normalisation of long examples, the `failed` state after a model error, unreadable files, a word-boundary test whose text contained only one would-be match, and the clamp on the logged similarity band. The evaluation data's tenant-name guard also rejected a draft sentence ("Globex"), which is the guard doing its job.
- **Gap: the label table and the rules are policy.** Nothing measured says the tiers they pick give better answers (`specs/015-label-sets-and-tiered-routing/research.md`).

### 76. The images are built in stages with uv and a cache mount, carry no installer, and run hardened
On 2026-10-23 rebuilding the app image after a lock change (#181) spent 347.7 s in `pip install` on the maintainer's laptop. The Dockerfile was one stage and ran `pip install --no-cache-dir -r requirements-lock.txt`, so any cache miss on that layer downloaded every package again; the image it produced still carried pip, whose vendored certifi Trivy reads as a second certifi that the lock cannot reach (pattern 72); the Python base image floated, so two builds of one commit could differ; and nothing restricted how the containers run. This covers both images production pulls (the app image, for the api and both worker roles, and the ML service image) and how they are published and run. The pieces are made together because each is half a fix alone: a cache without a faster installer still pays the install, a faster installer without a cache still downloads, and neither changes what ships or how it runs.
- **Four stages in both Dockerfiles, and the one that ships is last.** `base` (the Python image), `uv` (the installer), `builder` (installs the dependencies into a virtualenv at `/opt/venv`; thrown away) and `runtime` (the last stage, so what `docker build .` and every `build: .` in compose produce: the base, the OS packages, the virtualenv copied in at the same path because a virtualenv's scripts name their interpreter by absolute path, and the app). Both stages build on the one `base`, so the interpreter the virtualenv links to is the one it was built for. The compose builds and `deploy.yml` also name `target: runtime`, so a reordered Dockerfile fails a build instead of shipping the builder.
- **Pinned by digest and bumped by a bot, not floated.** `base` is the multi-architecture index of `python:3.13-slim` (linux/amd64 and linux/arm64) and `uv` is `0.12.24` (the 0.13 line was days old when it was chosen), each its own `FROM` line so Dependabot, which reads those, can propose the bump. `.github/dependabot.yml` gains a `docker` entry for both Dockerfiles: weekly, a 14-day cooldown (the rule the uv pin was chosen by), the Python minor never moved (3.13 is what the lock was resolved for). The compose files are deliberately not read: the `docker-compose` ecosystem would also propose postgres major versions, so the LiteLLM digest stays a hand bump with `make gateway-check` (pattern 74). What keeps a pinned base fresh: that weekly proposal, `apt-get upgrade` whenever the layer is rebuilt, and CI's Trivy image gate failing if the pinned base ages into a fixable CRITICAL. `tests/core/test_dockerfile_build.py` runs over both files and fails if their two digests ever differ.
- **A cache mount for uv's wheel cache and a bind mount for the dependency file.** The wheel cache lives in the builder between builds and is never part of an image; the file is bind-mounted so no layer holds it, and BuildKit still keys the step on its content, so it reruns exactly when the file changes and a change downloads only what changed. `UV_LINK_MODE=copy` (the cache is another filesystem, so hard links cannot work) and `UV_COMPILE_BYTECODE=1` (the .pyc files are written at build time, because a non-root container cannot write them under a root-owned virtualenv and would compile on every start). The two images share the cache, so the ML service's install reused most of what the app build had fetched.
- **No installer in what ships.** The runtime stage runs `python -m pip uninstall -y pip setuptools wheel` and never copies uv; the virtualenv uv made has no pip. Nothing in the running app installs anything (the sandbox prompts tell the model not to). The vendored certifi and any future pip finding leave with it, replacing the old "upgrade pip first" step; `tests/core/test_trivy_ignore.py` pins the new form. A consequence: `docker exec <container> pip install ...` no longer works; to debug with tools, build the builder stage (`docker build --target builder`).
- **Hardened at runtime, in both compose files.** The api, the four agent workers, the ingest worker and the ML service (dev); the api, the agent worker, the ingest worker and the ML service (prod) get `init: true` (a real PID 1 that reaps the sandbox bridge's children and forwards SIGTERM, so `stop_grace_period` is honoured), `no-new-privileges`, `cap_drop: ALL` and `read_only: true`, with the writes that remain going to size-capped tmpfs (a tmpfs counts against the container's memory limit). One anchor, merged service by service, never applied to the third-party services whose write paths nobody has checked. **Running the image this way found two things reading the code did not.** (1) The first version gave only `~/.cache` a tmpfs and the api crashed at start: `crawl4ai` creates `~/.crawl4ai` the moment it is IMPORTED (`OSError: Read-only file system`), a third-party write that a search of first-party code cannot see. So `$HOME` itself is a tmpfs owned by the app user (`uid=1000,gid=1000`), which also covers the next library's dot-directory. (2) A tmpfs `/tmp` is the wrong place for uploads: the multipart parser spools every file to `/tmp` before the handler runs, the limits allow 5 x 25 MB per request, and a 128 MB tmpfs stops at 128 MiB (shown: `dd` of 200 MB into it) while holding the spool in RAM against the prod api's 512 MB limit. So the api, the only role that receives uploads, has a disk-backed anonymous volume at `/tmp` (200 MB went in) and tmpfs only for `$HOME`; `tests/core/test_compose_hardening.py` pins that, and that no tmpfs covers the ML service's model volume.
- **Published with a bill of materials and provenance.** `deploy.yml` builds the app image from `target: runtime` and attaches `sbom: true` and `provenance: mode=max` to both images (the layer cache already used `mode=max`, which is what exports the builder stage's layers). **Not run:** that workflow only runs on `main` after CI, so these inputs are pinned by `tests/core/test_deploy_workflow_images.py` as text and will be exercised by the first deploy.
- **Measured, on the maintainer's arm64 laptop, one run each; not a controlled comparison with the pasted 347.7 s** (a different run, at a different moment on the network, with other builds going). App image, cold with an empty uv cache: 2 min 47 s end to end (91 s of it pulling the 19 MB uv image from ghcr over a slow network, a one-time cost per machine, and 27 s exporting), the install step **29.8 s** (170 packages resolved in 4.8 s, downloaded in 16.7 s, installed in 2.8 s, 13,056 files byte-compiled in 4.3 s). One pin changed in the lock (certifi): 51 s end to end, the install step **11.4 s** ("Prepared 1 package", the other 169 from the cache mount). Rebuilt on the new base digest (every apt layer re-ran): 1 min 14 s. ML service image: 3 min 10 s end to end, mostly its apt layers; its 37 packages resolved in 1.8 s, 15 downloaded in 4.5 s (the other 22 were already in the shared cache), installed in 0.7 s. Image sizes: app 1.67 GB against 1.69 GB for the old Dockerfile's on the same lock, ML 529 MB against 531 MB: about what pip and its leftovers weighed; the dependencies are the size.
- **Run, on the built images, under the exact flags compose renders:** the app image as the api role on the real dev network: healthy, `/health` 200 and `/health/ready` 200 with qdrant, both Postgres databases, redis and the ML service all reachable; uid 1000, `CapEff` 0, `NoNewPrivs` 1, PID 1 `docker-init`; `/app`, the interpreter's directory and `/opt/venv` read-only, `/tmp` and `$HOME` writable; the app's own sparse-embedding model (`Qdrant/bm25`) fetched and used in 2.5 s into the tmpfs; a 4 MB spooled upload; CI's own `docker-build` check (skills, subagents, sandbox bridge, scripts all landed) on the image earlier; and `pip`, `python -m pip` and `uv` absent. The ML service image: `/health` 200 within 20 s with an empty model volume, port 80 bound as uid 1000 with no capability (Docker's `ip_unprivileged_port_start`), the models I saw in `/health/models` (rerank, prompt-guard, bge-small) `ready` in about 30 s (my output was cut off before the rest), no read-only, permission or capability errors in its log. The throwaway containers and volume were removed; the running stack was not touched.
- **CI, on the first version of this change (the app Dockerfile only):** 17 of 18 checks green, `docker-build` in 48 s (1 min 26 s before), and the one red, `trivy`, listed **only** pillow CVE-2026-96639 in both gates (`Total: 1`), nothing about pip, uv or `ensurepip`: the removed pip left no finding behind. That red is pattern 72's cap and is on `main` too.
- **CI on the full change found what no local run could: the test harness built the ML image with the Docker SDK's legacy builder.** `tests/containers.py` called `docker.from_env().images.build(...)`, whose builder rejects `RUN --mount` ("the --mount option requires BuildKit"). `test-integration` (23 setup errors and 1 failure, `No such image: agent-core-demo-ml-service:test`, the same cause one step later) and `test-live` (4 setup errors) failed on that alone; the first version of this PR had not touched the ML Dockerfile, so it passed. Reproduced locally with the old call, then fixed: the harness builds with the Docker CLI (BuildKit) through `_build_image`, and a test fails if any test calls `images.build(`. The lesson is about adopting a build feature: it is only as portable as the least capable builder anyone uses, and I had checked CI's job and compose, not the Python harness. Grep for every way an image is built (SDK, CLI, compose, workflow actions) before adopting one.
- **Verified:** 36 new hermetic tests (`test_dockerfile_build.py` runs 21, 19 over both Dockerfiles and 2 for the harness, `test_compose_hardening.py` 8, `test_deploy_workflow_images.py` 7), the rewritten pip test and a fixed healthcheck helper, 2,496 across `tests/core`, `tests/scripts`, `tests/billing` and `tests/agent`; **49 mutants, all caught**: 15 for the app Dockerfile, 31 for the rest and 3 for the harness helper (each hardening flag, the home tmpfs and its ownership, the api's disk-backed `/tmp`, the build targets, the deploy inputs, each Dependabot setting, the ML service's pins, curl and cache directory). Four mutants first survived or were skipped and were genuine test gaps, now fixed: a test that checked only a bind mount's source and not that the install reads from its target, a check that picked the wrong `RUN` chunk, a `curl` assertion satisfied by the word in the HEALTHCHECK, and patterns made ambiguous by the api override.
- **Gaps (disclosed):** CI gets the smaller image but not the cache-mount speed-up (a fresh runner has an empty builder; the gha cache stores layers, not cache mounts). The SBOM scanner is BuildKit's default, a floating image. Images are not signed and nothing on the droplet verifies a signature; no Dockerfile linter (Checkov covers part). The lock has no hashes (uv would enforce `--require-hashes` if it did). `ensurepip`'s bundled pip wheel is still in the standard library directory (not an installed pip), and CI's image gate found nothing there. The tmpfs sizes (128 MB `/tmp`, 64 MB `$HOME`) were chosen, not measured under production load; the hardening was run on the dev stack's services, not on the droplet. The api's anonymous `/tmp` volume survives a restart (it is recreated with the container, not emptied), so a crash that leaves a spool file leaves it there. Dependabot's docker entry and its cooldown have not run yet. `docker exec ... pip install` no longer works in these images.
