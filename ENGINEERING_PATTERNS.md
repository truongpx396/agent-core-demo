# Engineering patterns: lessons about this repository's settings and tests

Two lessons that billing happened to teach and that are not about the agent: what a settings error must not print, and how a test may re-apply a migration to a shared database. They
were written in `GRAPH_PATTERNS.md` (as patterns 59 and 60) and moved here so that file stays about the graph. They keep their ORIGINAL numbers, so every earlier reference still
resolves; a pattern number is never reused or shifted. The billing-specific parts of each are in [`packages/billing/docs/PATTERNS.md`](packages/billing/docs/PATTERNS.md).

## Patterns

### 59. A settings error must not print the secret it rejected
Pydantic's `ValidationError` prints the raw offending value (`input_value='...'`), a `Settings()` error is raised at import time, and the output goes to a terminal or a container log. Checked, not assumed: with an API key set to a value its validator rejects, the startup error repeated the key whole, and so would a credential pasted into the wrong variable.
- **One line closes it for every field.** `hide_input_in_errors=True` on the settings class: the error still names the field and the rule and no longer repeats the value. A test per path (a rejected credential, a malformed map of secrets) fails without it; each was checked against the mutant that removes it. It is class-wide, so every other settings error also stops quoting its value (the field name and rule remain).
- **Credentials are `SecretStr`, and a blank is "not set".** A variable left in `.env` with no value arrives as an empty string, which would otherwise be a credential that is empty and fail its format check with a confusing message. Only a blank is touched before wrapping; a real value is never inspected in the clear. The one mistake worth catching at startup is pasting the wrong kind of key.
- **A setting that nothing reads is a promise the code does not keep**, so when one was deliberately removed a test pins its absence.
- **A warning that can go stale is pinned.** A comment in `.env.example` that says "do not enable X until Y exists" has a test that fails the day Y exists, as the prompt to rewrite the comment.
- The billing package's own credential settings (the key-prefix checks, the sandbox default, the verification numbers and the disclosed gaps) are in `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md".

### 60. A test that re-applies a migration to a shared database must be the one that gives up
A test that checks "this migration can be applied twice" failed about one parallel run in seven, and in one full integration run the victim was an unrelated test that failed with `DeadlockDetected` instead of its injected error. Tests re-apply migrations to the database the other xdist workers are writing to, and re-running DDL is not harmless there. Measured on a real Postgres rather than assumed: a no-op `ALTER TABLE … ADD COLUMN IF NOT EXISTS` takes an **ACCESS EXCLUSIVE** lock, `CREATE INDEX IF NOT EXISTS` a **SHARE** lock and `CREATE OR REPLACE TRIGGER` a **SHARE ROW EXCLUSIVE** lock, all on tables other tests hold row locks on.
- **Why the wrong test failed.** A concurrent transaction that holds a lock on one table and waits for another forms a cycle with the script, and Postgres aborts whichever session's `deadlock_timeout` (1 s here) runs its check first. That is the session that began waiting first, so it was the unlucky DML test, not the DDL one. Catching and retrying inside the DDL test would not have helped: the victim was somebody else.
- **The fix makes this session always give up first.** `tests/integration/schema_reapply.py::reapply` sets a `lock_timeout` (300 ms) shorter than `deadlock_timeout`, so the script abandons a wait and rolls back before any deadlock check can run; that dissolves the cycle, the other transaction continues, and the idempotent script is tried again with jitter. A `DeadlockDetected` is deliberately not retried: with the timeout in place it cannot happen, and if it does the assumption is wrong and the test should say so. A test asserts the timeout stays below `deadlock_timeout`.
- **The cycle is built on purpose, not hoped for.** A test takes a lock the script needs, waits until the script is actually blocked on it (read from `pg_locks`), then asks for a lock the script already holds. Without the timeout that is a deadlock within a second.
- **A hang is the worst way for a test to fail.** The first mutant run hung (with the timeout removed, the "never released" test waits forever) and the harness timed out, leaking a container. Every re-apply in the tests is now bounded by `asyncio.wait_for`, so a regression is a failure with a name, not a stalled CI job.
- **The same cause wore a second, misleading face.** A later failure was `DID NOT RAISE UniqueViolation`, which looks like a missing unique index. It was not: the code under test never raises (a failure is recorded and returned as a value), the test discarded that outcome, the deadlock had killed the FIRST write, and so the second one "succeeded". The tests that set the stage with a bare call and could fail the same way now go through a helper that asserts the setup did not fail, with a test that it does.
- **Verified:** real-Postgres tests of the helper itself. **Mutation check: 5 mutants, 4 caught** (no `lock_timeout`, a timeout longer than the deadlock check, no retry, giving up silently); the fifth, also retrying `DeadlockDetected`, is **equivalent** once the timeout is in place (nothing can deadlock), and is not counted as a gap. **16 of 16 parallel runs of the affected files were clean**, against about one failure in seven before.
- **Gaps (disclosed):** other tests that run DDL against the shared database are not covered unless they use the helper; `.claude/rules/testing.md` says so. `lock_timeout` bounds this session only: a test that holds a lock for tens of seconds would still make the re-apply fail after its 60 tries.
- The billing-specific parts (the migration whose lock order the cycle test depends on, the webhook test that was the victim) are in `packages/billing/docs/PATTERNS.md`, "Notes on patterns that stay in the agent app's GRAPH_PATTERNS.md". The package keeps its own copy of the helper (`packages/billing/tests/schema_reapply.py`), because it cannot import this repository's.
