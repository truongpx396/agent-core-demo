# Cost governance: what the agent spends, and how it stays within limits

The patterns behind the agent's own usage meter and spend limits: pricing a model call, recording one immutable usage event per call, the dollar caps that sum those events, the holds that keep concurrent turns honest, the gateway backstop, and the history of retiring the old per-turn ledger. They were written in `GRAPH_PATTERNS.md` and moved here so that file stays about the graph. They **keep their original numbers**, so every earlier reference ("pattern 58") resolves; a number is never reused or shifted.

Not here: the billing half of the meter (rating a call in credits, the wallet, the export outbox, reconciliation) is the billing package's, in [`packages/billing/docs/PATTERNS.md`](packages/billing/docs/PATTERNS.md), and what the app hands it is in [`BILLING_INTEGRATION.md`](BILLING_INTEGRATION.md). The per-turn and token ceilings that end a run early are graph patterns (10, 34, 35). Operating it (sweeps, reconciliation) is in [`infra/README.md`](infra/README.md).

| Concern | Patterns |
|---|---|
| What a call costs; one event per call behind one choke point | 26, 51 |
| The limits: budgets, holds, overrides, the gateway backstop | 26, 58, 74 |
| What the gateway sees: prices on local models, the per-person end user and its default cap, the conversation on every call, the pinned image | 74 |
| Retiring the per-turn ledger, and carrying its history | 57, 58, 62, 64 |
| Retention | 63 |

## Patterns

### 26. Usage and cost ledger
(**Superseded by 58 and 62–64: the caps now sum the usage events, nothing writes `usage_ledger`, and the module is gone.**) `record_usage(…)` wrote one tenant+principal row per completed turn into `usage_ledger` (`app/agent/usage_ledger.py`), read back by `usage_summary` and the daily cap. Cost is priced per LLM call by `app/agent/cost/pricing.py` from LiteLLM's `GET /model/info` (input, output and cached-input rates) and accumulated in `State.total_cost_usd`; the ledger row stored that same figure.
- **Bug: cost came from a two-entry code table with one rate per total token (spec 008 A2).** Any other alias cost $0 with no signal, and every dollar ceiling multiplies tokens by a price, so pointing `chat` at a paid model blinded the per-turn, per-subagent and per-tenant ceilings at once. Prices now come from LiteLLM, where the alias is already resolved, so swapping the model behind an alias re-prices it and a self-hosted model is priced by `model_info` in the LiteLLM config.
  - **Unknown is not free.** LiteLLM's known $0 (Ollama) is a price; a missing one is `None`, counted per call (`agent_unpriced_usage_total`, alert `ModelUsageUnpriced`) and refused outright under `UNPRICED_MODEL_POLICY=block`. An alias served by several deployments is priced at the dearest, and as unknown if any is unpriced.
  - A delegated run is priced by its specialist's own alias (`GraphDeps.model_alias`) and **`block` covers it too:** the turn-entry check only sees the parent's `CHAT_MODEL`, so `run_subagent` refuses a specialist whose own `model:` is unpriced before any model work (`agent_subagent_run_total{outcome="model_unpriced"}`). The advisory AI review on #124 caught that the first version let one through.
- **Degrade paths are counted, and two are alerted (spec 008 A1).** A failed ledger write, ledger read, reservation write/release/read or model resolution each increments `agent_cost_governance_degraded_total{path}`. Two hide committed spend, so they page: `LedgerWriteFailing` (the turn succeeded but its row is gone, so every allowance read from that ledger undercounts; retired with the ledger write in 62, whose replacement page is `UsageEventWriteFailing`) and `TenantAllowanceUnenforced` (the allowance read failed open, so those turns ran with no daily cap).
- **The rolling-window read is indexed and the table was trimmed (spec 008 A3).** `17-usage-ledger-indexes.sql` added `(tenant, recorded_at)` and `(tenant, principal, recorded_at)` (600,000 rows: 5,770 buffers / 9.3 ms down to 1,857 / 1.5 ms) and dropped the redundant `(tenant, principal)`. The sweep script (retired in T030c3; its successor for the events is 63) deleted rows past `USAGE_LEDGER_RETENTION_DAYS` in bounded batches (at most 1,000 batches or 5 million rows per run; hitting that is logged and the next run continues) with a 35-day floor enforced again inside `sweep_old_rows`, so a calendar-month window never loses spend still inside it. Nothing scheduled it. Existing volumes needed the index file applied by hand (plain `psql -f`: it uses `CONCURRENTLY`).
- **Resume re-checks the allowance; crash-continue holds a reservation (spec 008 A6).** Only a brand-new turn used to be checked, so a tenant past its ceiling could keep spending by approving paused turns (the approval wait is unbounded). `astream_events_resume` now refuses an over-budget tenant (`tenant_budget_exceeded`; the thread stays paused, and `cancel_run` is never gated because it gives the model no turn) and holds a reservation for its duration. The unattended decline loop passes `admitted=True`: it's a step of a request that already passed, and refusing it would strand the conversation at its pause. `astream_events_continue_turn` is **not** refused (it retries admitted work, and refusing could strand a turn that already ran a mutating tool) but takes a hold, since the crashed worker's was lost. The overshoot that allows is bounded by that one turn's `MAX_COST_USD_PER_TURN`.
- **The allowance's failure mode is a decision, and the rule is its own module.** The check moved from `app/agent/runtime/core.py` to `app/agent/cost/budgets.py` (`check_tenant_daily` returns an `Allowance`, not a bool; `runtime.allowance_refusal` is the one question every entry point asks). When the ledger READ fails, `BUDGET_CHECK_FAILURE_POLICY=open` (default) serves the turn, counted and alerted, with `Allowance.degraded=True`; `closed` refuses it as `budget_check_unavailable`, which blames no budget and so doesn't trip the budget alerts. The in-flight hold read stays open either way, since it only closes a race and the ledger check beneath it is still enforced. A refusal is logged with its tenant and principal (the counter deliberately has no label for them).
- **Four limits, two scopes, two windows (`app/agent/cost/budgets.py`).** A limit is `(scope, window, dollars)`: scope `tenant` or `principal`, window `day` (rolling 24 h) or `month` (the CALENDAR month in UTC, resetting on the 1st like an invoice). Only tenant/day is always on; `MAX_COST_USD_PER_TENANT_PER_MONTH` and `MAX_COST_USD_PER_PRINCIPAL_PER_DAY`/`_PER_MONTH` are off at 0, so an unconfigured deployment pays for exactly one ledger read.
  - The first exceeded limit refuses (tenant before person, since an organisation-wide stop matters more) and only it is counted: `agent_budget_exceeded_total{scope,window}`. A person who hit their own limit gets `personal_budget_exceeded`; everyone else keeps `tenant_budget_exceeded`.
  - Turns still allowed but past 70/85/95% of a limit are counted under `agent_budget_threshold_total` (highest crossed only) and logged once per day/month with tenant and person; only tenant-scope 95% pages (`TenantBudgetNearLimit`), because a person reaching their own cap is the guard rail working. These replace the unlabelled `agent_tenant_budget_*` pair, and `TenantDailyCostBudgetExceeded` became `TenantBudgetExceeded`.
- **Operators can override a limit per tenant or per person (`budget_policies`).** The four limits are Settings defaults for everyone. `postgres-init/18-budget-policies.sql` holds overrides keyed `(tenant, subject, period)` where `subject` is `''` (the tenant's own), `'*'` (every person in the tenant: a plan tier) or one principal, and `budgets.resolve_limits` applies person > `*` > default. The value has two opposite special meanings, kept distinct by the column and a real-Postgres test: **NULL = explicitly no cap** and **0 = refuse everything** (the suspend switch).
  - Edited only through `scripts/budget_policy.py` (`make budget-policy`, audited with `--by`), read before every turn through a per-process cache (`BUDGET_POLICY_REFRESH_SECONDS`, 30), so **a change, including a suspend, reaches a running worker within that long, not instantly**.
  - A failed override read follows the same fail policy as a ledger read (counted as `policy_read` under `TenantAllowanceUnenforced`); a MISSING table (migration not applied) reads as no overrides with one warning, because refusing every turn over an unapplied migration would be worse.
  - `GET /usage` also returns `budgets`: every limit that applies to the caller, with spent, remaining and `resets_at`.
- **The gateway is the backstop, and the app tells it who is calling (`app/core/gateway.py`).** The app-level limits can all be wrong at once (a bug in the allowance, a loop; NOT an unpriced model: LiteLLM prices from the same list, so it can't see that spend either, 74), so LiteLLM holds a scoped key with its own `max_budget`, minted by `scripts/litellm_key.py`. The master key can't carry a budget, so an app sending it had no gateway-side cap and handed over gateway admin with one compromised container. Compose sends `LITELLM_APP_KEY` (falling back to the master key so an existing deployment keeps running), and a real run confirmed the scoped key can still read `/model/info`, which `pricing.py` and `model_resolver.py` need (had LiteLLM refused it, every model would read as unpriced and `UNPRICED_MODEL_POLICY=block` would be an outage).
  - Every LLM call (agent, follow-ups, compaction, the two cron scripts) carries `user` and `metadata.tags` = `tenant:<name>`; **verified against a real LiteLLM**, they land as `end_user` and `request_tags` in its spend log, and neither reached the model backend.
  - LiteLLM's stop is recognised by its error `type` (`budget_exceeded`), not its status (400 on older code, **429 on `main-stable`**; my first version assumed 400 from reading source). It becomes `provider_budget_exceeded` plus `agent_gateway_budget_exceeded_total` and the critical `GatewayBudgetExceeded` alert, also when follow-ups or compaction swallow it.
  - **Bug found by that run:** LangGraph's default `retry_on` retries any non-programming error, so the agent node retried the refusal three times (nine gateway requests with the SDK's own retries); `AGENT_RETRY_POLICY` now refuses to retry it.
  - **Gap (partly closed by 74):** a key budget is one global number, not per tenant, and covers embeddings too. 74 added a per-person default budget for chat calls, so there is no tenant-wide cap at the gateway, and embeddings still have none.
- **Closed for chat-model calls (spec 010 PR 1b), open for embeddings.** The ledger used to see only the agent node's calls, so follow-ups and history compaction spent tokens no dollar cap counted. Every chat call now goes through `metering.metered_invoke` (51), so the caps and `GET /usage` include them. **Still open:** embeddings (`OpenAIEmbeddings` returns vectors only) are neither metered nor attributed at the gateway (PR 1c).
- **Bug: unfinished turns weren't recorded.** Only the success branch recorded usage, yet completed steps sit in the checkpoint and timed-out turns spend the most. `_record_unfinished_turn` now reads the last checkpoint on the timeout, error and cancel paths.
- **The daily cap counts in-flight turns.** `reserve_budget` records a hold of `MAX_COST_USD_PER_TURN` per running turn (`tenant_budget_holds`), released by id at the end; holds older than `RESERVATION_STALE_AFTER_MINUTES` stop counting. Without holds, N concurrent turns all read the same "spent so far".
- **Bug: the first design was one running total per tenant.** A killed worker's amount was never released, and every reserve refreshed the same timestamp, so a leaked amount never aged out (still counted 40 minutes later), refusing real turns over spend that never happened. One timestamp can't mean both "last touched" and "how old is what this holds". Fake-cursor tests can't show this; `test_budget_holds_real_postgres.py` ages real rows.
- **Gaps:**
  - In-flight holds are per tenant, so a person's limit doesn't see their own concurrent turns and can be overshot by up to (concurrent turns) x `MAX_COST_USD_PER_TURN`; tenant limits stay exact.
  - A monthly window reads a month of the tenant's rows before every turn, and only when a monthly limit is on: 2.4 ms for a 10,000-row day, **16.6 ms for a 300,000-row month**, 0.3 ms for one person's month (real Postgres, shipped indexes, warm). Fine against a multi-second turn but linear in volume; past a few million turns a month it wants a daily rollup table.
  - Tokens from a call cut off mid-flight, and turns paused and never resumed, aren't counted. A LiteLLM fallback (`chat` to `chat-backup`) can serve a call at another deployment's price without saying so, and cache-WRITE tokens are billed at the input rate because `langchain-openai` drops that field. The cap fails open (a failed reserve means unprotected, not blocked). Existing volumes need `16-tenant-budget-holds.sql` applied by hand.

### 51. Per-call usage events behind one metering choke point
`usage_ledger` is one row per completed turn with no key that names a call: enough for a spend cap, not for billing (a replayed write is unrecognisable, and a provider that deduplicates usage by a caller-supplied id, Stripe `identifier` or Polar `external_id`, has nothing to be handed). `usage_events` (`postgres-init/19-usage-events.sql`) is one append-only row per model call, and `metering.metered_invoke` is the one place a chat-model call is made, priced and recorded. Design: `specs/010-credit-billing-readiness/`.
- **Identity is verified, not assumed.** `event_id = uuid5(tenant | AIMessage.id)`. Read from the installed langchain-core and confirmed with a real `ChatOpenAI` through a checkpointed graph: the id is assigned by langchain as `run-<run id>-<index>`, is unique per invocation even when the provider repeats its own id, and is identical after a checkpoint round trip. The provider's `chatcmpl-…` id is deliberately not used (a backend may return a fixed or missing one). `tests/agent/cost/test_usage_events.py` pins it, so a library upgrade that changes id assignment fails loudly instead of silently merging or double-counting calls.
- **The duplicate story is the primary key,** `INSERT … ON CONFLICT DO NOTHING`, proven on a real Postgres (20 concurrent writers of one event produce one row). The table is append-only by trigger (UPDATE always refused; DELETE only when the retention job says so inside its own transaction, and `SET LOCAL` means it can't be left on). `cost_usd` is **NULL when the model has no price**, never 0, because a 0 would be billed as free; money is `NUMERIC(18,12)`, because six places would store a $0.0000004 call (a cheap model, an embedding) as exactly zero, a systematic loss a billing meter can't afford.
- **A choke point, because a call site that must remember to meter will one day forget.** The agent node, subagents and every later call site go through it; `tests/agent/cost/test_metering_choke_point.py` reads the AST and fails on any new unmetered `llm.ainvoke` and on a stale exemption. The exemption list, once four sites, is now empty and stays as a place to record a deliberate exception.
- **Fails open, counted, alerted.** A failed write never fails a turn, but a lost event is lost revenue and a log line tells nobody, so `usage_event_write` pages (`UsageEventWriteFailing`) and an unapplied migration is its own counted path (`UsageEventTableMissing`). There is **no kill switch** (58: the caps sum these rows, so `USAGE_EVENTS_ENABLED=false` is refused at startup). The write costs p50 0.56 ms / p95 0.79 ms on a pooled local Postgres, against multi-second model calls.
- **Every chat call is routed (PR 1b) and counted exactly once.** Follow-ups, compaction and the two cron scripts go through the choke point, and a call's cost reaches the caps once: `tests/agent/cost/test_metering_every_call_site.py` asserts that across an answer, a compaction and follow-ups the events' cost equals the turn's running total plus the others' own cost, with no gap and no overlap. **Compaction deliberately does not add to the turn's token or cost budget:** it can summarise tens of thousands of tokens, and charging that to the turn could stop the very answer the turn exists to give.
- **Bug this prevented:** the first test pass took 46 s against ~15 s before. The new write was reaching a real Postgres and a real model resolver on every test turn, the exact leak the autouse mocks exist to close; `usage_event_sink` now closes it and captures each row for assertions.
- **An escalated turn is priced as the alias that served it (specs/014, GRAPH_PATTERNS.md 68).** `agent()` passes the routed alias as both the per-call `model=` and `model_alias`, so the call, the per-turn dollar ceiling and the usage event all name the same model. If that call never reaches a model (a connection failure, timeout or gateway 5xx), the same call is repeated on the local alias and recorded as local: a failed call writes no event, so the ledger never shows a price for a model that didn't answer. That's why the degrade-to-local is in the app and not in a LiteLLM `fallbacks` entry, which would record the strong alias for a local answer. An unpriced strong alias keeps the route local (counted `strong_unpriced`) whatever `UNPRICED_MODEL_POLICY` says, so the router can never be why a turn is refused. The gateway's own budget stop is deliberately not caught by the fallback.
- **Gaps:** a model call whose response arrives and whose process dies before the event commits isn't recorded (the planned reconciliation against the gateway log is the detector). Embeddings aren't routed yet (PR 1c: they need the tenant plumbed through nine call sites that take no `ctx`).

### 57. Carrying the ledger's history into the events, and a first version that could never finish
The dollar caps summed `usage_ledger` and were about to sum `usage_events` (specs/010 T030b). The events only begin when `postgres-init/19` is applied, so switching the read alone would make a monthly cap forget the month so far and `GET /usage`'s all-time total come back short. This is the additive half, merged first: it changes no behaviour, so it can be run and checked before the release that depends on it.
- **What it copies, and what it mustn't.** `make usage-events-carry-over` (`scripts/usage_events_carry_over.py`) copies each ledger row older than the **first real event** as one `ledger:<id>` row (`kind='chat'`, the ledger's own time as `occurred_at`, no input/output split because the ledger never kept one). Nothing newer: since the events existed every turn has been written to both tables, so copying those would count them twice and double a tenant's spend the day it is switched on. The cutoff is the first row whose id doesn't start with `ledger:`, so a carried row never moves it (a naive `MIN` would slide back to the oldest history and stop the second run carrying the rest; a test pins it).
- **History is not a call.** A carried row is never rated, charged or queued for export: the statement is plain SQL outside those paths. A real-Postgres test pins that the row has no credits and the tenant has neither a wallet transaction nor an outbox row afterwards.
- **The first version could never finish a large ledger.** Each run scanned from ledger id 0, so a ledger bigger than one run's ceiling (1,000 batches of 5,000) re-read the same carried rows and never advanced, while the docstring promised a re-run continues where the last stopped. Found while writing the test: the statement now selects only rows not yet carried, and a test running three ceiling-limited runs expecting 2, 2, 1 fails on the old query. `ON CONFLICT DO NOTHING` stays for two runs racing, and a test runs two against 3,000 rows and checks nothing counted twice.
- **`--tenant` exists for two reasons:** the cutoff is one instant for the whole table and the integration container is shared by every xdist worker, so an unfiltered carry-over would copy other tests' ledger rows; and an operator wants to check one tenant before the full run. The empty-table branch (no real event yet, so the cutoff is now) is tested by deleting every real event inside a rolled-back transaction.
- **A test that writes history can break an unrelated test that deletes it.** The ledger sweep test deletes old rows across tenants in batches of 2 up to a ceiling of 2,000; the race test writes 3,000 three-year-old rows, so the sweep never reached its own rows (it had passed in a full run by ordering luck). The carry-over tests now remove their ledger rows afterwards and run in the sweep tests' xdist group.
- **Verified:** 10 hermetic and 11 real-Postgres tests; **7 mutants, all caught** (the cutoff counting carried rows, no cutoff bound, the copy stamped with the copy time, carried rows re-read, the tenant filter ignored, `ON CONFLICT` dropped, history rated).
- **Gaps:** nothing alerts that the carry-over was skipped (`ARGS=--dry-run` printing `Would carry 0` is the check). A turn that straddles the cutoff is counted by its events only. A ledger row from a stretch when events weren't being written *after* the first one existed sits past the cutoff and isn't carried (`make credit-reconcile` names such a tenant-day). It probes `usage_events` by primary key once per row: fine for a one-time job, not for every minute.

### 58. The dollar caps sum the per-call events, and the history is carried across instead of forgotten
The caps and `GET /usage` summed `usage_ledger` (a row per turn, written when it ended) while billing, the wallet and the export were built on `usage_events` (a row per call): two records of one spend, kept in step by a test. `app/agent/cost/spend.py::usage_summary` now sums the events, so what is capped, charged, exported and reconciled is one set of rows. The history comes across first, by 57.
- **Three gaps close by construction.** A turn is counted as it spends, not when it ends (a timed-out, cancelled or paused turn used to spend money no cap could see). Every kind of call is counted (follow-ups, compaction, subagents, cron scripts) because the choke point writes the event. And the cap and the bill can't disagree, since they sum the same rows.
- **The kill switch had to go.** `USAGE_EVENTS_ENABLED=false` was an emergency switch for a hurting write path; with the caps reading the same rows it would make every cap read $0 and stop enforcing without a sound. It is refused at startup. The setting is kept (not deleted) because Settings ignores unknown variables, so an operator's old `=false` would otherwise be dropped silently while they believed writes were off.
- **Deliberate differences from the ledger sum.** An unpriced call adds its tokens and $0 (cost NULL; `SUM` skips it; `UNPRICED_MODEL_POLICY=block` refuses a model with no price). The window is `occurred_at`, the time of the call, not the end of the turn. A running turn is counted twice in the safe direction: its finished calls are events while its hold (`MAX_COST_USD_PER_TURN`) still stands, so a sibling's check can refuse a little early and never let a burst through.
- **The history meets the read in a test:** `test_the_history_a_carry_over_copied_is_what_the_cap_then_reads` shows the read missing 40 dollars of history before the copy, seeing it after, and a recent window still seeing only the recent event.
- **Measured, and an index was decided against.** One tenant with 2,000,000 events in 30 days (2.6M rows): tenant rolling 24 h (the always-on cap) 9.3 ms; one person, 24 h, 5.8 ms; one person, month, 98 ms; **tenant, month, 426 ms (a sequential scan)**. A `(tenant, principal, occurred_at)` index took person-day to 0.46 ms and person-month to 79 ms but would cost 118 MB (32% of the table) and a write per model call to save ~5 ms on an opt-in cap; the existing `(tenant, occurred_at)` already gives a good plan, and a covering index for the monthly sum (194 ms) wasn't adopted either.
- **A scratch script shares the test harness's container.** `tests/containers.py::ensure_postgres()` caches its container, so a measurement script left 2.6M rows and its own index there and the next pytest run failed an index-planner test on an index that was never part of the schema. Measure on a container of your own.
- **Verified:** 18 hermetic and 11 real-Postgres tests (including a cap that trips on events with no ledger row anywhere, and a ledger row alone no longer counted); **9 mutants caught**. One survived first and was a real gap: nothing asserted that the suite's autouse guard covers the new module (`test_the_suites_own_guard_covers_this_read` now does).
- **Gaps:** the **monthly caps are linear in a month's model calls** (426 ms at 2M events; off by default; the lever is a per-day rollup written in the event's transaction, not built). **Nothing alerts that the carry-over was skipped,** so a monthly cap under-counts the month so far until it runs. A deployment that never applied `19-usage-events.sql` now has caps that fail open (`TenantAllowanceUnenforced` pages) where they used to work off the ledger alone.

### 62. The per-turn ledger stops being written: one record of spend, and what that costs
The caps sum the usage events (58) and the reconciliation no longer compares the ledger, so the per-turn `usage_ledger` row had no reader left. This change stops writing it (specs/010 T030c2): the turn-end row in `_record_turn_metrics`, the subagent run's own row, `metered_invoke(to_ledger=...)`, the follow-up/compaction/cron call sites that passed it, `record_usage` itself, the `LedgerWriteFailing` alert and the `ledger_write` metric path. One record of spend remains, written where the call is made.
- **What it closes.** 26 disclosed that a turn which timed out, errored, was cancelled or sat paused never reached its end-of-turn ledger write (spec 008 B17 patched only part of it). That was a MONEY problem because the row was written at the end. It's gone by construction: each call's event is written the moment the call returns, so nothing that happens to the turn afterwards can lose it.
- **A correction to my own plan.** `tasks.md` said the unfinished-turn checkpoint re-read "existed only to feed" the ledger. It also feeds `agent_tokens_total`, so it stays, bounded to 2 s and unable to change the terminal event. What went is its `ctx` and `thread_id` plumbing.
- **The ledger's tests' properties moved, not vanished.** `test_record_usage.py` was deleted whole. The concrete model behind an alias (38) wasn't covered by any event test, so two were added; a negative cost can't reach an event (`pricing` accepts only finite non-negative rates and the column has a `CHECK`); the call-site invariant became "one event per call, the agent node's inside the turn's running total, the others' outside it". The now-dead autouse fixture `mock_model_resolver` was deleted, not retargeted (`usage_event_sink` already patches the only remaining caller).
- **What it costs, plainly.** There is no way back: a release that reads the ledger would see spend only up to the day this deployed, and the runbook's old "to go back, revert the release" is replaced. A failing event write is now the only thing that makes a cap under-count, so `UsageEventWriteFailing` is its page. And there is no second local record: a lost event is found only by the gateway comparison.
- **Verified:** the hermetic suite (2543) and the real-Postgres tier pass; **7 mutants, all caught** (unfinished turns no longer counting tokens, a failure while counting reaching the turn, the checkpoint read unbounded, the resolved model not recorded, a delegated run recorded as `chat`, follow-ups or compaction under the wrong kind).
- **Gaps:** the frozen table still existed with its retention sweep, and the budget holds still lived in `usage_ledger.py`; both went in 63 and 64. `postgres-init/12-tenant-budget-reservations.sql` still has a historical comment naming `record_usage`.

### 63. The usage events get the retention sweep that spec D7 promised, and it refuses to hide unfinished exports
`usage_events` is append-only and, since the caps sum it (58), grows with every model call; the ledger had a sweep, the events had none. `make usage-events-sweep` (`app/agent/cost/usage_events_retention.py`, `scripts/usage_events_sweep.py`; specs/010 T030c3) deletes events older than `USAGE_EVENT_RETENTION_DAYS` (400 by default).
- **A floor, enforced twice.** A monthly cap reads back 31 days, the reconciliation up to 35, the export outbox gives up on an unsent event at 30, so the setting refuses to load below 35 and `sweep_old_events` raises below it BEFORE touching a row (the floor holds for any caller, not only the script).
- **It will not delete evidence of unfinished work.** *(Since spec 013 the export outbox and this guard belong to the billing package's own sweep, `credit-billing-usage-sweep`, over its own `billing_usage_events`: `packages/billing/docs/PATTERNS.md` B3. The agent's sweep has no outbox to protect; this records why the guard exists.)* An event whose export is `pending`, `failed` or `expired` is usage meant to reach a provider and didn't: lost revenue with an alert on it. Deleting it because it's old would turn something nobody has resolved into something nobody can see, so it is kept and counted (`held_back`, printed with a pointer to the runbook). Only a `sent` export is finished: that event goes together with its outbox row in ONE statement, because the foreign key `usage_export_outbox.event_id -> usage_events` is checked at the end of it.
- **The delete is permitted per transaction, not per session.** The table refuses DELETE unless `usage_events.allow_delete` is on; the sweep sets it with `set_config(..., true)`, LOCAL to the transaction, so it can't be left switched on (a test pins that a bare DELETE is still refused afterwards).
- **It doesn't touch the wallet.** A debit keeps its `usage_event_id` as lineage (no foreign key) and the balance doesn't move. What's lost is the ability to recompute that debit's credits from the event row, so keep events at least as long as you may need to explain a charge.
- **Verified:** 20 hermetic and 10 real-Postgres tests; **7 mutants, all caught** (unfinished exports unprotected, only `pending` protected, the finished row not cleared, the delete never allowed, the cutoff inverted, no floor, held-back not counted).
- **Gaps:** nothing schedules it (on purpose: this is the table spend is read from). A `failed` or `expired` export keeps its event forever until a person resolves it, and there's no "resolved" state to mark that. The all-time `/usage` total is bounded by the retention window. The per-batch scan has no index on `occurred_at` alone (the oldest rows are first in the heap; checked by reasoning, not measured at scale).

### 64. The budget holds move out of the retired ledger module, and the module goes with its sweep and its setting
The last live thing in `app/agent/usage_ledger.py` wasn't about the ledger: the in-flight budget holds (`reserve_budget`, `release_budget_reservation`, `in_flight_reservation`) that keep N concurrent turns from passing the same stale cap check. They're now `app/agent/cost/budget_holds.py`, moved verbatim apart from docstrings, and the module, its sweep script (`scripts/usage_ledger_sweep.py`), `make usage-ledger-sweep` and `USAGE_LEDGER_RETENTION_DAYS` are deleted (specs/010 T030c3b). The `usage_ledger` TABLE stays, frozen and read-only: it's the source the carry-over copies from, and dropping it is a later, separate, destructive decision.
- **A rename, checked as one:** every caller and test that patches a hold function moved, and the full suite and real-Postgres tier ran before and after; no statement changed. `test_the_ledger_module_is_gone_so_a_stale_caller_fails_loudly` asserts importing the old module raises `ModuleNotFoundError`.
- **A test group whose reason changed under it.** The shared xdist group of the carry-over, spend and retention tests existed because the LEDGER sweep deleted old rows across tenants. The events' sweep does the same across `usage_events` and would delete the carry-over tests' three-year-old rows mid-test, so the group stays, renamed `usage_events_old_rows` with its rationale rewritten.
- **Two collisions only a shared database shows.** (1) The retention tests leave events with unfinished export rows (that's what they prove are kept) and a carry-over test deletes every real event inside a rolled-back transaction to ask the cutoff of an empty table; the outbox foreign key then refused the delete, so it clears the outbox first, inside the same transaction (the export worker can't touch the leftovers: it claims only providers it's configured for, checked in `export.py`). (2) The carry-over race test leaves 3,000 years-old events, and the retention test (batches of 2, ceiling 1,000 batches) hit that ceiling at 2,000 deleted rows before reaching its own (`deleted=2000, complete=False`, reproduced by running the files in that order). Two fixes, doing different jobs: that test passes an explicit generous `max_batches` (independent of any residue), and the three fixtures `purge_events` what they wrote.
- **Verified:** the hermetic suite (2548) and the full real-Postgres tier. The move is mechanical, so no new mutant is claimed.
- **Gaps:** the `usage_ledger` table and its indexes (`postgres-init/03`, `17`) remain on every volume; `12-tenant-budget-reservations.sql` still has a historical comment naming `record_usage`.

### 74. What the gateway sees of spend: priced local models, a readable per-person end user with a default cap, the conversation on every call, and a pinned image
Four changes to the same seam, found by asking what LiteLLM's own limits could and couldn't do for a deployment on local models, shipped together: a gateway cap is only as good as the price and the identity behind it.
- **A local model is priced, or no gateway budget can trip on it.** On the 1.94.1 image, `GET /model/info` reported `chat`, `chat-backup` and `embed` at a known 0 and `vision` as `null`. A `null` is "unpriced" to the app (counted; refused under `block`); a 0 is a price, but LiteLLM's budget docs say a model whose two prices are both 0 skips budget checks, so neither the key's `max_budget` nor a tenant budget could ever accumulate local spend. Every alias in `litellm-config.yaml` now states a shadow price in `model_info`: $0.10 / $0.20 per million input / output tokens for the 7B aliases, $0.20 / $0.40 for the 14B, $0.05 / $0.10 for the 3B vision slot, $0.01 for embedding input (the order of magnitude hosted providers charge for open-weights models of that size, not a bill). A test keeps them real numbers (PyYAML reads `1e-7` as a string, so they're decimals).
  - **Run, not read:** on a scratch Router a price in `model_info` or in `litellm_params` gave 10 x 1e-7 + 20 x 2e-7 = 5e-6; an unpriced model gave nothing; a deployment with no price of its own *inherits* the price registered for the same underlying model by another deployment, which is why each alias states its own and a test requires one price per underlying model.
  - **Expect:** billing rates a call as `cost_usd x CREDITS_PER_USD x markup`, so local usage now debits a few millionths of a credit where it debited none; a turn that fills the 32,000-token context costs well under a cent.
- **Three chat tiers, two waiting for a hosted model.** `chat` (easy, qwen2.5:7b), `chat-medium`, and `chat-strong` (specs/014, qwen2.5:14b in dev). `chat-medium` follows `chat-strong`'s rules exactly (`tests/core/test_model_tiers_config.py`): always present, a keyless local stand-in in dev (the same 7B as `chat`), three `LLM_MEDIUM_*` variables defaulting to the `chat` values in production, and no gateway fallback naming it (a fallback would answer with one model and price the call as another). Nothing in the app selects it yet except a specialist's `model:`. The dev stand-ins stay local so `make test-live` exercises the router against `chat-strong`'s. Attaching Gemini is one entry (dev) or three variables (prod), with its key in `GEMINI_API_KEY_MEDIUM` / `_STRONG` (the dev compose already passes both, empty).
  - **Not verified, no key yet:** Google documents tool calling and streaming on its OpenAI-compatibility endpoint (still beta) but not `stream_options.include_usage`, which the app needs to meter a streamed call; and LiteLLM doesn't know an `openai/<gemini id>`, so its price must be stated. Run `make probe-tools ARGS="--alias chat-medium"` plus one streamed turn when the key exists.
  - **A trap closed:** `litellm_key.py create` listed only `chat,embed`, so a minted key refused `chat-strong` and would refuse every new tier; the default now follows the prod config's aliases (a test). A key minted earlier must be re-minted or widened with `/key/update`.
- **The end user is the person, readable, and the default gateway budget caps each person (for chat).** The app sends `user` = `tenant:<tenant>/user:<principal>`, each part percent-encoded (tenants and principals are client-supplied strings: an `x-principal-id` header, `telegram:123`, an email, so a `:` or `/` becomes `%3A` / `%2F`; `gateway.parse_end_user_id` reads it back strictly, so another application's end user on a shared gateway isn't mistaken for one of ours). LiteLLM keeps it as the call's end user: its **Customer Usage** view filters by it and per-end-user budgets key on it. **This corrects PR #183**, which shipped the end user as a hash of the tenant; the user who wanted usage filterable by person pointed out it listed tenants only and asked why it was a hash at all.
  - `litellm_settings.max_end_user_budget_id: person-default` in both configs names a budget that applies to every end user without one of its own, including ones LiteLLM hasn't seen. `litellm_key.py person-budget set --max-budget <usd> [--budget-duration 30d]` creates or updates it and `info` reads it back (exit 1 when missing). The CLI and id were `tenant-budget` / `tenant-default` for the day #183 merged, so a budget created under the old name is no longer referenced.
  - **What that costs:** the cap is per PERSON, so a tenant with many people can spend many times it, and **there is no tenant-wide cap at the gateway** (it would need the tenant to be the end user, or a key per tenant); the app's own tenant limits are exact and stay.
  - **Why it was a hash, and why it can be readable now.** `user` is a standard OpenAI parameter, a person's name has no business reaching a model provider, and whether a gateway forwards `user` depends on provider and version, so the first version hashed it. That assumption is now checked: `make gateway-check` (`scripts/gateway_check.py`) runs the PINNED image on the shipped dev config with a stub backend and a readable id carrying an email-shaped principal: nothing identifying (the end user, tenant, principal, conversation or metadata) reached the backend on the Ollama route or an OpenAI-compatible one, and every alias was priced and billed at tokens x price. The image is pinned by digest for this reason and a bump re-runs the check (`infra/README.md`). The gateway's own database and Langfuse already held the readable tenant and principal in `metadata`.
  - **The reconciliation** reads the tenant off the end user and sums a tenant's people into its day, so a tenant the gateway spent for and the database has no events for needs no special case (`compare` reports a day present on one side only). Spend-log rows under the older one-way `tenant_<hash>` id are still attributed by hashing the known tenants (`gateway.legacy_end_user_id`); that branch can go once the gateway holds no such rows.
  - **Run against a live 1.94.1 proxy with its database:** the budget commands (`info` on a missing budget exits 1, `set` creates, a second `set` updates, `info` reads it back; deleted afterwards), and one chat call with the readable id: LiteLLM stored it verbatim as `end_user`, created a customer row and tagged the call `tenant:acme-check` (the test customer was deleted; its one spend-log row remains). **Read from the installed LiteLLM, not run:** the enforcement itself. `get_default_end_user_budget` applies the default, `_check_end_user_budget` refuses when `spend > max_budget` (so the call that crosses the line still goes through), and the refusal is `BudgetExceededError`, answered as `type: budget_exceeded`, which `gateway.is_budget_exceeded` already recognises.
  - **It fails open:** the config only names the budget, and a name with no object behind it makes LiteLLM log "Default end user budget not found in database" and apply nothing, hence `info` and the runbook step. Size it above the largest person's legitimate spend for the same window; it's a backstop above the app's limits, not a copy (a different number for one person is a `/customer/new`, a second place beside `budget_policies`).
- **The conversation is on every call.** `litellm_session_id` and `metadata.session_id` carry the `thread_id`, which the app's own Langfuse trace already uses as its session, so the proxy's per-call traces and the app's turn land in one Langfuse session (before, nothing joined them). The cron scripts already pass a synthetic thread id (`ops-digest:<date>`, `followup-sweep:<item id>`), so each digest day and follow-up draft became a session of its own too; their identity tests changed to expect it (they had pinned "no session", true only because nothing sent one). **Run against the pinned image with a stub backend** (`make gateway-check` repeats it): neither field, nor the metadata, tenant, principal or `user`, reached the model backend. **Observed on a live 1.94.1 proxy:** LiteLLM's Session ID (`session_id` in `/spend/logs/v2`) holds the thread id. That the Langfuse trace is then filed under the same session was read from source (the Langfuse logger pops `metadata.session_id`), not seen in the UI.
- **The gateway image is pinned by digest** in both compose files (the same one, a test): the multi-architecture index of `main-stable` as of 2026-07-30 (LiteLLM 1.94.1, via `docker manifest inspect`: linux/amd64 and linux/arm64), the image every check above ran on. The tag moved under this app once (the budget stop went 400 → 429) and a LiteLLM release on PyPI was compromised in March 2026; the tag stays beside the digest for the reader. A bump is deliberate: `infra/README.md`, "Bumping the LiteLLM image".
- **The containerized app couldn't carry the scoped key (found after #186).** The dev compose `x-app-env` block had no `OPENAI_API_KEY`, and a container doesn't read `.env` (compose uses it only to fill `${...}`), so every containerized role (`api`, the four agent workers, `ingest-worker`) sent the built-in default `sk-anything`, the dev MASTER key: a scoped key put in `.env` was never used by them, its budget never moved and the spend log named `default_user_id`. Found when a freshly minted key showed spend 0, and confirmed by reading the key out of a running container (masked). The block now carries `OPENAI_API_KEY: ${LITELLM_APP_KEY:-sk-anything}`, the prod compose's pattern; **run with a real `docker compose config`:** set, all six roles get it; unset or empty, they get `sk-anything`; the `litellm` service is unchanged. Host processes (`make serve`, `make agent-worker`) still read `OPENAI_API_KEY` from `.env`.
  - **Gap:** the one key has two names, `OPENAI_API_KEY` for a host process and `LITELLM_APP_KEY` for a container; setting `LITELLM_APP_KEY` in `.env` does nothing for a host process, the trap this was found in. Unifying them means teaching `Settings` a second name for the field; not done.
  - Seen on the same stack, unrelated to the key: containers created before #181 report their workers `unhealthy` (the probe asks a worker for `localhost:8000/health/ready`, a port a worker doesn't serve). The current compose carries #181's `worker-healthcheck`, so `make up-app` should clear it; not run.
- **A gateway-side router alias is unpriced, not free.** LiteLLM's own routers (`auto_router/complexity_router`, `adaptive_router`, `quality_router`, the semantic router) choose a model per call. A scratch 1.94.1 gateway reported such an alias in `/model/info` at input and output 0, and `pricing._rate` accepts 0 as an honest price (what separates Ollama from an unpriced model), so every call would have been metered at $0 while the gateway's spend log, priced per real model, was right: the app's ledger and the gateway's would disagree by the whole bill with no counter, alert or `block` refusal. `pricing._is_gateway_router` (the `auto_router/` model prefix, read from the image's `router.py`, or a `complexity_router_config`) makes such an alias unknown, so it's counted on every call (`ModelUsageUnpriced`) and refused under `block`. The app routes in `route_model` instead (GRAPH_PATTERNS.md 68), where the alias that served is known and priced as itself. A free local model is still free (a test pins it).
  - **Gaps:** a router kind under a name that doesn't start with `auto_router/` would read as 0 again, and the exact cost of a routed call is in the `x-litellm-response-cost` response header, which `ChatOpenAI` doesn't surface, so this makes the spend visible as unpriced and doesn't make it exact.
- **Decided against:** an alert on LiteLLM's `litellm_zero_cost_requests_total`. Production Prometheus doesn't scrape LiteLLM (`prometheus.prod.yml`), so the rule would be dead exactly where it matters, and the app's own `ModelUsageUnpriced` counts the same calls; `UNPRICED_MODEL_POLICY=block` is already set in `deploy/env/prod.env.example`.
- **Verified:** hermetic tests across the end-user id and its parsing, the reconciliation's attribution, the cron scripts' identity, the CLI, the configs and `gateway_check`'s parts (2,312 across `tests/agent`, `tests/core`, `tests/scripts`); mutation checks of 27 mutants for #183 and 23 for the per-person change, all caught; `make gateway-check`; and the live-proxy run above. **Not run:** budget enforcement against a live gateway with its database, and the CI tiers (integration, live, deepeval), left to CI; the reconciliation integration tests (`test_usage_reconcile_real_postgres.py`) were updated for the new ids.
- **Gaps:** embeddings carry no end user, so no per-person gateway cap covers them (PR 1c), and no gateway cap is per tenant; an unpriced model is invisible to every gateway budget; the cap is a backstop, not exact, and its window is LiteLLM's own (a `30d` budget reset at the next month boundary, 2026-11-01, and a `7d` one at the next seven-day boundary; measured on 1.94.1), not the app's rolling day or calendar month. A readable end user is only as private as LiteLLM's not forwarding it, which `make gateway-check` verifies for the pinned image and nothing verifies for a future one. The reconciliation keeps a branch for the older hashed ids with no removal date; the Gemini attachment is untested until a key exists; the digest has no automated bump (Dependabot here is `github-actions` only, on purpose); a key minted before #183 still lists `chat,embed`; one customer row per person accumulates in LiteLLM's database.
