# Cost governance: what the agent spends, and how it stays within limits

The patterns behind the agent's own usage meter and spend limits: pricing a model call, recording one immutable usage event per call, the dollar caps that sum those events, the
holds that keep concurrent turns honest, the gateway backstop, and the history of retiring the old per-turn ledger. They were written in `GRAPH_PATTERNS.md` and moved here so that
file stays about the graph. They keep their ORIGINAL numbers, so every earlier reference ("pattern 58") still resolves; a pattern number is never reused or shifted.

Not here: the billing half of the meter (rating a call in credits, the wallet, the export outbox, the wallet reconciliation) is the billing package's, in
[`packages/billing/docs/PATTERNS.md`](packages/billing/docs/PATTERNS.md); what the app hands it is in [`BILLING_INTEGRATION.md`](BILLING_INTEGRATION.md). The per-turn and token ceilings
that end a run early are graph patterns (10, 34, 35) and stay in `GRAPH_PATTERNS.md`. Operating it (the sweeps, the reconciliation) is in [`infra/README.md`](infra/README.md).

| Concern | Patterns |
|---|---|
| What a call costs; one event per call behind one choke point | 26, 51 |
| The limits: budgets, holds, overrides, the gateway backstop | 26, 58, 74 |
| What the gateway sees: prices on local models, the readable per-person end user and its default cap, the conversation on every call, the pinned image | 74 |
| Retiring the per-turn ledger, and carrying its history | 57, 58, 62, 64 |
| Retention | 63 |

## Patterns

### 26. Usage and cost ledger
(**Superseded, patterns 58 and 62-64: the caps now sum the usage events, nothing writes `usage_ledger`, and the module is gone.**) `record_usage(…)` wrote one tenant+principal row per completed turn into `usage_ledger` (`app/agent/usage_ledger.py`), read back by `usage_summary` and the daily cap. Cost is priced per LLM call by `app/agent/cost/pricing.py` from LiteLLM's `GET /model/info` (input, output and cached-input rates), accumulated in `State.total_cost_usd`, and the ledger row stores that same figure.
- **Bug: cost came from a two-entry code table with one rate per total token (spec 008 A2).** Any other alias cost $0 with no signal, and every dollar ceiling multiplies tokens by a price, so pointing `chat` at a paid model blinded the per-turn, per-subagent and per-tenant ceilings at once. Prices now come from LiteLLM, where the alias is already resolved, so swapping the model behind an alias re-prices it and a self-hosted model is priced by `model_info` in the LiteLLM config. **Unknown is not free**: LiteLLM's known $0 (Ollama) is a price; a missing one is `None`, counted per call (`agent_unpriced_usage_total`, alert `ModelUsageUnpriced`) and refused outright under `UNPRICED_MODEL_POLICY=block`. An alias served by several deployments is priced at the dearest, and as unknown if any is unpriced. A delegated run is priced by its specialist's own alias (`GraphDeps.model_alias`), and **`block` covers it too**: the turn-entry check only sees the parent's `CHAT_MODEL`, so `run_subagent` refuses a specialist whose own `model:` is unpriced before any model work (`agent_subagent_run_total{outcome="model_unpriced"}`) — the advisory AI review on #124 caught that the first version let one through.
- **Degrade paths are counted, and two are alerted (spec 008 A1).** A failed ledger write, ledger read, reservation write/release/read or model resolution each increments `agent_cost_governance_degraded_total{path}`. Two hide committed spend, so they page: `LedgerWriteFailing` (the turn succeeded but its row is gone, so every allowance read from that ledger undercounts; **retired with the ledger write in T030c2, pattern 62: the page for a lost cap-feeding write is now `UsageEventWriteFailing`**) and `TenantAllowanceUnenforced` (the allowance read failed open, so those turns ran with no daily cap).
- **The rolling-window read is indexed and the table is trimmed (spec 008 A3).** `17-usage-ledger-indexes.sql` adds `(tenant, recorded_at)` and `(tenant, principal, recorded_at)` (measured on 600,000 rows: 5,770 buffers / 9.3 ms down to 1,857 / 1.5 ms) and drops the now-redundant `(tenant, principal)`. `scripts/usage_ledger_sweep.py` (retired in T030c3; its successor for the events is pattern 63) deleted rows past `USAGE_LEDGER_RETENTION_DAYS` in batches (at most 1,000 batches, 5 million rows, per run; hitting that is logged and printed, and the next run continues, so one run's duration is bounded even if something keeps re-inserting old rows); the setting has a 35-day floor, enforced again inside `sweep_old_rows`, so a calendar-month window can never lose spend still inside it. Nothing schedules the sweep. Existing volumes need the index file applied by hand (plain `psql -f`: it uses `CONCURRENTLY`).
- **Resume re-checks the allowance; crash-continue holds a reservation (spec 008 A6).** Only a brand-new turn used to be checked, so a tenant past its ceiling could keep spending by approving paused turns (the approval wait is unbounded) — each resume runs the approved tool and calls the model again. `astream_events_resume` now refuses an over-budget tenant (`tenant_budget_exceeded`; the thread stays paused, and `cancel_run` is never gated because it gives the model no turn) and takes a hold for its duration. The unattended decline loop passes `admitted=True`: it is a step of a request that already passed, and refusing it would strand the conversation at its pause. `astream_events_continue_turn` is **not** refused — it retries admitted work, and refusing could strand a turn that already ran a mutating tool — but it takes a hold, since the crashed worker's was lost. The overshoot that allows is bounded by that one turn's `MAX_COST_USD_PER_TURN`.
- **The allowance's failure mode is a decision, and the rule is its own module.** The check moved out of `app/agent/runtime/core.py` into `app/agent/cost/budgets.py` (`check_tenant_daily` returns an `Allowance`, not a bool; `runtime.allowance_refusal` is the one question every entry point asks). When the ledger READ fails, `BUDGET_CHECK_FAILURE_POLICY=open` (default, unchanged) serves the turn, counted and alerted, with `Allowance.degraded=True`; `closed` refuses it as `budget_check_unavailable`, which blames no budget and so doesn't trip the budget alerts. The in-flight hold read stays open either way, since it only closes a race and the ledger check beneath it is still enforced. A refusal is now logged with its tenant and principal (the counter deliberately has no label for them).
- **Four limits, two scopes, two windows (`app/agent/cost/budgets.py`).** A limit is `(scope, window, dollars)`: scope `tenant` or `principal` (one person inside their tenant), window `day` (rolling 24h) or `month` (the CALENDAR month in UTC, resetting on the 1st like an invoice). Only tenant/day is always on; `MAX_COST_USD_PER_TENANT_PER_MONTH` and `MAX_COST_USD_PER_PRINCIPAL_PER_DAY`/`_PER_MONTH` are off at 0, so an unconfigured deployment behaves as before and pays for exactly one ledger read. The first exceeded limit refuses (tenant before person, since an organisation-wide stop matters more) and only it is counted: `agent_budget_exceeded_total{scope,window}`. A person who hit their own limit gets `personal_budget_exceeded`, everyone else keeps `tenant_budget_exceeded`. Turns still allowed but past 70/85/95% of a limit are counted under `agent_budget_threshold_total` (highest crossed only) and logged once per day/month with the tenant and person; only tenant-scope 95% pages (`TenantBudgetNearLimit`), because a person reaching their own cap is the guard rail working. These counters replace the unlabelled `agent_tenant_budget_*` pair, and `TenantDailyCostBudgetExceeded` became `TenantBudgetExceeded`.
- **Operators can override a limit per tenant or per person (`budget_policies`).** The four limits are Settings defaults for everyone; `postgres-init/18-budget-policies.sql` holds overrides keyed `(tenant, subject, period)` where `subject` is `''` (the tenant's own), `'*'` (every person in the tenant: a per-tenant plan tier) or one principal, and `budgets.resolve_limits` applies person > `*` > default. The value has two special meanings that are opposites: **NULL = explicitly no cap** and **0 = refuse everything** (the suspend switch), which the column and a real-Postgres test keep distinct. Edited only through `scripts/budget_policy.py` (`make budget-policy`, audited with `--by`), read before every turn through a per-process cache (`BUDGET_POLICY_REFRESH_SECONDS`, 30), so **a change, including a suspend, reaches a running worker within that long, not instantly**. A failed override read follows the same fail policy as a ledger read, counted as `policy_read` under `TenantAllowanceUnenforced`; a MISSING table (migration not applied) reads as no overrides with one warning, because refusing every turn over an unapplied migration would be worse. `GET /usage` now also returns `budgets`: every limit that applies to the caller, with spent, remaining and `resets_at`.
- **The gateway is the backstop, and the app tells it who is calling (`app/core/gateway.py`).** The app-level limits can all be wrong at once (a bug in the allowance, a loop; NOT an unpriced model: LiteLLM prices from the same list, so it cannot see that spend either, pattern 74), so LiteLLM holds a scoped key with its own `max_budget`, minted by `scripts/litellm_key.py`; the master key can't carry a budget, so an app sending it had no gateway-side cap and handed over gateway admin with one compromised container. Compose now sends `LITELLM_APP_KEY` (falling back to the master key so an existing deployment keeps running; both cases checked with a real `docker compose config`), and a real run confirmed the scoped key can still read `/model/info`, which `app/agent/cost/pricing.py` and `app/core/model_resolver.py` need: had LiteLLM refused it, every model would read as unpriced and `UNPRICED_MODEL_POLICY=block` would be an outage. Every LLM call (agent, follow-ups, compaction, the two cron scripts) carries `user` = a hash of the tenant and `metadata.tags` = `tenant:<name>`; **verified against a real LiteLLM**, they land as `end_user` and `request_tags` in its spend log, and neither reached the model backend. LiteLLM's stop is recognised by its error `type` (`budget_exceeded`), not its status, which was 400 on older code and is **429 on `main-stable`**: my first version assumed 400 from reading source, and a real run showed otherwise. It becomes `provider_budget_exceeded` plus `agent_gateway_budget_exceeded_total` and the critical `GatewayBudgetExceeded` alert, also when follow-ups or compaction swallow it. **Bug found by that run:** LangGraph's default `retry_on` retries any non-programming error, so the agent node retried the refusal three times (nine gateway requests with the SDK's own retries); `AGENT_RETRY_POLICY` now refuses to retry it. **Gap (partly closed by pattern 74):** a key budget is one global number, not per tenant, and it covers embeddings too; pattern 74 first added a per-tenant default budget for chat calls and then made it per person (the end user is the person), so there is no tenant-wide cap at the gateway, and embeddings still have none.
- **Closed for chat-model calls (spec 010 PR 1b), open for embeddings.** The ledger used to see only the agent node's calls (`graph/agent_node.py` was the one accumulator), so follow-up suggestions and history compaction spent tokens no dollar cap counted. Every chat call now goes through `metering.metered_invoke` (pattern 51): the agent node's cost still joins the turn's running total, and the others get their own ledger row, so the caps and `GET /usage` now include them. **Still open:** embeddings (`OpenAIEmbeddings` returns vectors only) are neither metered nor attributed at the gateway; that is PR 1c.
- **Gap:** in-flight holds are per tenant, so a person's limit does not see their own concurrent turns and can be overshot by up to (concurrent turns) x `MAX_COST_USD_PER_TURN`; the tenant limits stay exact. A monthly window reads a month of the tenant's ledger rows before every turn, and only when a monthly limit is on. Measured on a real Postgres with the shipped indexes (warm, best of 5): 2.4 ms for a 10,000-row day, **16.6 ms for a 300,000-row month**, 0.3 ms for one person's month. That is fine in front of a multi-second turn, but it grows linearly with a tenant's volume; past a few million turns a month it wants a daily rollup table.
- **Bug: unfinished turns weren't recorded.** Only the success branch recorded usage, yet completed steps sit in the checkpoint and timed-out turns spend the most. `_record_unfinished_turn` now reads the last checkpoint on the timeout, error and cancel paths.
- **The daily cap counts in-flight turns.** `reserve_budget` records a hold of `MAX_COST_USD_PER_TURN` per running turn (`tenant_budget_holds`), released by id at the end; holds older than `RESERVATION_STALE_AFTER_MINUTES` stop counting. Without holds, N concurrent turns all read the same "spent so far".
- **Bug: the first design was one running total per tenant.** A killed worker's amount was never released, and every reserve refreshed the same timestamp, so a leaked amount never aged out (still counted 40 minutes later), refusing real turns over spend that never happened. One timestamp can't mean both "last touched" and "how old is what this holds". Fake-cursor tests can't show this; `test_budget_holds_real_postgres.py` ages real rows.
- **Gap:** tokens from a call cut off mid-flight, and turns paused and never resumed, aren't counted. A LiteLLM fallback (`chat` to `chat-backup`) can serve a call at another deployment's price without the response saying so, and cache-WRITE tokens are billed at the input rate because `langchain-openai` drops that field. The cap fails open (a failed reserve means unprotected, not blocked). Existing volumes need `16-tenant-budget-holds.sql` applied by hand.

### 51. Per-call usage events behind one metering choke point
`usage_ledger` is one row per completed turn with no key that names a call, which is enough for a spend cap and not for billing: a replayed write is unrecognisable, and a provider that deduplicates usage by a caller-supplied id (Stripe `identifier`, Polar `external_id`) has nothing to be handed. `usage_events` (`postgres-init/19-usage-events.sql`) is one append-only row per model call, and `metering.metered_invoke` is the one place a chat-model call is made, priced and recorded. Design in `specs/010-credit-billing-readiness/`.
- **Identity is verified, not assumed.** `event_id = uuid5(tenant | AIMessage.id)`. Read from the installed langchain-core and confirmed with a real `ChatOpenAI` through a checkpointed graph: the id is assigned by langchain as `run-<run id>-<index>`, is unique per invocation even when the provider repeats its own id, and is identical after a checkpoint round trip. The provider's `chatcmpl-…` id is deliberately not used (a backend may return a fixed or missing one). `tests/agent/cost/test_usage_events.py` pins all of it, so a library upgrade that changes id assignment fails loudly instead of silently merging or double-counting calls.
- **The duplicate story is the table's primary key**, `INSERT … ON CONFLICT DO NOTHING`, proven on a real Postgres (20 concurrent writers of one event produce one row). The table is append-only by trigger (UPDATE always refused; DELETE only when the retention job says so inside its own transaction, and `SET LOCAL` means it cannot be left on). `cost_usd` is **NULL when the model has no price**, never 0, because a 0 would be billed as free; money is `NUMERIC(18,12)`, because six places would store a $0.0000004 call (a cheap model, an embedding) as exactly zero, a systematic loss that a billing meter cannot afford (found when a credit-pricing test failed on it).
- **A choke point, because a call site that must remember to meter will one day forget.** The agent node, subagents and every later call site go through it; `tests/agent/cost/test_metering_choke_point.py` reads the AST and fails on any new unmetered `llm.ainvoke`, and on a stale exemption, so the list of the four known unrouted sites (follow-ups, compaction, the two cron scripts) can only shrink.
- **Fails open, counted, alerted.** A failed write never fails a turn, but a lost event is lost revenue and a log line tells nobody, so `usage_event_write` pages (`UsageEventWriteFailing`) and an unapplied migration is its own counted path (`UsageEventTableMissing`). There is **no kill switch any more** (pattern 58: the caps sum these rows, so `USAGE_EVENTS_ENABLED=false` is refused at startup). The write costs p50 0.56 ms / p95 0.79 ms on a pooled local Postgres (loopback: add your network round trip), against multi-second model calls.
- **Every chat call is routed (PR 1b), and a call is counted exactly once** (`to_ledger` was removed in T030c2, pattern 62: the event is the whole record). Follow-ups, compaction and the two cron scripts now go through the choke point with `to_ledger=True`, because their cost never joins the agent node's running total (the turn-end ledger row is written from that total, so the agent node passes `to_ledger=False`; a row from both would count it twice). `tests/agent/cost/test_metering_every_call_site.py` asserts the invariant directly: across an answer, a compaction and follow-ups, the events' cost equals the turn's running total plus the others' own ledger rows, with no gap and no overlap. **Compaction deliberately does not add to the turn's token or cost budget**: it can summarise tens of thousands of tokens, and charging that to the turn could stop the very answer the turn exists to give. The ratchet's exemption list, which started with four sites, is now empty and stays as a place to record a deliberate exception.
- **Bug this prevented:** the first test pass was green in 46 s against ~15 s before. The new write was reaching a real Postgres and a real model-resolver on every test turn, which is the exact leak the autouse mocks exist to close; `usage_event_sink` now closes it and captures each row for assertions.
- **Gap (disclosed; closed in T030c2, pattern 62):** a dual write (`usage_ledger` per turn, `usage_events` per call) that outlived this change: the caps now read the events (pattern 58) and the ledger is kept as the second record and the way back until its write is retired; both come from one `PricedCall`, and a test asserts the per-call events sum to the running total the ledger row is written from. A model call whose response arrives and whose process dies before the event commits is not recorded; the planned reconciliation against the gateway log is the detector. Embeddings are not yet routed (PR 1c: they need the tenant plumbed through nine call sites that take no `ctx`).
- **An escalated turn is priced as the alias that served it (specs/014, GRAPH_PATTERNS.md pattern 68).** When the model router sends a turn to `STRONG_CHAT_MODEL`, `agent()` passes that alias both as the call's per-call `model=` and as `model_alias`, so the call, the per-turn dollar ceiling and the usage event all name the strong model and cannot disagree about it. If that call never reaches a model (a connection failure, a timeout, or a gateway 5xx) the same call is repeated on the local alias and recorded as the local alias: a call that failed writes no event, so the ledger never shows a price for a model that did not answer. That is why the degrade-to-local is in the app and not in a LiteLLM `fallbacks` entry, which would have recorded the strong alias for a local answer. An unpriced strong alias keeps the route local (counted `strong_unpriced`) whatever `UNPRICED_MODEL_POLICY` says, so the router can never be the reason a turn is refused. The gateway's own budget stop is deliberately not caught by the fallback.

### 57. Carrying the ledger's history into the events, and a first version that could never finish
The dollar caps sum `usage_ledger` today and are about to sum `usage_events` (specs/010 T030b), so the per-call meter, the wallet and the export are no longer a second record kept in step with the one the caps use. The events only begin when `postgres-init/19` is applied, so switching the read alone would make a monthly cap forget the month so far and `GET /usage`'s all-time total come back short. This change is the additive half and is merged first: it changes no behaviour, so it can be run and checked before the release that depends on it.
- **What it copies, and what it must not.** `make usage-events-carry-over` (`scripts/usage_events_carry_over.py`) copies each ledger row older than the **first real event** as one `ledger:<id>` row (`kind='chat'`, the ledger's own time as `occurred_at`, no input/output split because the ledger never kept one). Nothing newer: since the events existed every turn has been written to both tables, so copying those would count them twice and double a tenant's spend on the day it is switched on. The cutoff is the first row whose id does not start with `ledger:`, so a carried row never moves it (a test pins that: a naive `MIN` would slide back to the oldest history and stop the second run carrying the rest).
- **History is not a call.** A carried row is never rated, charged or queued for export: the statement is plain SQL outside the paths that do those, so it cannot bill anyone or reach a provider. A real-Postgres test pins that the row has no credits and that the tenant has neither a wallet transaction nor an outbox row afterwards.
- **The first version could never finish a large ledger.** Each run scanned from ledger id 0, so a ledger bigger than one run's ceiling (1,000 batches of 5,000) re-read the same already-carried rows and never advanced, while the docstring promised that a re-run continues where the last stopped. Found while writing the test for it, not by reading: the statement now selects only rows not yet carried, and the test that runs three ceiling-limited runs and expects 2, 2, 1 fails against the old query. `ON CONFLICT DO NOTHING` stays for two runs racing each other, and a test runs two against 3,000 rows and checks nothing was counted twice.
- **A global cutoff on a shared test container needed a filter.** The cutoff is one instant for the whole table, and the integration container is shared by every worker, so an unfiltered carry-over would copy other tests' ledger rows and could race their assertions. `--tenant` exists because of that, and it is also what an operator wants for checking one tenant before the full run. The empty-table branch (no real event yet, so the cutoff is now) is asked of an empty table by deleting every real event inside a transaction that is rolled back.
- **A test that writes history can break an unrelated test that deletes it.** The ledger sweep test deletes old `usage_ledger` rows across tenants in batches of 2 up to a ceiling of 2,000; the race test writes 3,000 three-year-old rows, so the sweep never reached its own rows and failed. It had passed in a full integration run by ordering luck. The carry-over tests now remove their ledger rows afterwards (the ledger is not append-only; the events are, so those stay) and run in the sweep tests' xdist group so the two never overlap; removing the cleanup makes the sweep test fail again (checked).
- **Verified:** 10 hermetic tests (the loop's control flow with a scripted connection: when it stops, what each batch resumes after, the ceiling, the wording an operator reads, the missing-table message) and 11 real-Postgres tests (history carried and nothing newer, a re-run, the sum whole afterwards and history in the window it was spent in, never rated/charged/queued, the tenant filter, a dry run that writes nothing, ceiling resumption, batches, two runs racing, the empty-table cutoff, a carried row not moving the cutoff). **Mutation check: 7 mutants, all caught** (the cutoff counting carried rows, no cutoff bound, the copy stamped with the copy time, carried rows re-read, the tenant filter ignored, `ON CONFLICT` dropped, history rated).
- **Gaps (disclosed):** nothing alerts that the carry-over was skipped (`ARGS=--dry-run` printing `Would carry 0` is the check). A turn that straddles the cutoff is counted by its events only: its earlier calls, once. A ledger row from a stretch when events were not being written *after* the first one existed sits past the cutoff and is not carried (`make credit-reconcile` names such a tenant-day). It scans `usage_ledger` by id and probes `usage_events` by its primary key once per row, which is fine for a one-time job and not something to run every minute.

### 58. The dollar caps sum the per-call events, and the history is carried across instead of forgotten
Until now the caps and `GET /usage` summed `usage_ledger` (a row per turn, written when the turn ended) while billing, the wallet and the export were built on `usage_events` (a row per call). Two records of one spend, kept in step by a test. `app/agent/cost/spend.py::usage_summary` now sums the events, so what is capped, charged, exported and reconciled is one set of rows (specs/010 T030b; T030c retires the ledger write). The history comes across first, by pattern 57.
- **Three gaps close by construction.** A turn is counted as it spends, not when it ends (a turn that timed out, was cancelled or sat paused for approval used to spend money no cap could see; spec 008 B17 patched the timeout case by re-reading the checkpoint). Every kind of call is counted (follow-ups, compaction, subagents, the cron scripts) because the choke point writes the event. And the cap and the bill cannot disagree, because they sum the same rows.
- **The cutover keeps its way back (until T030c2, pattern 62 ended it).** The ledger was still written (the dual write stayed until T030c), so reverting the read was a one-line change that found the ledger complete. Retiring both at once would have put the working cost caps at risk, which is why `plan.md` chose the dual write in the first place.
- **The history is carried first, and the two meet in a test.** Events only begin when `postgres-init/19` is applied, so switching the read alone makes a monthly cap forget the month; pattern 57 is the copy, merged before this. `test_the_history_a_carry_over_copied_is_what_the_cap_then_reads` runs both halves: before the copy the read misses 40 dollars of history, after it the read sees it, and a recent window still sees only the recent event.
- **The kill switch had to go.** `USAGE_EVENTS_ENABLED=false` was an emergency switch for a hurting write path; with the caps reading the same rows it would make every cap read $0 and stop enforcing without a sound. It is refused at startup. The setting is kept (and not deleted) because Settings ignores unknown variables, so an operator's old `=false` would otherwise be dropped silently and they would believe the writes were off.
- **Deliberate differences from the ledger sum.** An unpriced call adds its tokens and $0 (its cost is NULL; `SUM` skips it; `UNPRICED_MODEL_POLICY=block` is what refuses a model with no price). The window is `occurred_at`, the time of the call, not the end of the turn. A running turn is counted twice in the safe direction: its finished calls are events while its hold (`MAX_COST_USD_PER_TURN`) still stands, so a sibling's tenant check can refuse a little early and can never let a burst through.
- **Measured, and an index was decided against.** One tenant with 2,000,000 events in 30 days (a throwaway Postgres, 2.6M rows): the tenant's rolling 24h read (the cap that is always on) 9.3 ms; one person, 24h, 5.8 ms; one person, month, 98 ms; **tenant, month, 426 ms (a sequential scan)**. A `(tenant, principal, occurred_at)` index took the person-day read to 0.46 ms and the person-month to 79 ms, and would cost 118 MB (32% of the table) and a write on every model call to save about 5 ms on an opt-in cap; unlike the ledger (spec 008 A3, whose only index made the read walk every one of a tenant's rows) the existing `(tenant, occurred_at)` already gives a good plan. A covering index for the monthly sum (194 ms) was measured and not adopted either.
- **A scratch script shares the test harness's container.** `tests/containers.py::ensure_postgres()` caches the container it starts, so a measurement script that called it left 2.6M rows and its own index there, and the next pytest run picked them up: a test that asserts which index the planner uses failed on an index that was never part of the schema. It was my own pollution, not a product bug, and the run's teardown removed the container; measure on a container of your own.
- **Verified:** 18 new hermetic tests (one retired with the kill switch; the statement's shape, the wiring from `budgets`, the suite's own connection guard, the refused kill switch) and 11 real-Postgres tests (the sum never crosses tenants or people, the window, an unpriced call, **a cap that trips on events with no ledger row anywhere**, **a ledger row alone no longer counted**, the real writer's columns agreeing with the reader, the carry-over's history being what the cap then reads, the index the window read uses). **Mutation check: 9 mutants, all caught** (the read pointed back at the ledger, the window on the wrong column, the tenant or the person dropped from the statement, `budgets` no longer asking, the kill switch allowed, the suite's connection guard removed, `COALESCE` dropped, the window bound removed). One mutant **survived** at first and was a real test gap: nothing asserted that the suite's autouse guard covers the new module, so a turn test could have started paying a real connection attempt for the cap read; `test_the_suites_own_guard_covers_this_read` now does.
- **Gaps (disclosed):** the **monthly caps are linear in a month's model calls** (426 ms at 2M events, off by default; the lever is a per-day rollup written in the event's transaction, not built). The carry-over's own gaps are pattern 57's, and one matters more now: **nothing alerts that it was skipped**, so a monthly cap under-counts the month so far until it runs. **Nothing trims `usage_events`** (spec D7's retention job was never built, and the ledger sweep no longer governs what the caps read); the sweep is T030c3, pattern 63. A deployment that never applied `19-usage-events.sql` now has caps that fail open (`TenantAllowanceUnenforced` pages) where they used to work off the ledger alone.

### 62. The per-turn ledger stops being written: one record of spend, and what that costs
The caps sum the usage events (pattern 58) and the reconciliation no longer compares the ledger (pattern 61), so the per-turn `usage_ledger` row had no reader left. This change stops writing it (specs/010 T030c2): the turn-end row in `_record_turn_metrics`, the subagent run's own row, `metered_invoke(to_ledger=...)` and the follow-up, compaction and cron call sites that passed it, `record_usage` itself, the `LedgerWriteFailing` alert and the `ledger_write` metric path. One record of what was spent remains, written where the call is made.
- **What it closes.** Pattern 26 disclosed that a turn which timed out, errored, was cancelled or sat paused for approval never reached its end-of-turn ledger write, and spec 008 B17 patched only part of it by re-reading the checkpoint. That was a MONEY problem because the row was written at the end. It is gone by construction: each call's event is written the moment the call returns (`metered_invoke`), so whatever happens to the turn afterwards cannot lose it.
- **A correction to my own earlier plan.** `tasks.md` said the unfinished-turn checkpoint re-read "existed only to feed" the ledger. It did not: it also feeds `agent_tokens_total`, so it stays, bounded to 2 s and unable to change the terminal event. What went is its `ctx` and `thread_id` plumbing, which only the ledger write needed (`_record_turn_metrics` lost both parameters). The test file for it was rewritten around the tokens metric; the old "a failed usage write does not change the terminal event" became "a failure while counting does not change it".
- **The properties the ledger's tests held did not vanish with them.** `test_record_usage.py` was deleted whole. The concrete model behind an alias (pattern 38) is not covered by any event test, so two were added (resolved when LiteLLM answers, null and still written when it does not); a negative cost cannot reach an event because `pricing` only accepts finite non-negative rates and the column has a `CHECK` (pinned by `test_pricing.py` already); no identity, no tokens and a failing write are the events' own tests. The call-site invariant ("every call counted exactly once") was rewritten from "an event and a ledger row" to "one event per call, the agent node's inside the turn's running total, the others' outside it".
- **A fixture that quietly became dead.** `mock_model_resolver` (autouse) patched `usage_ledger.resolve_model`, the ledger's own binding; removing the import made every test error at setup. `usage_event_sink` already patches the only remaining caller, so the fixture was deleted, not retargeted, and its docstring references reworded.
- **What it costs, said plainly.** There is no way back: a release that reads the ledger would see spend only up to the day this change deployed, and the runbook's old line "to go back, revert the release" is replaced. A failing event write is now the only thing that makes a cap under-count, so `UsageEventWriteFailing` is the page for it. And there is no second local record: a lost event is found only by the gateway comparison (pattern 61).
- **Verified:** the hermetic suite (2543) and the full real-Postgres tier pass. **Mutation check: 7 mutants, all caught** (unfinished turns no longer counting tokens, a failure while counting reaching the turn, the checkpoint read unbounded, the resolved model not recorded, a delegated run recorded as `chat`, follow-ups or compaction recorded under the wrong kind).
- **Gaps (disclosed):** the frozen table still existed with its retention sweep, and the budget holds still lived in `usage_ledger.py`; both went in T030c3 (patterns 63 and 64). `postgres-init/12-tenant-budget-reservations.sql` still has a historical comment naming `record_usage`.

### 63. The usage events get the retention sweep that spec D7 promised, and it refuses to hide unfinished exports
`usage_events` is append-only and, since the caps sum it (pattern 58), it grows with every model call. The ledger it replaced had a sweep; the events had none, so a year of calls was a year of rows read by the reconciliation and scanned by the monthly caps. `make usage-events-sweep` (`app/agent/cost/usage_events_retention.py`, `scripts/usage_events_sweep.py`; specs/010 T030c3) deletes events older than `USAGE_EVENT_RETENTION_DAYS` (400 by default).
- **A floor, enforced twice.** A monthly cap reads back 31 days, the reconciliation up to 35, the export outbox gives up on an unsent event at 30, so the setting refuses to load below 35 and `sweep_old_events` raises below it BEFORE a row is touched (the floor holds for any caller, not only the script).
- **It will not delete evidence of unfinished work.** *(Since spec 013 the export outbox and this guard belong to the billing package's own sweep, `credit-billing-usage-sweep`, over its own `billing_usage_events`: see `packages/billing/docs/PATTERNS.md` B3. The agent's sweep below has no outbox to protect and the paragraph is the history of why the guard exists.)* An event whose export is `pending`, `failed` or `expired` is usage that was meant to reach a provider and did not: lost revenue with an alert on it. Deleting it because it is old would turn something nobody has resolved into something nobody can see, so it is kept and counted (`held_back`, printed with a pointer to the runbook). Only a `sent` export is finished: that event goes together with its outbox row, in ONE statement, because the foreign key `usage_export_outbox.event_id -> usage_events` is checked at the end of it (the migration's own note said any retention job would have to clear finished outbox rows first, on purpose). Mutation check: protecting only `pending`, protecting nothing, and not clearing the finished row are each caught.
- **The delete is permitted per transaction, not per session.** The table refuses DELETE unless `usage_events.allow_delete` is on; the sweep sets it with `set_config(..., true)`, which is LOCAL to the transaction, so it cannot be left switched on, and a test pins that a bare DELETE is still refused afterwards.
- **What it does not touch: the wallet.** A debit keeps its `usage_event_id` as lineage (there is no foreign key from it) and the balance does not move; a test deletes the event of a charged debit and checks both. What is lost is the ability to recompute that debit's credits from the event row, so keep events at least as long as you may need to explain a charge.
- **Verified:** 20 hermetic and 10 real-Postgres tests (past the cutoff and across batches, a re-run, the floor, a bare DELETE still refused, a `sent` event with its export row, `pending`/`failed`/`expired` kept, two providers where only one finished, the wallet untouched, another tenant's recent events). **Mutation check: 7 mutants, all caught** (unfinished exports unprotected, only `pending` protected, the finished row not cleared, the delete never allowed, the cutoff inverted, no floor, held-back not counted).
- **Gaps (disclosed):** nothing schedules it (like the other sweeps, on purpose: this is the table spend is read from). A `failed` or `expired` export keeps its event forever until a person resolves it, and there is no "resolved" state to mark that yet. The all-time `/usage` total is bounded by the retention window. The per-batch scan has no index on `occurred_at` alone (the oldest rows are first in the heap, so a batch is found quickly; checked only by reasoning, not by a measurement at scale).

### 64. The budget holds move out of the retired ledger module, and the module goes with its sweep and its setting
The last thing in `app/agent/usage_ledger.py` that was not dead was not about the ledger at all: the in-flight budget holds (`reserve_budget`, `release_budget_reservation`, `in_flight_reservation`) that keep N concurrent turns from all passing the same stale cap check. They sat there because they always had. They are now `app/agent/cost/budget_holds.py`, moved verbatim apart from their docstrings, and the module, its sweep script (`scripts/usage_ledger_sweep.py`), `make usage-ledger-sweep`, and the `USAGE_LEDGER_RETENTION_DAYS` setting are deleted (specs/010 T030c3b). The `usage_ledger` TABLE stays, frozen and read-only: it is the source the carry-over copies from, and dropping it is a later, separate, destructive decision.
- **A rename, so it was checked as one.** Every caller and test that patches or calls a hold function moved to the new module, and the full suite and the real-Postgres tier ran before and after; the move changed no statement.
- **A stale caller fails loudly.** `test_the_ledger_module_is_gone_so_a_stale_caller_fails_loudly` asserts importing the old module raises `ModuleNotFoundError`, the replacement for "the ledger no longer has `usage_summary`" now that the whole module is gone.
- **A test group whose reason changed under it.** The shared xdist group of the carry-over, spend and retention tests existed because the LEDGER sweep deleted old rows across tenants. That sweep is gone, but the events' sweep does the same across `usage_events`, and would delete the carry-over tests' three-year-old carried rows mid-test, so the group stays. It was renamed `usage_events_old_rows` and its rationale rewritten, rather than keeping a name and a comment about a thing that no longer exists.
- **Two tests collided, in a way only a shared database can show.** The retention tests deliberately leave events with unfinished export rows behind (that is what they prove are kept), and a carry-over test deletes every real event inside a rolled-back transaction to ask the cutoff of an empty table; the outbox foreign key then refused the delete. It now clears the outbox first, inside the same rolled-back transaction. The export worker cannot touch the leftover rows (it claims only providers it is configured for), checked in `export.py` rather than assumed.
- **A third collision, and what actually fixed it.** The carry-over race test leaves 3,000 years-old carried events behind, and the retention test (batches of 2, a ceiling of 1,000 batches) hit that ceiling at 2,000 deleted rows without ever reaching its own: `deleted=2000, complete=False`, reproduced by running the two files in that order. The same class of bug as the ledger sweep one. Two changes, and they do different jobs: that test now passes an explicit, generous `max_batches` (that alone makes it independent of any residue; checked by removing the purge and watching it still pass), and the three fixtures now `purge_events` what they wrote (events are append-only, but the transaction-local permission the sweep uses works for a cleanup), which keeps the shared table tidy and is what stops leftover export rows blocking the carry-over cutoff test.
- **Verified:** the hermetic suite (2548) and the full real-Postgres tier. The move is mechanical, so no new mutant is claimed beyond the holds' own existing tests.
- **Gaps (disclosed):** the `usage_ledger` table and its indexes (`postgres-init/03`, `17`) remain on every volume. `postgres-init/12-tenant-budget-reservations.sql` still has a historical comment naming `record_usage`.

### 74. What the gateway sees of spend: priced local models, a readable per-person end user with a default cap, the conversation on every call, and a pinned image
Four changes to the same seam, found by asking what LiteLLM's own limits could and could not do for a deployment on local models, and shipped together (they are one story: a gateway cap is only as good as the price and the identity behind it).
- **A local model is priced, or no gateway budget can trip on it.** Measured on the 1.94.1 image before this change, `GET /model/info` reported `chat`, `chat-backup` and `embed` at a known 0 and `vision` as `null`. A `null` is "unpriced" to the app (counted, and refused under `UNPRICED_MODEL_POLICY=block`); a 0 is a price, but LiteLLM's budget docs say a model whose two prices are both 0 skips budget checks, so neither the key's `max_budget` nor a tenant budget could ever accumulate local spend. Every alias in `litellm-config.yaml` now states a shadow price in `model_info`: $0.10 / $0.20 per million input / output tokens for the 7B aliases, $0.20 / $0.40 for the 14B, $0.05 / $0.10 for the 3B vision slot, $0.01 for embedding input. They are the order of magnitude hosted providers charge for open-weights models of that size, not a bill, and a test keeps them real numbers (PyYAML reads `1e-7` as a string, so they are decimals). **Run, not read:** on a scratch Router a price in `model_info` or in `litellm_params` gave 10 x 1e-7 + 20 x 2e-7 = 5e-6; an unpriced model gave nothing; a deployment with no price of its own *inherits* the price registered for the same underlying model by another deployment, which is why each alias states its own and a test requires one price per underlying model. **A consequence to expect:** billing rates a call as `cost_usd x CREDITS_PER_USD x markup`, so local usage now debits a few millionths of a credit where it debited none; a turn that fills the 32,000-token context costs well under a cent.
- **Three chat tiers, two of them waiting for a hosted model.** `chat` (easy, qwen2.5:7b), the new `chat-medium`, and `chat-strong` (specs/014, qwen2.5:14b in dev). `chat-medium` follows `chat-strong`'s rules exactly (`tests/core/test_model_tiers_config.py`): always present, a keyless local stand-in in dev (the same 7B as `chat`, so nothing extra to pull), three `LLM_MEDIUM_*` variables defaulting to the `chat` values in production, and no gateway fallback naming it, because a fallback would answer with one model and price the call as another. Nothing in the app selects it yet (a specialist can name it in its `model:`); this is configuration only. The dev stand-ins stay local on purpose: `make test-live` exercises the router against `chat-strong`'s. Attaching Gemini is one entry (dev) or three variables (prod), with its key in `GEMINI_API_KEY_MEDIUM` / `_STRONG` (the dev compose already passes both through, empty). **Not verified, no key yet:** Google documents tool calling and streaming on its OpenAI-compatibility endpoint (still beta) but not `stream_options.include_usage`, which the app needs to meter a streamed call, and LiteLLM does not know an `openai/<gemini id>`, so its price must be stated. `make probe-tools ARGS="--alias chat-medium"` plus one streamed turn is the check to run when the key exists. **A trap closed on the way:** `litellm_key.py create` listed only `chat,embed`, so a key minted by it refused `chat-strong` (already shipped) and would refuse every new tier; the default now follows the prod config's aliases (a test), and a key minted earlier must be re-minted or widened with `/key/update`.
- **The end user is the person, readable, and the default gateway budget caps each person (for chat).** The app sends `user` = `tenant:<tenant>/user:<principal>`, e.g. `tenant:acme/user:alice`, with each part percent-encoded (tenants and principals are client-supplied strings: an `x-principal-id` header, `telegram:123`, an email, so a `:` or `/` inside one becomes `%3A` / `%2F`, and `gateway.parse_end_user_id` reads it back, strictly: only the canonical encoding is ours, so another application's end user on a shared gateway is not mistaken for one of ours). LiteLLM keeps it as the call's end user: its **Customer Usage** view filters by it and its per-end-user budgets are keyed by it. **This is a correction of the first version of this pattern** (PR #183 shipped the end user as a hash of the tenant, to keep a per-tenant cap and the reconciliation as they were); the user who wanted usage filterable by person pointed out that it listed tenants only, and asked why it was a hash at all. `litellm_settings.max_end_user_budget_id: person-default` in both configs names a budget object that applies to every end user without one of its own, including ones LiteLLM has not seen; `litellm_key.py person-budget set --max-budget <usd> [--budget-duration 30d]` creates or updates it and `info` reads it back (exit 1 when missing); the CLI and the id were `tenant-budget` / `tenant-default` for the day #183 was merged, so a budget created under the old name is no longer referenced. **What that costs, plainly:** the cap is per PERSON, so a tenant with many people can spend many times it, and **there is no tenant-wide cap at the gateway** any more (it would need the tenant to be the end user, or a key per tenant); the app's own tenant limits are exact and stay. **Why it was a hash, and why it can be readable now:** `user` is a standard OpenAI parameter, a person's name or an organisation's has no business reaching a model provider, and whether a gateway forwards `user` depends on the provider and the version, so the first version hashed it. That is an assumption about LiteLLM, so it is now checked instead of assumed: `make gateway-check` (`scripts/gateway_check.py`) runs the PINNED image on the shipped dev config with a stub backend and sends a readable id carrying an email-shaped principal: nothing identifying reached the backend on the Ollama route or on an OpenAI-compatible one (not the end user, tenant, principal, conversation or metadata), and every alias was priced and billed at tokens x price. The image is pinned by digest for this reason and a bump re-runs the check (`infra/README.md`). The gateway's own database and Langfuse already held the readable tenant and principal in `metadata`; a principal can be an email, which is what would leave if a future LiteLLM forwarded `user`. **The reconciliation** now reads the tenant off the end user and sums a tenant's people into its day, so a tenant the gateway spent for and the database has no events for needs no special case (`compare` already reports a day present on one side only); spend-log rows written under the older one-way `tenant_<hash>` id are still attributed by hashing the known tenants (`gateway.legacy_end_user_id`), and that branch can go once the gateway no longer holds such rows. **Run against a live 1.94.1 proxy with its database:** the budget commands (`info` on a missing budget exits 1, `set` creates, a second `set` updates, `info` reads it back; deleted afterwards), and one chat call carrying the readable id: LiteLLM stored it verbatim as `end_user` (encoding intact), created a customer row for it and tagged the call `tenant:acme-check`; the test customer was deleted (its one spend-log row remains). **Read from the installed LiteLLM, not run:** the enforcement itself. `get_default_end_user_budget` applies the default, `_check_end_user_budget` refuses when `spend > max_budget` (so the call that crosses the line still goes through), the refusal is `BudgetExceededError`, which `auth_exception_handler` answers as `type: budget_exceeded`, the type `gateway.is_budget_exceeded` already recognises. **It fails open:** the config only names the budget, and a name with no object behind it makes LiteLLM log "Default end user budget not found in database" and apply nothing, hence `info` and the runbook step. Size it above the largest person's legitimate spend for the same window; it is a backstop above the app's limits, not a copy (a different number for one person is a `/customer/new`, a second place beside `budget_policies`).
- **The conversation is on every call.** `litellm_session_id` and `metadata.session_id` carry the `thread_id`, which the app's own Langfuse trace already uses as its session, so the proxy's per-call traces and the app's turn land in one Langfuse session (before, nothing joined them: the app's trace id is random per turn and the proxy's is its own call id). The cron scripts already pass a synthetic thread id (`ops-digest:<date>`, `followup-sweep:<item id>`), so each digest day and each follow-up draft became a session of its own too; their two identity tests changed to expect it (they had pinned "no session", which was only ever true because nothing sent one). **Run, against the pinned image with a stub backend (`make gateway-check`, which repeats it):** neither field, nor the metadata, the tenant, the principal or `user`, reached the model backend, on the Ollama route and on an OpenAI-compatible one. **Observed on a live 1.94.1 proxy:** LiteLLM's own Session ID (`session_id` in `/spend/logs/v2`) holds the thread id it was sent. That the proxy's Langfuse trace is then filed under the same session was read from its source (the Langfuse logger pops `metadata.session_id`), not seen in the Langfuse UI.
- **The gateway image is pinned by digest** in both compose files (the same one, a test): the multi-architecture index of `main-stable` as of 2026-07-30 (LiteLLM 1.94.1, read with `docker manifest inspect`: linux/amd64 and linux/arm64), the image every check above ran on. The tag moved under this app once (the budget stop went from 400 to 429) and a LiteLLM release on PyPI was compromised in March 2026; the tag stays beside the digest for the reader. A bump is a deliberate act: `infra/README.md`, "Bumping the LiteLLM image".
- **Decided against:** an alert on LiteLLM's `litellm_zero_cost_requests_total`. Production Prometheus does not scrape LiteLLM (`prometheus.prod.yml`), so the rule would be dead exactly where it matters, and the app's own `ModelUsageUnpriced` already counts the same calls; `UNPRICED_MODEL_POLICY=block`, which refuses them, is already set in `deploy/env/prod.env.example`.
- **Verified:** 123 hermetic tests in the files #183 touched, and for the per-person change 199 in the files it touches (the end-user id and its parsing, the reconciliation's attribution of people and of older ids, the cron scripts' identity, the CLI, the configs, `gateway_check`'s own parts) and 2,312 across `tests/agent`, `tests/core` and `tests/scripts`; a mutation check of 27 mutants for #183 and 23 more for this change (the principal left out, no encoding, a non-canonical id parsing, the conversation leaking into the end user, the reconciliation not parsing people or overwriting instead of summing, the older ids no longer resolved, the CLI ignoring the principal, update-vs-create, a missing budget reading as success, the budget id drifting from the configs, the check never reporting a leak, the backends not pointed at the stub, an unpinned image), all caught; `make gateway-check`; and the live-proxy run above. **Not run:** budget enforcement against a live gateway with its database, and the CI tiers (integration, live, deepeval), which are left to CI; the integration reconciliation tests (`test_usage_reconcile_real_postgres.py`) were updated for the new ids and are among them.
- **Gaps (disclosed):** embeddings carry no end user, so no per-person gateway cap covers them (PR 1c), and no cap at the gateway is per tenant; an unpriced model is invisible to every gateway budget; the cap is a backstop and not exact, and its window is LiteLLM's own (measured on 1.94.1: a `30d` budget reset at the next month boundary, 2026-11-01, and a `7d` one at the next seven-day boundary), not the app's rolling day or calendar month; a readable end user is only as private as LiteLLM's not forwarding it, which `make gateway-check` verifies for the pinned image and nothing verifies for a future one until it is run; the reconciliation keeps a branch for the older hashed ids with no removal date; the Gemini attachment is untested until a key exists; the digest has no automated bump (Dependabot here is `github-actions` only, on purpose); a key minted before #183 still lists `chat,embed`; one customer row per person accumulates in LiteLLM's database.
