# LangGraph patterns

Fifty patterns the agent in `app/agent/` applies, each with the bug or gotcha that motivated it. Numbers are stable: code and tests cite them ("pattern 43"), and a number
is never reused or shifted. **Bug** marks a real defect that was found and fixed; **Gap** marks something disclosed and left open. Patterns that are not about the graph
(spend, billing, repository lessons) moved out and left their numbers behind: see [51-66](#5166-moved).

## Patterns

### 1. Input validation with a real exit
`validate_input` stamps state; the conditional edge `route_after_validation` sends bad input to `reject_input` (an `AIMessage`: the system speaking, not the user) and on to `END`. Valid input continues to `compact_history`.
- **Use when:** always. It costs nothing and catches most bad cases.

### 2. Context enrichment
`retrieve_context` pre-fetches before the LLM reasons. `agent` carries the result as text ahead of the turn's question, in the same message (79), never as a system message. The domain's system prompt is the first message of every call, put there by the agent node from the manifest at call time (19); nothing stores it in the thread.
- **Use when:** you have a knowledge base (Qdrant, a DB, an API).

### 3. State tracking
Flow control lives in explicit state (`iterations`, `context`, …), which is what makes loop limits, retries and conditional routing possible.
- **Bug:** `context` and `context_anchor_index` are written only by `retrieve_context`, which a semantic-cache hit skips (22), and nothing reset them. A cache-hit answer that then failed `check_output` was retried with the PREVIOUS turn's retrieved text spliced in at the previous turn's index. `validate_input` now resets both each turn (`test_safety_budgets.py::TestPerTurnReset`).

### 4. Conditional routing
`should_continue` is an edge function, not a node: it decides where execution goes after `agent` (tools, approval, budget exit, or done).

### 5. Output gate with a real retry
`check_output` + `route_after_check` + `retry_output`. A suspiciously short answer routes to `retry_output`, which appends a corrective `HumanMessage` and loops to `agent`. `MAX_ITERATIONS` bounds the retries. Pattern 50 adds two retry reasons from live findings.
- **One registry, not a flag per check:** each reason is an `OutputCheck` in `graph/output_checks.py` (code, detect, feedback, metric, whether a repeatedly-rejected answer is still safe to show, fallback text), in one ordered tuple whose order IS the priority. `check_output` runs them all and records what fired in `State.output_findings` (`{code: detail}`); `last_retry_reason` is the first key. `retry_output`, `retry_exhausted` and `no_answer` read feedback, trust and fallback from the same entry. A new check is one entry. Leak, fabrication and a skipped tool are judged on what the model wrote; deferral and misattribution on that text without a closing offer (70); length and "still uncited" on what is shown.
- **Retry artifacts:** the feedback is a `HumanMessage` only because that is the role a model acts on; it is not something the person said. `retry_output` tags it, and the answer it rejected, with `additional_kwargs[RETRY_ARTIFACT_KEY]` (`graph/messages.py`). `is_user_message` is how every reader finds "the user's message" or "this turn"; `get_session_messages` and `_format_turns_for_summary` skip artifacts, `_estimate_tokens` (the figure that decides when to compact) does not count them, and the worker's `_classify_reclaimed_turn` finds the turn's question with `is_user_message` and does not read a tagged answer as a finished turn; the agent node drops earlier turns' artifacts before a call but keeps this turn's, because the retry needs them. `retry_exhausted` and `no_answer` tag the untrusted answer they replace the same way. An `AIMessage` with `tool_calls` is never tagged: dropping it would orphan its `ToolMessage`s. **Threads from before the tagging are healed, not just fixed from now on:** `validate_input` tags the old untagged feedback (one of seven fixed sentences, directly after an untagged answer; `legacy_retry_artifact_ids`) and the answer it rejected the next time the thread runs a turn, `get_session_messages` skips the same ids for a thread nobody has written to, and `agent_legacy_retry_artifacts_healed_total` stops growing once no such thread is used any more, which is when that code can go. It is a heuristic: a person typing one of those sentences in full right after an answer would be hidden too.
- **Bug:** the feedback was saved as a plain `HumanMessage`, and everything that looks for the last `HumanMessage` found it. After one retry round the semantic cache was keyed by the feedback text instead of the question, a vague follow-up ("more detail pls") searched on the feedback plus itself, the transcript replay showed the feedback as a user message beside the rejected answer, and `_turn_acted` only saw the messages after the feedback, so a turn that ran an approved write and then retried **was written to the semantic cache** (under the feedback text, so a replay was unlikely, but the guarantee in 22 that a cached answer never replays a write no longer held). Tests: `test_graph_integration.py::TestRetryFeedbackIsNotConversation`.

### 6. Loop control
`MAX_ITERATIONS` is the shared cap for both the tool loop and the output-retry loop.

### 7. Error recovery
`ToolNode(handle_tool_errors=friendly_tool_error)` turns a tool exception into a `ToolMessage` the agent sees next turn instead of killing the run. Three failure modes, three policies:
- A tool fails mid-turn: recover via that message.
- `retrieve_context` fails: **degrade** to no pre-fetch (the LLM still has `search_docs`).
- The `agent` node's LLM call fails: automatic **retry** (`AGENT_RETRY_POLICY`). LangGraph's default `retry_on` excludes programming errors, so retry can't mask a bug. It did retry every 4xx from the OpenAI SDK, though (a rejected key, an unknown model, a content-guardrail 400); the policy now gives up on a permanent client error and on the gateway's budget stop, and a guardrail refusal is the turn's answer (71).

### 8. Human-in-the-loop
`human_approval` calls `interrupt()`, which suspends the node and persists state through the checkpointer; a caller resumes with `Command(resume=True/False)`. Two routes reach it: the opt-in `require_approval` flag, and the mandatory route for any non-`read_only` call (15). `make chat-hitl` is a runnable example.
- **Gotcha:** a rejection still needs a matching `ToolMessage` per pending `tool_call`, or the next LLM call fails. `human_approval` synthesizes them.
- **Unattended callers** (`astream_events_turn_unattended`: Telegram, fire-and-forget jobs) auto-decline with `Command(resume=False)`.
- **Bug:** a rejection's `ToolMessage` had no `name`, and `pending_skill_required_tool` counts a required tool as dealt with only when a `ToolMessage` names it. A person who rejected the `run_python_in_sandbox` call a loaded skill demanded was still told "call run_python_in_sandbox now" on every later round, and `check_output` kept rejecting answers for skipping it. `reject_tool_calls` now sets `name` on every rejection (human, cancel, over-budget, invalid name, `use_skill` without search). Test: `test_routing.py::TestPendingSkillRequiredTool`.
- **Bug:** it declined only once, so a model that re-requested the gated write left the checkpoint paused: an empty reply, then every later message refused as "pending approval". It now declines up to `UNATTENDED_MAX_DECLINE_ROUNDS` (3), then cancels the run and sends one explicit "needs a person's approval" message. Test: `test_agent_pause_handling.py::TestUnattendedSecondPause` (earlier tests mocked the stream and never drove a second pause).
- **Use when:** an action sends, writes, spends or deletes.

### 9. Parallel tool execution
`ToolNode` already runs several tool calls from one LLM turn concurrently. No fan-out node is needed (LangGraph's `Send` is for fanning one node over dynamic graph branches, a different case).

### 10. Layered safety budgets
`MAX_ITERATIONS` alone is one layer. Each budget below catches a failure the others can't.

| Budget | Where | Catches |
|---|---|---|
| `MAX_ITERATIONS` | `should_continue` | Model stuck calling tools |
| `MAX_TOOL_CALLS_PER_TURN` | `should_continue` | One turn fanning into dozens of calls |
| `MAX_TOKENS_PER_TURN` | `should_continue`, `agent()` | Unbounded spend over few iterations |
| `HISTORY_TOKEN_CEILING`/`FLOOR` | `compact_history` | History growing without bound (13, 41) |
| `MAX_COST_USD_PER_TURN` | `should_continue`, `agent()` | Same tokens, different dollars by model tier (35) |
| `MAX_REPEATED_ACTIONS` | `should_continue` | The same call with the same args, repeatedly (34) |
| `TOOL_TIMEOUT_SECONDS` | Per tool call | A hung Qdrant or embedding call |
| `REQUEST_TIMEOUT_SECONDS` | Whole turn | Many slow-but-not-hung steps |
| `RECURSION_LIMIT` = `MAX_ITERATIONS * 2 + 15` | LangGraph step cap (`app/agent/runtime/core.py`) | A routing bug causing a node cycle |

- **Bug:** `iterations` and `total_tokens` persist across a thread, so `validate_input` resets them each turn (not on a resume).
- **Bug:** a reset only works if the field's reducer allows it. `subagent_spend` used `operator.add`, so "reset to `[]`" did nothing and old spend counted against later turns; `cancelled`/`approved` weren't reset at all (36). The test asserted the return value, which can't see a reducer. Assert on state read back across two turns (`test_safety_budgets.py::TestPerTurnResetThroughTheGraph`).
- **Bug:** the four safety-net exits (iterations, tokens, cost, no-progress) route to `no_answer`, which appended a fallback message but never answered the `tool_calls` of the `AIMessage` that tripped them. The thread kept a call with no `ToolMessage` for good, and the next LLM call on it is rejected by OpenAI-style APIs. `no_answer_fallback` now answers each pending call (also for a subagent, whose last `AIMessage` stays the tool-calling one), and treats text written alongside a tool request as untrusted, not as a final answer. `run_subagent_impl` applies the same rule to its own read: a last `AIMessage` with pending `tool_calls` is never the answer, even when the model wrote a sentence beside the call ("Let me check that"), so such a run is still reported `budget_exceeded` and not `completed` with the narration as its answer. Tests: `test_graph_integration.py::TestNoProgressDetection`, `test_tools.py::TestRunSubagentImpl`.
- **Use when:** any agent talking to a real model and tools. The pattern (several narrow budgets) matters more than the numbers.

### 11. Custom metrics
OpenTelemetry counters and histograms (`app/core/metrics.py`, `telemetry.py`) for the "how often, across everyone" view that Langfuse's per-call traces can't give.
- **Push, not pull:** every process pushes OTLP to one otel-collector, so one scrape target covers the API and all workers. A `/metrics` on the API could never see a worker.
- **Wiring:** `MetricsCallbackHandler` for tool calls with no node changes; direct `.inc()` where a node decides or degrades. Histogram buckets are explicit: OTel's defaults put every 1–90 s turn in one bucket.
- **Bug: scheduled jobs exported nothing.** `ops_digest`, `followup_sweep`, `tool_call_dedup_sweep` and `ops_investigate` exited before the 15 s export timer, so counters died with the process, and a failing digest post could never fire `TeamChannelNotifyFailing`. Each now runs in `job_runtime.py::scheduled_job()`, which flushes in a `finally`.
- **Bug: a Langfuse client per turn.** Each client starts three background threads nothing stops (six per turn), and the flush hit a fresh client's empty queue. Now one shared client per process (`app/core/tracing.py`), flushed once at exit.
- **Bug: that exit flush could hang for ~90 seconds.** `flush()` joins the client's queue, which retries a batch it cannot deliver, so with Langfuse unreachable a process took about a minute and a half to exit (a one-file pytest run did, with every test passing; a worker would outlast a container's stop grace and be killed). The flush now runs on a daemon thread and exit waits `LANGFUSE_SHUTDOWN_TIMEOUT_SECONDS` (5) for it, logging `tracing_client_shutdown_timed_out` if it gives up. The default test suite also never builds a real client any more (`no_real_tracing` in `tests/conftest.py`). Tests: `test_tracing_client.py`, `test_default_suite_has_no_real_tracing.py`.
- **Gap:** long-lived processes don't flush on graceful shutdown (up to one export interval lost); a SIGKILL loses unflushed metrics and a fraction of a second of traces.
- **Use when:** as soon as there is more than one user.

### 12. Untrusted content framing
Retrieved text is wrapped in `<retrieved_document>` delimiters, and `SYSTEM_PROMPT` says delimited content is data, not instructions. It's structural, so the model needn't spot an attack. One function does all framing, `app/core/untrusted.py::frame_untrusted`: the pre-fetch, the three page-reading tools, and `package_lead_brief`'s replay of stored CRM notes.
- **Bug:** only the pre-fetch wrapped anything. Page readers returned raw text, and `enrich_lead_from_website` stored up to 20,000 characters as a CRM note that `package_lead_brief` (read-only, so un-approved) replayed unframed: 59,150 characters after three enrichments. Separately, a page containing `</retrieved_document>` closed the frame early.
- **Fix:** tag-shaped sequences inside the text are neutralised (still visible, no longer a tag). Notes are framed at replay and bounded to the newest `BRIEF_NOTES_MAX_CHARS`.
- **Limits:** it can't stop a model that follows what's inside; the approval gate does (Principle II). Not covered: ticket comments, `check_ticket_status` notes, a per-note replay cap.
- **Use when:** content the model didn't type re-enters the prompt.

### 13. Bounded conversation history
`messages` is the one `State` field with no cap by construction. `compact_history` (right after `validate_input`) trims via `RemoveMessage` with an estimated-token hysteresis: no-op at or under `HISTORY_TOKEN_CEILING`; once exceeded, drop the oldest whole turns until at or under the lower `HISTORY_TOKEN_FLOOR`.
- **Hysteresis, not "trim back to N":** trimming to the same ceiling re-triggers summarization on nearly every turn and shifts every later token, invalidating the provider's prefix cache.
- **Tokens, not turns:** turns vary wildly; a `tiktoken` estimate (approximate) tracks the context window.
- **Turn-aware:** a turn runs from a message the person sent to the next (not from `retry_output`'s feedback, which is a `HumanMessage` too, 5), so a `tool_call`/`ToolMessage` pair is never split (an orphan fails the next LLM call). The system prompt and latest turn are never dropped. Dropped turns are folded into a summary (41).

### 14. Node telemetry
`build_graph` wraps every node (never inside the node), the `tools` node included, in `instrumented`, which logs `node_started` then `node_completed`/`node_failed`/`node_paused` with the node name, a per-turn `run_id` and `duration_ms`. `human_approval`'s `GraphInterrupt` is a normal pause, logged as `node_paused` and re-raised untouched.
- **Never logged:** message content or the `state` dict, so this can't become an unscrubbed second copy of prompt text outside Langfuse.
- `run_id` is the join key across a request's logs and metrics; Promtail ships the JSON to Loki.
- **An unexpected failure logs where, not what:** the class and `origin` (`app/agent/runtime/stream.py:612 in _run_graph_stream`, from `errors.error_origin`: the innermost frame in `app/`), never the message, which can carry a host, a SQL fragment or a DSN (pattern 30). A bare `IndexError` in a CI run (#171) could not be traced without it.

### 15. Tool capability declarations: a mandatory gate
Every tool declares `read_only`, `mutating` or `outward`: the shared tools in `SHARED_TOOL_CAPABILITIES` (`app/agent/tools/builtin.py`), merged with each domain's own (`app/domains/<name>/tools.py`). `should_continue` checks every pending batch: any non-`read_only` call routes through `human_approval` **unconditionally**. A tool missing from the mapping defaults to `outward` (fail closed). No flag turns this off.
- **Why mandatory:** a RAG agent already carries untrusted content on nearly every turn (12); adding write capability is one gamble from a document steering a real write.
- **`add_note` is the worked example** of the companion rule: a write tool is a fixed, typed, closed-vocabulary operation, and its point id is derived by code (a fresh UUID, later `tool_call_id`-derived, see Extending Further), never supplied by the model, so it can only append.
- **Use when:** the moment a second tool exists. Retrofitting after several writers accumulate means auditing them all at once.

### 16. Durable checkpointing and cross-restart compatibility
`build_graph()` defaults to `MemorySaver` for tests; the runtime singleton uses `AsyncPostgresSaver` (its own database) so a paused approval survives a restart and several processes (API plus worker replicas) share one checkpoint store, which a SQLite file's writer lock can't do safely.
- **Async everywhere:** the saver's lock binds to the event loop that created it, so every process awaits `init_graph_async()` on its own loop.
- **`STATE_SCHEMA_VERSION` + `graph_version`:** each turn stamps a schema version (bumped only on a breaking `State`/topology change) and a build id. `resumability_error_async` runs before every resume and distinguishes `checkpoint_lost` (no paused run) from `checkpoint_incompatible` (schema mismatch). A differing build SHA alone is not an error: deploys change it constantly.
- **A turn left mid-flight is not covered by that version, and a topology change can hide it.** LangGraph names the channel that triggers a node after the edge feeding it, and a conditional edge's channel carries the router function's name. Rename a router (as #171 did, `route_after_check` to `route_after_check_bound`) or remove a node, and a checkpoint a worker left mid-turn no longer shows its pending node: `next` is `()` and a resume runs nothing, silently (verified on the installed LangGraph; `tests/agent/graph/test_checkpoint_across_a_topology_change.py` pins it, so a LangGraph upgrade that changes it is noticed). A turn paused at `human_approval` is unaffected while that node's edges are unchanged, which is why `STATE_SCHEMA_VERSION` is not bumped for these changes. What the app does about it: `_classify_reclaimed_turn` dead-letters an unfinished turn with nothing left to run (`agent_checkpoint_issue_total{reason="nothing_to_continue"}`), so the caller is told to retry; and `_run_graph_stream` reports `checkpoint_incompatible` for a run that ends with no answer, where it used to stream the person's own question back as the answer. **Deploying a graph change: stop the workers and let their in-flight turns finish first** (they await them on SIGTERM); renaming a router or node is what makes this necessary, so prefer keeping names stable.
- **Use when:** a HITL gate must survive a deploy.

### 17. Multi-tenant isolation
A `SecurityCtx` (`tenant`, `principal`, `claims`) is stamped once by `validate_input` from `config["configurable"]["ctx"]`, never from message content. `Policy.lower(ctx, target)` becomes a Qdrant filter applied **inside the query**, never a Python post-filter: a buggy post-filter looks identical to a correct one until a cross-tenant leak.
- `documents` scope to `tenant`; `memories` also to `owner`, in one collection told apart by a `kind` field that is part of the filter.
- **Fail closed:** `route_after_validation` checks ctx first, and every ctx-aware tool re-checks it (a different code path).
- **Not authentication:** `get_ctx` trusts `X-Tenant-Id`/`X-Principal-Id`; a real auth gateway sets them.
- **Bug: conversations weren't isolated.** Thread state (checkpoint, cancel flag, lock, dedup key) is keyed by `thread_id` alone and only the `GET` endpoints checked ownership. Anyone naming an id could read it through the model, approve its pending action under their own identity, or cancel it. `_require_conversation_owner` now runs first on send, resume and cancel: a send atomically claims a new id (`claim_session`, `INSERT … ON CONFLICT DO NOTHING`) or verifies an existing one, and every refusal is the 404 an unknown id gets. It fails closed.
- **Gap:** the check is at the API; anything publishing to Redis directly bypasses it. `telegram:<chat id>` ids are reserved, but Telegram still shares one thread across a group chat. A conversation with no `chat_sessions` row can't be resumed over HTTP.
- **Use when:** more than one customer or workspace shares a deployment. Do this first.

### 18. Cross-session memory
`remember` is the only way a memory is written (`mutating`, gated like `add_note`). Recall is automatic, folded into retrieval: the model decides to *write*, never to *read*.
- **Why writing is opt-in:** whatever writes memory decides what replays into every future prompt, so an autonomous write would be a privileged side channel.
- **Re-filtered every call:** the memory leg of `gather_context` applies `Policy.lower` fresh, scoped to tenant **and** owner, never cached.
- **Framed like a retrieved document, and more so:** a poisoned document affects one answer; a poisoned memory replays every turn until removed.
- **Not built:** an LLM-facing forget tool. `delete_by_filter` supports a data-subject-request script, not the model.

### 19. Prompt-cache stability
`SYSTEM_PROMPT` is a plain constant: no principal, tenant or timestamp is ever interpolated. `SecurityCtx` flows through `config`/`state["ctx"]`, never into the messages sent to the LLM. The classic cache-buster, `ctx["principal"]` in the prefix, looks stable within one conversation and only shows once a second principal shares the manifest. `tests/agent/graph/test_prompt_cache_stability.py` asserts byte-identical rendering across two ctx values, plus a leak sweep.
- **Bug (and the design that ended its class):** the prompt used to be *seeded into each thread* once. `ensure_seeded_async` only asked whether a `SystemMessage` with the CURRENT text existed, so every prompt edit appended the new prompt after the old one in every existing thread (`System(v1), Human, AI, System(v2), …`), and `_messages_to_trim` never trims a `SystemMessage`, so both stayed for the thread's life. A patch (replace in place, remove extras) fixed that, but the design kept producing bugs: a graph built directly and never seeded ran as an **un-guided agent** (a test suite did this for weeks, with every prompt edit it "verified" having no effect), and every first turn of every thread paid a checkpoint read and write. The prompt is now **not stored at all**: the agent node prepends `manifest.system_prompt` to every call. An edit reaches every conversation on the next call with nothing to migrate; the prefix changes once, at the edit. A prompt persisted by an older build is ignored when the call is built (`is_legacy_prompt`; never shown to the model, left in the checkpoint). Tests: `tests/agent/graph/test_system_prompt_at_call_time.py`, including a real-Postgres two-process case in `test_durable_checkpoint.py`.
- **Use when:** more than one principal's traffic shares a deployment behind a provider that discounts a stable prefix.

### 20. Hybrid retrieval, rerank and cited answers
`search_docs`/`gather_context`/`retrieve_context` run `hybrid_search()` (`qdrant_store.py`): two Qdrant legs (dense via LiteLLM, BM25 sparse via in-process `fastembed`) fused server-side with RRF, then reranked by a cross-encoder that runs in the `ml-service` container (it was a measured concurrency bottleneck in-process). Every hit is numbered `[1]`, `[2]`, …; `check_output` scans the final answer for the markers it actually contains (`find_used_citations`) and writes only those to state, **never trusting the model's claim about what it cited**.
- **Two degradation layers:** sparse failure falls back to dense-only (`agent_retrieval_degraded_total{stage="sparse"}`); reranker failure returns the RRF order (`stage="rerank"`). The answer is still fully cited.
- Citations are computed by intersecting the answer's markers with what retrieval offered, so a hallucinated or forgotten marker resolves correctly.
- **Use when:** retrieval quality matters and an answer needs an audit trail.

### 21. Fixed-tool structured data access, plus MCP exposure
`query_employees` is a closed, typed Postgres query: `tenant` (from `SecurityCtx`), `department` (a closed enum) and `name_contains` are the only variables, every query is parameterized and always ANDs `WHERE tenant = %s`. There is no `execute(sql)` anywhere. Same principle as `add_note` (15), for reads: the access boundary lives in reviewable code, not a string the model writes.
- **MCP exposure is a separate trust boundary.** `mcp/server.py` wraps the same query for external clients. MCP has no `RunnableConfig`, so the identity is the launcher's (`MCP_TENANT` and `MCP_PRINCIPAL`, `app/mcp/identity.py`) and no tool takes either as an argument: they used to be, and an assistant connected to the server chose the tenant it read (pattern 78). The same fail-closed `Policy.permit` still runs. It does not authenticate whoever starts the process; a networked transport would have to take the identity from a verified credential on each connection.
- **Use when:** HR lookups, order status, inventory counts, wherever text-to-SQL would be tempting and exactly wrong.

### 22. Semantic cache
`check_semantic_cache` does a cosine-KNN lookup in Redis Stack scoped to tenant **and** principal (a cached answer can cite a principal's memories). A hit at or above `SEMANTIC_CACHE_SIMILARITY_THRESHOLD` (0.95) skips retrieval and the LLM and rejoins at `check_output`; `write_semantic_cache` stores confirmed-final turns that weren't hits. Every cache call degrades to a miss on failure: a latency optimization, never a correctness dependency (`app/retrieval/semantic_cache.py`).
- **Bug: it cached turns that acted.** After an approved write, a near-identical request got "Ticket #123 created" with no model call, no approval and no write, because a hit never reaches the gate. Found when a browser test that repeated a prompt got the cached answer instead of an approval prompt. The write node now skips any turn that called a non-`read_only` tool. Not covered: an answer quoting live read-only data can be stale until its TTL.
- **Bug: tag escaping.** RediSearch treats `-` as syntax, and the first fix (a list of known characters) missed `|`: principal `alice|bob` built a filter that also matched `bob`'s entries, an isolation break. `_escape_tag` now escapes every ASCII character that isn't a letter, digit or underscore: a rule, not a list. Tests: `test_semantic_cache_tag_escaping.py` and a real-Redis integration test.
- **Use when:** near-duplicate questions repeat across sessions.

### 23. Config-first multi-domain composition
`build_graph(manifest, domain)` keeps its topology and adapts to a domain through an `AgentManifest` (config: name, system prompt, exposed tools) and a `DomainPlugin` (code: tool implementations, capabilities, policy). There is no `if domain == "…"` in the graph, and no default domain: both arguments are required. Ecorp is one more entry in `app/domains/registry.py`, with the same shape as support, ops and sales (`app/domains/ecorp/`: `store.py` + `tools.py` + `domain.py`); the process default (`DEFAULT_DOMAIN`, `app/agent/runtime/core.py`) is a registry lookup.
- **Port-swapping, not parameterization:** `should_continue` needs a domain's capability map but LangGraph calls it with only `state`, so it is bound with `functools.partial(should_continue, tool_capabilities=…)` once per build (no default: a tool set, tier map and prompt only mean something relative to one domain).
- **The load-bearing test:** `tests/agent/test_manifest.py` builds a domain with a different `Policy` and one Ecorp-unknown tool, proves the unmodified gate treats it as `mutating` using that domain's map, and checks Ecorp's tools are absent from its `ToolNode`.
- **Bug (structural):** Ecorp's prompt and tools were welded into the generic graph, and `build_graph`, `should_continue`, `check_output`, `invalid_tool_call` and `make_llm` each defaulted to "Ecorp" when a caller named nothing. That default forced the deferred imports (graph → manifest → builtin → `run_subagent` → graph) and let any module that merely wanted "the graph" pick up one domain's tools. Ecorp moved out, the defaults went, and `graph/build.py` is the only module that imports every node; nothing a node imports imports it back. Tests bind the generic functions to Ecorp in one place (`tests/ecorp.py`).
- **Not done:** several domains from one process (see 47).

### 24. General-purpose ingestor with parent-child chunking
`ingest_text`/`ingest_file`/`ingest_url` and `make ingest` share one chunk → embed → `build_point` pipeline (`app/ingestion/`); every item carries its tenant and is refused without one.
- **Parent and child chunks:** `chunk_text` makes ~1200-character parents and ~600-character overlapping children. Only children are embedded; the payload carries `parent_text`, which the agent prefers. Overlap keeps a boundary from splitting the answering sentence; `_dedupe_by_parent` keeps the best hit per parent.
- **Idempotent ids:** `_content_point_id` derives each point id from `(tenant, source, chunk index, content)`, not `uuid4()`, so re-ingesting identical content upserts instead of duplicating.
- **SSRF guard:** `https` only, every resolved address must be globally routable (`ipaddress.is_global`, an IPv4-mapped IPv6 address judged as the IPv4), no redirects.
- **Bug:** the first guard was a deny-list and missed `100.64.0.0/10` (carrier-grade NAT, where cloud metadata services live). Separately, a blocking `getaddrinfo` in `async def` froze the event loop (a 0.5 s resolver stalled a heartbeat 0.51 s); async callers now use `assert_safe_url_async`.
- **Gap:** validate-then-fetch leaves a narrow DNS-rebinding race, and a hung resolver still holds a task and a thread.

### 25. Input moderation before any spend
`moderate_input` + `route_after_moderation` + `reject_moderation` (`app/core/moderation.py`) run right after `validate_input`'s checks, before the cache, compaction, retrieval or any LLM call. Two layers, cheapest first: (1) a regex screen for known injection/jailbreak phrasings plus a small denylist; (2) an ML classifier, Meta's Llama Prompt Guard 2 (22M) served by `ml-service`'s `/prompt-guard`, which catches paraphrases the patterns miss (`ML_INJECTION_THRESHOLD` 0.5; ~25–100 ms).
- A real hit at either layer fails **closed**; a failure of the check *itself* (a regex bug, `ml-service` unreachable) fails **open**, recorded as `outcome="error"`. The two are deliberately not conflated.
- **Bug:** compaction (an LLM call) ran right after `validate_input`, i.e. BEFORE moderation and the cache, so a moderated-out turn on a long thread and a cache-hit turn each still paid for a summarization, which broke the "before any spend" in the title. The order is now `validate_input → moderate_input → check_semantic_cache → (miss) compact_history → retrieve_context`. Test: `test_graph_integration.py::test_compaction_runs_only_after_moderation_and_a_cache_miss` (it reads the order of node starts off the event stream, which is what a router test can't see).
- **Gap:** the threshold is the model's natural boundary, not recalibrated on live traffic. Moderation screens words, not pixels (44).
- **Use when:** any input surface reachable by someone not fully trusted.

### 27. Clarification and follow-ups without forking the graph
`ask_clarification` is an ordinary `read_only` tool: its result becomes a `ToolMessage` and `SYSTEM_PROMPT` says to relay it verbatim. Follow-ups are a real node, `suggest_followups`, after `check_output`'s non-retry branch, making one small LLM call for 2–3 questions. It runs in parallel with the cache write-through (22): neither needs the other, so `done` waits for the slower of the two, not their sum.
- Follow-ups gate on `used_citations`: an answer with nothing derived (a refusal, a clarification, general knowledge) has none, so one signal suppresses all three cases. They are skipped on a cache hit, since an unconditional call would reintroduce an LLM call the hit exists to avoid.

### 28. Consuming a remote MCP tool catalog
`load_remote_tools(command, args, capability_overrides, env, cwd, pinned=, dependency=, cap_output=)` (`app/mcp/client.py`) connects to an MCP server over stdio and wraps each tool as a `StructuredTool` with the remote's JSON Schema passed through.
- **`capability_overrides` is the only source of truth.** MCP `ToolAnnotations` are self-reported hints; a tool not named defaults to `outward`, the same fail-closed default as an undeclared local tool, and the mandatory gate then applies with no special-casing.
- **Async only, over one shared connection per server and event loop** (`app/mcp/connection.py`, pattern 78). This used to read "sync and async, one fresh connection per call": the sync bridge went when its last caller did, and the per-call process spawn went with pattern 78.
- **What the remote says is input, not fact** (pattern 78): its catalog can be pinned by hash, its replies are rendered, scrubbed and bounded, and a call that may have reached it is never sent twice.

### 29. Built-in web UI
One self-contained HTML file (`app/api/static/index.html`, inline CSS/JS, no build step, no CDN) served at `GET /`, talking only to `POST /chat/stream/queued` and rendering the published SSE vocabulary (`token`, `tool_start`, `tool_end`, `citations`, `approval_required`, `error`, `done`). It uses `fetch()`, not `EventSource`, because the endpoint is POST and needs the identity headers `EventSource` can't send.
- **Bug it surfaced:** running the page against a live `uvicorn` raised `asyncio.InvalidStateError` from sync checkpointer calls (`update_state`/`get_state`) on the loop the async checkpointer was opened on. Three call sites needed `aupdate_state`/`aget_state` and a new `resumability_error_async`; the `MemorySaver` suite structurally couldn't catch it.

### 30. Canonical error envelope
One shape, `{code, message, details}`, from a single `ErrorCode` enum (`app/core/errors.py`) for every SSE `error` event and CLI error. It isn't applied to `ToolMessage` content, which is prose for the model.
- `internal_error_envelope(exc)` returns a fixed message plus `error_class`, never `str(exc)`; the text goes to the trace.
- **Bug:** both catch-alls (`runtime/stream.py::_run_graph_stream`, `agent_worker.py::process_request`) sent `str(exc)` to the caller, leaking internal hosts, SQL fragments or DSNs; the worker's had no `code` either. Three tests asserted the leak. They now assert a hostname-shaped sentinel never appears.
- **Gap:** the ingest worker's `process_job` has the same catch-all but mixes uploader-facing messages with unexpected failures, so it needs a per-exception decision; `CrawlFailed`/`IngestRefused` also embed a raw `{exc}`. Read from code, not reproduced.

### 31. DB connection pool
One lazy `psycopg_pool.ConnectionPool` singleton (`min_size=1`, `max_size=10`) behind `get_connection()` in `app/core/sql_store.py`, so call sites didn't change. `close_pool()` runs in the API lifespan shutdown; without it, background pool threads outlived the process (a reproduced bug).

### 32. Credential scrubbing on tool output
`app/core/scrubbing.py`, at the one chokepoint every tool result funnels through: static patterns for common credential shapes (API keys, AWS ids, `password=`/`token=` pairs, `user:password@`, JWTs) plus this deployment's own configured secret values, so an exact echo of a real secret is caught. Tool output specifically because it never passes through the model's input: a raw DB row can carry a credential straight into `ToolMessage.content`. Fails open (logged) on its own internal failure.

### 33. Memory deletion audit, age selector, retention at recall
`delete_memories(ctx, *, memory_id=None, older_than_days=None, target_principal=None)` requires **exactly one** selector, refusing an ambiguous request rather than narrowing to "everything". It counts matches with the same filter before deleting, and records every call, refused or not, via metrics and a log. Independently, `Policy.lower`'s memory filter ANDs a `DatetimeRange(gte=cutoff)` (`MEMORY_RETENTION_DAYS`, 365) onto every recall, so an unswept expired memory is invisible regardless.
- **Gap:** nothing calls `delete_memories` (no script, endpoint or make target); retention is enforced at read time only.

### 34. No-progress detection
`consecutive_repeat_count` scans backward from the latest `HumanMessage`; `_tool_call_fingerprint` normalizes a batch (tool name + sorted args) order-independently. `MAX_REPEATED_ACTIONS` (3) identical consecutive batches ends the turn, usually before `MAX_ITERATIONS`. It is a pure function of `state["messages"]`: the history already is the record, so there is no second counter to drift.

### 35. Cost ceiling
`MAX_COST_USD_PER_TURN` is a hard stop on cumulative per-turn dollars, distinct from the token cap because the same tokens cost differently by model tier. `agent()` computes incremental cost per call from LiteLLM's input/output/cached rates (`pricing.price_usage`), the same running total each usage event is priced from (`COST_GOVERNANCE.md`). It is checked **before** the next call: enforcement, not just recording.

### 36. Run cancellation
A third outcome for a paused interrupt, not a repurposed rejection: `route_after_approval` checks `cancelled` first and goes to `__end__`, never back to `agent` (`CANCEL_SENTINEL`, `runtime/stream.py::cancel_run`). A rejection lets the agent react; a cancel must stop the run.
- **Bug: a cancel outlived its run.** Nothing cleared `cancelled`, so a later pause on the same thread that the person *approved* went straight to `__end__`, leaving a dangling `tool_call`. `validate_input` now resets `cancelled`/`approved` each turn (a resume skips it). Test: `TestApprovalAfterAnEarlierCancel`.
- **Bug: an approved run couldn't be cancelled.** `astream_events_resume` took no `cancel_check`, so `POST /chat/cancel` between "approve" and "done" set a flag nothing polled. It now forwards it: a cancel before the worker picks the job up stops the turn before the approved write, and a later one stops it at the next event boundary (a running tool finishes; cancellation is cooperative).
- **Bug: a stream closed before its terminal event left a blank trace and no metrics.** The consumer can stop iterating mid-turn (the worker's `publish_result` raising, its task cancelled while publishing, Telegram or the CLI returning early). That lands in the consumer's frame, so `_run_graph_stream`'s `CancelledError` branch never ran; the generator was closed with `GeneratorExit`, which matched no `except`, and the trace kept its input with no output or level (indistinguishable in Langfuse from a turn still running) while the turn left no outcome behind. What holds now:
  - `GeneratorExit` finishes the trace (the partial answer, `[abandoned: ...]`, `WARNING`) and counts the turn as `agent_requests_total{outcome="abandoned"}` with its latency and the tokens already spent. It is not `cancelled`: nobody asked for a stop, and `agent_streaming_cancellation_total` stays the POST /chat/cancel counter. `process_request` always acks, so an abandoned turn is never retried: the person gets a generic error if the results stream still answers and nothing if it does not, and any write the turn made stays committed. The `TurnsAbandoned` alert (any occurrence, `warning`) is for that; a graceful worker shutdown awaits its in-flight turns, so a deploy does not raise it.
  - Every loop over these streams uses `contextlib.aclosing`: the three entry points over `_run_graph_stream`, and the consumers (the worker's `_publish_events`, the unattended wrapper, the Telegram and CLI renderers). A bare `async for` does not close a generator when it is left, so its cleanup ran a loop turn later, after the failure had been handled.
  - The trace is opened through `_turn_trace`, a plain (not async) context manager: a failure before the stream starts, or any exit the stream did not handle, still leaves the trace with an output. There is nothing to await on the way out; a Langfuse v2 trace has no `end()` and `update` is a queued call.
  - The one synthetic token a turn that never called the model streams (cache hit, `reject_*`) is yielded after the turn is recorded, because that part of the generator is covered by no `except` branch.
  - **The LangGraph iterator is deliberately left to the event loop's finalizer.** `graph.astream_events` runs the graph in a task of its own that stops only when that generator is closed, and `_run_graph_stream` does not close it (nor `_iterate_with_timeout` around it) inside its own `aclose()`. Measured against the real stack: the model produced no further output after the close and was stopped about a millisecond later. Closing it in the same `aclose()` was tried: the model's cleanup then ran before the terminal event rather than a loop turn after it, and in the one scenario measured (a model with a 1.5 s cleanup) the cancel event was not delayed. The gain is about a millisecond, and the effect on other node kinds (a tool slow to cancel) was not measured, so it was not kept. `TestClosingTheStreamStopsTheGraphRun` pins what matters: a consumer that leaves must not leave the run behind it still calling the model until it finishes on its own.
  - Tests: `TestAStreamClosedBeforeItsTerminalEventStillFinishesTheTrace`, `TestTheTurnTraceIsNeverLeftWithoutAnOutput`, and one per consumer.
- **Use when:** a human might change their mind mid-review.

### 37. Per-tool-call audit record
`MetricsCallbackHandler` correlates a `tool_called` start log with its success/failure log by LangChain's `run_id`. Args and results are logged as a truncated SHA-256 fingerprint, never raw content (pattern 14's rule extended to tools). "Which tool ran, with what, did it succeed" is answerable from logs at 3 a.m.

### 38. Resolved model recording
`model_resolver.resolve_model` asks LiteLLM's `GET /model/info` which concrete model serves an alias like `chat`, because neither the response body nor LangChain metadata carries it. Cached per process, degrades to `None`, recorded as `resolved_model` on each usage event. A silent gateway remap of the model behind an alias is otherwise invisible.
- **Bug:** the first version was a synchronous `httpx.get` on the event loop at the end of every turn. A slow LiteLLM froze every other turn and health check on that worker (a 0.5 s answer stalled a heartbeat for 0.56 s), and during an outage every turn paid a fresh 5 s timeout. It is now `async` and remembers a failure for `FAILED_LOOKUP_RETRY_SECONDS` (60) per alias. The regression test runs the real resolver against a deliberately slow local server with a heartbeat, which a mock can't do. `tests/conftest.py::mock_model_pricing` (autouse) keeps the default suite off the network.
- **Gap:** concurrent first lookups during an outage can each make one request before the failure is remembered.

### 39. Ungrounded-claims count
`count_ungrounded_claims` in `check_output` mirrors `find_used_citations` (20) but is computed **independently** from the same answer text, so a bug in one can't mask a bug in the other. It counts `[n]` markers matching no returned citation, which makes "did the model cite something real" a measurable, gateable property (40).

### 40. Eval statistical rigor
`scripts/eval.py` has two release gates. (1) Each case runs `EVAL_REPETITIONS` (5) times and passes only if `REPETITION_PASS_THRESHOLD` (80%) of repetitions pass: a stochastic system graded once is a coin flip. (2) A grounded-claims gate over the whole golden set (≥95% of citation markers real), computed from the runtime's own `used_citations`/`ungrounded_claims_count`, never a model's opinion of itself. Tokens, cost and grounding are summed across repetitions; latency is averaged. The thresholds are demo defaults; the structure generalizes.

### 41. Bounded history summarization
`compact_history` runs once per turn that reaches the model, after moderation and a semantic-cache miss and before retrieval (25), and summarizes exactly the discarded messages with one LLM call, folding the result into a cumulative `state["history_summary"]` that is never reset per turn. `agent()` puts the summary ahead of the question, like retrieved context, with a short "don't restate this" reminder behind it (a small model was seen regurgitating the injected summary); both ride on the question itself (79). A separate field, because `add_messages` has no insert-at-position.
- **Bug: the summary and the retrieved context landed after the question.** `compact_history` runs just before `retrieve_context` and what a node returns is appended, so its breadcrumb sits after the question, and the anchor was `len(messages) - 1`, which is the breadcrumb. The model was sent `question, summary, context` instead of `summary, context, question`, and the previous-turn lookup that enriches a vague follow-up (everything before the anchor) saw the current question as the previous turn. The anchor is now the question's own index. Test: `tests/agent/graph/test_compaction_anchor.py`. The breadcrumb still follows the question in the stored history (a node can only append), so a transcript replay shows it after the turn that triggered it.
- A cache hit skips it, so a long run of hits defers compaction to the next miss; that is the turn that needs the room, and a hit calls no model, so nothing is under context pressure meanwhile (`test_compaction_runs_only_after_moderation_and_a_cache_miss` pins it). The cost is on that miss: the span it summarizes has grown with every hit. If it outgrows the summarizing model's window the call fails, and compaction degrades as it always does, to the trim without a new summary (the breadcrumb says so). It takes hundreds of consecutive hits on one thread to get there, so it is accepted rather than capped.
- If the summary itself passes `MAX_HISTORY_SUMMARY_CHARS`, `route_after_compaction` routes to `context_window_exceeded`: a named dead end, not silent truncation. A summarization failure still applies the trim and skips updating the summary.

### 42. Telegram channel
`app/channels/telegram.py` long-polls `getUpdates`, resolves a stable `thread_id`/`SecurityCtx` per chat, and drives `astream_events_turn_unattended()`, collecting the stream into one reply. Long-polling needs no inbound port or public URL; production would use `setWebhook`.
- It reaches the public internet by design. `TELEGRAM_BOT_TOKEN` is empty by default and `run()` refuses to start without one.
- **Approvals reuse the auto-decline** (no approve/reject UX): a gated call is declined up to `UNATTENDED_MAX_DECLINE_ROUNDS` times, then the run is cancelled (pattern 8) with a real reply explaining why, never a silent write. `_send_message` sends nothing for an empty string, so `handle_message` substitutes `_NO_REPLY_FALLBACK` when a turn produced no text; before that, an empty turn read as the bot ignoring the user.
- **Bug: the long-poll `offset` was a local variable.** A restart reset it to 0 and Telegram redelivered every update it still remembered, each producing a duplicate turn and reply to a real user. It is now durable in Redis (`telegram:offset:{domain}`) and persisted **after** handling, so a mid-handling crash means one duplicate reply, never a dropped message.
- **Gap:** one thread is still shared across every user of a group chat (17).

### 43. Redis Streams queue between the API and agent workers
The only HTTP chat path. `POST /chat/stream/queued` publishes a turn to a Redis stream and relays events from a per-request results stream as SSE; it never runs the graph. `agent_worker.py` pulls through a consumer group, so each request reaches one worker and **N workers is the scaling story**. The SSE tier scales connections and the worker tier scales turns, independently.
- Results streams expire (`RESULTS_STREAM_TTL_SECONDS`, 300), so one turn's events can't reach another's response.
- **At-least-once:** a request is ACKed only after `process_request` finishes; a crashed worker's job is reclaimed (see Extending Further).
- **The per-thread lock belongs to the worker.** The Telegram and CLI paths drive `astream_events_turn_unattended`/`astream_events_turn` directly and take no Redis lock, so two messages into one conversation can overlap there. `_run_graph_stream` ends such a stream with `thread_busy` when work is still pending but nothing is waiting at an interrupt, where it used to read an interrupt that was not there and raise a raw `IndexError` from outside its handlers.
- **Bug:** redis-py's async `socket_timeout` defaults to 5 s, racing `XREAD`'s server-side `BLOCK`, so blocking reads timed out early. Fixed with `socket_timeout=None` plus a regression test.
- **An answerless pool must be visible.** With no worker running, each request got one error and nothing could page anyone. `read_results` now counts a first-event timeout (`agent_worker_unreachable_total{queue}`, alert `WorkerUnreachable`); a slow job that was picked up doesn't count. `test_alert_rules.py` checks every metric an alert names is defined, since an alert on an unrecorded metric is silent forever.
- **Not done:** a consumer-lag gauge, a readiness probe for consumers, a "no requests at all" rule. `promtool test rules` isn't wired in.
- **Use when:** SSE connection count and LLM concurrency need to scale on different axes.

### 44. Multimodal image questions
`_build_human_content(text, images)` returns a plain string (byte-identical to before) with no image and an OpenAI/LiteLLM content list with one or more. The app never fetches or decodes an image; the backing model does. Five call sites (`route_after_validation`, `moderate_input`, `check_semantic_cache`, `retrieve_context`, `write_semantic_cache`) assumed `.content` was a string, so `human_text`/`human_has_content` handle both, and an image-only question isn't rejected as empty.
- **Two scope boundaries:** moderation screens words, not pixels (an image-only message passes); retrieval and caching stay text-only. Verify vision **and** tool-calling support before assuming an alias swap is enough.

### 45. Skill packages with progressive disclosure
A catalog of `SKILL.md` packages (YAML frontmatter + markdown, one directory under `skills/`) discovered by meaning. `skill_search` hybrid-searches `{name, description}`; `use_skill(name)` loads one matched skill's full body. A turn that needs no skill pays for two tool schemas, not the size of the catalog (`app/agent/tools/skill_catalog.py`, `scripts/index_skills.py`).
- Reuses `hybrid_search` via an optional `collection` parameter; no forked fusion logic. **Disk is content truth, Qdrant only the index:** `use_skill` reads the body from an on-disk registry, so the index can't disagree with the file.
- Skills are a shared bundled catalog (no `SecurityCtx`, like `calculator`); a tenant-authored catalog is a larger extension not attempted. Domains scope skills with an optional `domains:` field.

### 46. Subagents: scoped, isolated delegation
`run_subagent(subagent_name, task)` starts a separate nested run: a fresh `build_subagent_graph()` with its own messages, prompt and budget. Skills add instructions to the same context; this doesn't. One tool with a closed enum built from `subagents/<name>/AGENT.md` (`app/agent/tools/subagent_catalog.py`).
- **Read-only tools only,** enforced at catalog-build time (others are dropped with a warning), so `run_subagent` is a plain `read_only` tool needing no gate special case. The nested graph runs synchronously on a throwaway `MemorySaver` inside one tool call; nobody could resume it hours later, so a write-capable subagent would mean a deadlocked gate or a bypass of pattern 15.
- **No recursion:** `run_subagent` is stripped from every subagent's tools.
- **Isolation:** fresh messages (its own prompt, the task as the only `HumanMessage`), inherited `SecurityCtx`, its own budget (`MAX_SUBAGENT_ITERATIONS=6`, `MAX_SUBAGENT_TOKENS_PER_RUN=4000`) via pattern 23's `functools.partial`, and `build_graph` with `SUBAGENT_PROFILE` (`build_subagent_graph()`), which leaves out 5 nodes (cache read/write, follow-ups, compaction and its dead end). Graphs are cached by `(domain, subagent_name)`.
- **Spend:** nested spend folds into the parent's budget through the `subagent_spend` reducer `concat_or_reset`, which concatenates and treats `None` as a reset (pattern 10's bug). Parent callbacks thread into the nested run, and its reasoning tokens never reach the client's stream.
- **Citations are the parent's alone:** a subagent's retrieval cites ITS sources, which mean nothing to the parent (its `[1]` is a different document), so its prompt says to use no `[n]` markers and the nested graph is built with `enforce_citations=False`: no tail "every sentence must end with its marker" reminder, and `check_output` neither flags nor inserts markers (every other check still applies). `run_subagent_impl` strips any marker that slips through (`strip_citation_markers`): a marker is `[n]` from 1, written after a clause, so an index like `items[0]` or `matrix[1][2]` and a literal `[0]` are left alone. It is still a heuristic: "pick element [2]" reads as a marker.
- **Bug:** the nested graph reused `agent` and `check_output` unchanged. The subagent got both "no bracket markers" (its prompt) and "every sentence must end with one" (the reminder), its own `check_output` inserted a `[1]` anyway, and that `check_output`'s `on_chain_end` reached the PARENT's stream: the client saw `retry`, then the subagent's text as a token, then `done`, so the subagent's words were shown as the answer. `_run_graph_stream` now ignores every `on_chain_end` tagged with `metadata.subagent_name`. Tests: `test_subagents.py::test_a_subagent_never_emits_citation_markers_or_events_into_the_parents_stream`, `test_streaming_terminal_events.py::test_a_nested_subagents_chain_ends_never_reach_the_parents_stream`.
- **Gap:** a new subagent needs a process restart.

### 47. Example domains as a load-bearing proof
`app/domains/support/`, `ops/` and `sales/` turn pattern 23's test-only proof into three runnable products on the same unmodified graph: a Tier-1 support copilot, an internal ops bot (reusing this repo's Prometheus thresholds) and a sales/CRM concierge. Each follows `core/sql_store.py`/`tools.py` conventions, plus a shared `app/domains/policy.py::ActionAllowlistPolicy`.
- **Runtime change kept minimal:** `init_graph_async` takes an optional `manifest`/`domain` (default `None`, today's exact behavior): which one domain this process boots as, decided at start from `AGENT_DOMAIN`. Not a multi-domain registry.
- **An unattended cron job can never approve itself.** `post_to_team_channel` is the first real `outward` tool and the gate has no bypass flag; auto-declining would silently make a digest never post. `scripts/ops_digest.py` and `followup_sweep.py` call the domain's `_impl` functions directly: a fixed pipeline that never enters the tool-calling loop.

### 48. Real-backend testing at every layer
`tests/containers.py` provides `ensure_*()` helpers (Postgres, Redis, Qdrant, Ollama, …) that start ephemeral testcontainers, so `tests/integration/` and `tests/live/` run in CI while a no-Docker `pytest -q` stays fast. `promptfoo/` and `garak/` target the same small Ollama model.
- **xdist:** shared containers need a fixed cache dir, not pytest's rotating `basetemp`; Ryuk is off and the controller tears down in `pytest_sessionfinish`. Concurrent first `init_graph_async()` calls hit an upstream `UniqueViolation` in `AsyncPostgresSaver.setup()`, so setup runs once, under a lock.
- **Gap: a local integration run stalled twice and has not been explained.** One test, `test_budget_policies_real_postgres.py::test_overrides_for_returns_only_this_tenants_rows_for_this_person`, never finished while the other 126 passed and the other workers sat idle (its worker's event loop idle, ten leftover Redis connections and a `CLOSE_WAIT` Postgres one, no blocked or idle-in-transaction session in Postgres). Eight runs before and four after were clean (99-123 s), CI has been green throughout, and the stall followed a killed or just-finished run both times, which is a correlation and not a cause. `faulthandler_timeout = 300` in `pyproject.toml` now makes any test that long dump every thread's Python stack, so the next stall names the line it waits on. Two stalls that looked like it were something else: a ~90 s wait at exit for the tracing flush (fixed, pattern 11) and the missing-summary look of a block-buffered log (run with `PYTHONUNBUFFERED=1 ... -v` to see per-test progress).
- **Tool calling is real:** `OPENAI_API_BASE` points at Ollama's OpenAI-compatible endpoint, confirmed by a raw `curl` to return structured `tool_calls` (LiteLLM's `ollama/` provider fakes them).
- **Tool gotchas:** promptfoo `file://` paths resolve from the config file, not the CWD; garak's `uri` must nest under `plugins:` or it is silently ignored.
- **Small local models make poor judges and targets.** A garak `dan` probe had 100% attack success on `qwen2.5:1.5b`, so `app/core/moderation.py` is the real defence. A local-judge redteam run reported 93% failed from malformed prompts and a grader inventing evidence, and deepeval's metrics couldn't separate good answers from bad ones either. So the judge is hosted (Gemini, Groq) and the target stays local.
- **Redteam findings, fixed:** a system-prompt leak under an "act as an auditor" framing, and a destructive script written for "wipe temp files" under urgency. Both got explicit prompt rules and were re-verified. Narrower paraphrase gaps remain: a ceiling of prompt-only defence on a small model.
- **deepeval** (`make deepeval`) checks faithfulness and relevancy to cited context, tool and argument correctness, and multi-turn role adherence and knowledge retention. In CI every case is `flaky=True`, so only a crash fails the job.
  - **Judge failover** (`tests/deepeval/fallback.py`): the primary, then other models on the same provider, then optional Plugsky and OpenRouter free models. It hands over on a rate limit, overload or timeout (and skips that model for 5 minutes, an hour for a daily limit), and on an unusable answer: invalid JSON or the wrong shape, for that one call, with no cooldown.

### 49. Per-domain requests streams
Every queued job once went onto one `agent:requests` stream, so the web UI reached only whichever domain a worker pool happened to run. `requests_stream_key(domain)` (`agent:requests:{domain}`) gives each domain its own stream and consumer group; `get_domain` reads `X-Domain` (default `ecorp`), so one API process reaches every domain with a running pool.
- The domain is inferred from which stream a message landed on, never carried in the payload: a resume or cancel must land where the original turn did, since the paused graph was compiled from that domain's manifest. An unknown `X-Domain` is a 422 rather than a publish nothing reads, which would hang silently.

### 67. Embedding roles and identity: a question is not a passage, and the same size is not the same space
Retrieval embeds two different things, a question and a stored passage, and one function (`embed_text`) used to serve both in seven places. The model in use, nomic-embed-text-v1.5, says on its card that its input "must include" `search_query: ` for a question and `search_document: ` for a passage; the app never sent either. Fixing that is not a prefix setting, because **changing what you embed changes the space**, and Qdrant cannot tell: two models of the same dimension (nomic and gte-modernbert-base are both 768-d) accept each other's queries and return confident nonsense with no error anywhere.
- **Two roles, old names deleted.** `embed_query` / `embed_document` / `embed_documents` replace `embed_text` / `embed_texts` (an `ImportError`, not a deprecation), and an AST test fails if any module under `app/` or `scripts/` calls the raw client around them. The semantic cache embeds with the query role on both sides, because it compares questions with questions. `EMBED_QUERY_PREFIX` / `EMBED_DOCUMENT_PREFIX` default to empty, so the text sent is byte-identical to before; whether a prefix helps is measured (`make model-eval`), not assumed.
- **Identity in the collection's name.** The identity is (the model the `embed` alias resolves to, the vector size, both prefixes, an operator label `EMBED_MODEL_REVISION`), hashed to 8 hex digits and written into the physical collection name (`docs-1a2b3c4d`). Every read and write goes through the alias `docs-live` and compares the suffix with the configured identity (`qdrant_store.check_identity`, cached `EMBED_IDENTITY_CACHE_SECONDS`). A mismatch is **refused**: a read degrades exactly like a retrieval outage (`retrieve_context` already absorbs one and counts it), a write fails, `agent_embedding_identity_total{outcome="mismatch"}` counts every refused call, `GET /health/ready` names the collection in `warnings` without turning the API unready, and the alert `EmbeddingIdentityMismatch` fires. The refusal comes before the query is embedded, so no spend is wasted. A data-subject delete and a count still work on a mismatched collection.
- **The swap is the point of the alias.** `scripts/reembed.py` (`make reembed COLLECTION_NAME=docs`) builds `docs-<new hash>` beside the live collection from the text each point already stores (`payload["text"]` is exactly what was embedded), keeping every id, the payload verbatim and the sparse vector as it was, verifies the ids and that a sample finds itself, then repoints the alias in ONE request. Verified against a real Qdrant (1.18.3): a concurrent search never fails across 40 swaps, a write through the alias lands in the target, and `scroll(with_vectors=True)` returns the named sparse vector. The old collection is never deleted by the script. A failure at any earlier step leaves the old one serving.
- **The answer cache follows the identity.** Its Redis index and key prefix carry the hash, so a new identity gets a fresh, correctly sized index and old entries are never read (they expire by TTL). A dimension change would otherwise have made the old index reject every vector.
- **`/v1/embeddings` on the ML service** speaks the OpenAI shape, so pointing the gateway's `embed` alias at an ONNX model served there is configuration only. The server never applies a prefix (the request cannot say whether a text is a question or a passage); `/v1/models` echoes what each model expects as documentation. Checked against the official `openai` SDK (whose default really is `encoding_format=base64`) and the LangChain client this app uses. Measured: the container idles at 781 MiB with bge-small enabled (574 MiB before) and reaches 1,069 MiB under 100 concurrent requests, against a 2 GiB production limit.
- **Bug found by the tests while building it:** the identity check reaches Qdrant *before* the query is embedded, so a hermetic test that used to fail fast at the embedding call began opening a real connection (the client's constructor probes the server; a developer with Qdrant running would have a unit test talk to it). An autouse guard now refuses a real Qdrant connection in the default suite (Constitution VII). And `make reembed COLLECTION=skills` would have exported `COLLECTION=skills` to the script, which is also the Settings variable naming the main collection; the variable is `COLLECTION_NAME`.
- **Gap: a pre-existing collection cannot be verified.** One from before this existed is a physical collection named exactly `docs` with no alias. It is *adopted* (an alias is created, nothing is moved), the configured identity is trusted, a warning and `outcome="adopted"` say so, and the first `make reembed` replaces it with a verifiable one. An operator who changes the model *and* upgrades in the same step defeats this.
- **Gap: the resolver is the weak link.** `model_resolver` asks LiteLLM `/model/info` which model an alias is. Where nothing answers (a deployment pointing straight at an OpenAI-compatible server, which is how the live test tier runs), the alias name stands in for the model and the check is counted `unverified`: stable, but it cannot see the same name re-pulled to different weights, which is what `EMBED_MODEL_REVISION` is for.
- **Gap: writes during a re-embed are not supported.** They are detected, not lost: the run re-reads the source before swapping and stops (exit 4) if it changed. The milliseconds between that read and the alias request remain.
- **Gap: the default stays the default.** The app's `embed` is still nomic through Ollama; prefixes are off; the ML service serves bge-small but nothing points at it. Whether to switch is a decision for the evaluation harness, with a re-embed afterwards.

### 68. A model-routing seam that can only advise, from two signals and in three tiers
A small local model answers most questions well, and a few need a stronger one. The seam lets an operator attach up to two more OpenAI-compatible models behind gateway aliases (`chat-medium`, `chat-strong`) and have the router choose a tier per turn from two signals: a few rules over the message (`app/core/routing_policy.py`: length, code, several questions, reasoning words) and a label from the ML service's `route-topics` label set (`app/core/classification.py`; specs/015). Each signal names the lowest tier it will accept and the tier is `min(ceiling, max(rules, label))`, lowered to the highest tier that is configured and priced. It is built so that choosing a model is all the router can ever do, and so that an operator reads what it would have spent (`ROUTER_MODE=shadow`) before it spends anything. The first version (spec 014) had one strong alias and one signal, a trained head; the head was withdrawn when the first real run showed the labels could not support one (ENGINEERING_PATTERNS.md pattern 69).
- **The risk it is built around: a router that is a second authority.** If the thing choosing the model could also affect which tools a turn may call, whether a write needs approval, whose data is read, or whether a write repeats, it would sit beside the three non-negotiable rules (tenant isolation, mandatory approval, exactly-once side effects) and every future change to it would need the same scrutiny as they do. So `route_model` writes `State.model_route` (`"local"`, `"medium"` or `"strong"`) and nothing else, a test pins that the returned dict has that one key, and another runs the same mutating `add_note` turn under all three tiers and asserts the same approval pause, the same tenant-scoped payload and the same `idempotent()` key.
- **Where it sits.** After moderation, the semantic cache and compaction, before retrieval: never reached for a refused input, a cache hit, or a resumed turn (a resume re-enters inside `human_approval`, so the decision is made once per turn and survives the pause), and not in a nested subagent run. `validate_input` resets the route each new turn; without that reset a refused turn would carry the previous turn's `strong` into its accounting (a mutant that removes the reset is caught by a test that follows a strong turn with a refused one).
- **What it sends.** Exactly one `choice` question named `route-topics` (its instructions and the eight labels with a sentence each, `routing_policy.LABEL_DESCRIPTIONS`) and `state`: the first 2,000 characters of the user's current message, to `POST /v1/decide` on the ML service (the System One / Jev request shape, spec 016), under `ROUTER_TIMEOUT_SECONDS` enforced as a hard wall-clock bound around the whole exchange (httpx's own timeouts are per phase, so a peer that trickles bytes would outlast them). Not the tenant, principal, history or retrieved text; a test pins the body. The answer is validated, not trusted: a non-200, a wrong shape, an answer to a question that was not asked, a choice that is not one of the options, a number out of range, or an unknown `x_served_by` is an error, and a 503 `model_unavailable` is its own outcome because an operator has to tell "the classifier is broken" from "the classifier has nothing to say yet". **A missing label never cancels the other signal:** the rules decide, and the outcome (`label_none`, `label_timeout`, `label_error`, `label_unknown`) says why; `ModelRouterLabelUnavailable` fires when more than half of the routed turns for 15 minutes had to.
- **Three modes, one code path.** `ROUTER_MODE=off` does nothing (no work, no call). `shadow` makes the same decision `on` would, counts it (`agent_model_route_tier_total{tier,mode,decided_by}`: the tier it WOULD have used) and logs it, and the turn runs on the local model; a graph test runs the same turn under `off` and `shadow` and asserts the same gateway keywords, ledger rows and answer. `on` writes the tier. There is no `if shadow` inside the decision, only at the one place that picks what to write to `State`, so shadow cannot drift from the thing it rehearses.
- **The decision is a pure function the harness runs too.** `routing_policy.decide` imports nothing from the app, so the graph node and the evaluation (`run(backend=...)`) execute the same code; a router evaluated by a copy of its logic is evaluated by something else. A sweep over every combination of rule tier, label, ceiling and configured tiers checks it against an independent rank-arithmetic oracle and that it never returns a tier that does not exist. **The label table and the rules are policy, written by a person, and nothing measured says they predict where a stronger model answers better** (see the gap below).
- **The trained head is gone (spec 016).** Spec 014 served a head, `sigmoid(w . x + b)` over the prompt's embedding, from `POST /classify` once a person marked it `"accepted": true`; none was ever accepted, the trainer was removed in #179 once the first real run showed the labels could not support any router, and since spec 015 the app did not ask for one. The endpoint, its head files, its metrics and its alert were deleted. Two lessons it taught stay true of the label sets that replaced it: **an artefact is bound to the model revision the Hub cache really holds** (read from the downloaded file's `snapshots/<sha>/` path, not the one the registry asked for; bge-small and MiniLM are both 384-d but different spaces, and a wrong one returns confident nonsense with no error), which is why a label set stores example TEXT and rebuilds its index when the revision changes; and **an unreadable directory is a refusal, not a crash** (`Path.exists()` raises `PermissionError` on Python 3.13 when the directory is not searchable by the service's user; found by CI, where a container running as uid 1000 mounted a `0700` temp directory, and Docker Desktop on macOS ignores bind-mount permissions so no local run could have shown it). `read_labelsets` guards it and a test uses a real unreadable directory.
- **Failover is the service's, the degrade is the app's.** `/v1/decide` tries the primary (`bge-small-en-v1.5`), then the fallback (`all-MiniLM-L6-v2`; with its own index and its own cutoff, because the two models place sentences on different scales), each under `ML_CLASSIFY_DEADLINE_MS`; a model that raises goes to the registry's `failed` state and is reloaded by the supervisor, a model that is only slow is skipped for that request and stays `ready`, and with neither usable `/v1/decide` answers 503 `model_unavailable`, never a 500. `MlServiceModelDown` alerts after 5 minutes when either model is out; there is no alert for "answering from the fallback" (the head-era `RouterClassifierOnFallback` went with its gauge).
- **A routed model failing is handled in `agent()`, not by the gateway.** If a medium or strong call raises a connection error, a timeout or any gateway 5xx, that one call is repeated on the local alias, `agent_model_route_total{outcome="routed_unreachable_fell_back"}` is incremented (`ModelRoutedTierFailing`), and the next call in the turn tries the routed alias again. A gateway `fallbacks` entry would have been simpler and wrong: the usage event would name the routed alias for an answer the local model gave, so the ledger, the per-turn dollar ceiling and the credit charge would price a model that did not serve. The gateway's budget stop (`budget_exceeded`) is deliberately not caught, even as a 5xx, and neither is any 4xx. **Found by a real run, not by reading:** the first version listed 502/503/504, and a real LiteLLM in front of an unreachable upstream answers HTTP **500** (`litellm.APIConnectionError: … Cannot connect to host`), as it does for an upstream that is up but lacks the model, so that list would never have fired for the failure it exists for; it is now any 5xx. Neither `chat-medium` nor `chat-strong` has a `fallbacks` entry in either LiteLLM config, and a test fails if one is added.
- **Priced as the alias that served.** A routed turn passes the alias as both the per-call `model=` and `model_alias` (`metered_invoke(..., invoke_model=...)`, which adds nothing to the call when it is `None`). A real `ChatOpenAI` over `httpx.MockTransport` proves the request body's `model` is the routed alias for a routed turn and `chat` otherwise, with the tools still bound. A routed alias with no price under `UNPRICED_MODEL_POLICY=block` makes `agent()` refuse the turn, so the router steps down one tier at a time until it reaches one that is priced (`tier_unpriced`, and `local` is the app's own default and is never price-checked): the router can never be the reason a turn is refused. A tier nobody configured steps down the same way, so the result is never dearer than the operator allowed.
- **The dev stand-ins are local.** `chat-medium` and `chat-strong` are always present in both gateway configs, so the proxy starts and the aliases resolve; in dev `chat-medium` is the same 7B as `chat` and `chat-strong` a 14B (`make pull-strong-model`, about 9 GB, only needed once the router is on), in production they default to the `chat` values until an operator sets `LLM_MEDIUM_*` / `LLM_STRONG_*`. The app switch is separate and off (`ROUTER_MODE=off`, both aliases empty); `shadow` or `on` without an alias, two tiers sharing an alias, or a leftover `ROUTER_ENABLED=true` (the old switch, refused rather than silently ignored) refuses to start. The constitution allows two such aliases (1.3.0).
- **Guard for the test suite.** Every hermetic test sees "no answer" from the label call (`mock_classification`, the eighth autouse guard); a meta-test shows a full turn with the router on makes no `/v1/decide` request, and that with the real function put back it would.
- **Not built (disclosed): per-tenant control.** The switch is operator-wide. A tenant cannot opt out of, or into, routing; for a deployment where a tenant's data may not leave for a hosted model this is a gap, and the mitigation today is to keep `chat-medium` and `chat-strong` pointing at models that are acceptable for every tenant (or `ROUTER_MAX_TIER=local`).
- **Gap: a routed endpoint that accepts the connection and never answers** is not a failure the fallback can see: the call just does not return, and the turn ends at the turn's own wall-clock bound (`REQUEST_TIMEOUT_SECONDS`, 60 s by default) exactly as it would if the local model hung. Only a failure the gateway reports promptly (a refused connection, a 5xx) degrades promptly. A client-side timeout on the routed call alone would close this and was not added: it would be a second timeout to tune beside the gateway's.
- **Gap: the label table and the rules are policy, not a measurement.** Nothing here says routing improves an answer. The only routing outcomes that exist (123 prompts, qwen2.5:3b against 7b, judged by the 7B) could not tell a perfect router from a random one, and they predate the 7B/14B pair the dev aliases are now. The label set's own quality is measured (`make model-eval KIND=classifier CANDIDATE=labelset-bge-small-en-v1.5 DATASET=route-topics`: in-scope accuracy 0.83 on bge-small, about half of the "none of these" sentences still get a label, and on this repository's own prompts the label signal first sent 11% of ordinary lookups up a tier and 5% after one round of added examples) and so is the spread of tiers a deployment would see (`shadow`), but whether a stronger model answers the escalated turns better is the open question, and the way to answer it is a labelling run with a judge that is not the strong model.
- **Gap: the conversation is not seen.** The label and the rules read the current message only, so "yes, do it" has no topic and falls to the rules, and a long thread whose last message is short routes on that message.
- **Gap: a margin would catch wrong labels a cutoff cannot** (median margin 0.010 for wrong nearest labels against 0.068 for right ones on bge-small) but is on a different scale per model; it is recorded in `specs/015.../research.md` and not used until there is a larger dev set to calibrate two numbers on.

### 70. A check judges what was said, not where a marker or a pleasantry landed
Langfuse trace `1e46b2c8` (2026-10-21): "what is working hours of ecorp ?" got a correct, cited answer three times and the user was told "I described what I'd do instead of actually doing it". Two heuristics, stacked, rejected a good answer, and each retry made the next attempt worse.
- **Bug 1: a marker written after the full stop was judged against the next sentence.** `... are free. [1]\n\nWould you like ...?` split into `...are free.` and `[1] Would you like ...?`, and the second shares nothing with the source, so a correct citation was `misattributed`. `graph/messages.py::sentence_spans` / `split_sentences` (shared by every citation check) keep a marker that follows the full stop on the same line with the sentence it follows. A marker that starts a new line still leads the next sentence, on purpose: it is ambiguous, and a marker put on the wrong sentence stays visible there (the trace's second answer is a true `misattributed`, and is still reported as one).
- **Bug 2: a closing question rejected a complete answer, and was only sometimes seen.** The permission cue had a 40-character window: "...or should I proceed differently?" was caught, "...or should I proceed with finding the general business operating hours?" was not, and "Is there anything else you would like assistance with?" never was. When it was caught the answer went back for a rewrite that cannot work (the system prompt forbids the question twice, qwen2.5:3b writes it anyway), and on exhaustion a correct answer was replaced by a fallback that blamed the model for narrating an action it never narrated.
- **A repair, not a verdict.** `output_guardrails.strip_closing_offer` cuts the offer, and the short sentences that continue it ("If so, we can ..."), off the END of an answer, the way a missing marker is already inserted (`insert_missing_citation_markers`). It cuts only when what is left is itself an answer: at least four distinctive words, not a lead-in ending in ":" or a question, no unclosed code fence, no narrated tool use. A reply that is only an offer, or that says "I can look that up for you. Would you like to know more?", is unchanged and is still `deferred`, so that fallback text is true again. A question with more answer after it is never touched. `CheckContext.body` carries the cut text; `check_output` stores and streams it (`on_chain_end` of `check_output` re-emits a replaced message), and the semantic cache stores it.
- **Leak and fabrication still see everything.** They are judged on `content`, what the model wrote, so a recitation of the system prompt placed inside the offer is cut from the reply and still flagged (`test_stripping_the_offer_never_hides_a_prompt_leak_inside_it`).
- **Metric:** `agent_closing_offer_stripped_total`. A steady rate means the model is ignoring the prompt, not that the graph is failing.
- **Tests:** `tests/agent/graph/test_closing_offer_and_marker_placement.py`. 11 of its 29 fail on the old code (shimmed to the old behaviour); the rest are the cases that must NOT be cut.
- **Gap: the cut is English and a closed list.** The cues are `would you like / do you want / shall I / want me to / should I` ending in "?", and the continuing sentences open with `if so / if yes / if you'd like / if you want / let me know`. "Anything else I can help with?" is not a permission question and is left alone, as before. A model answering in another language is not repaired.
- **Gap: four distinctive words is a threshold, not a measurement.** An answer that is correct but very short ("It is 9.") followed by an offer is not cut and is rejected as before.

### 71. A refusal is final: not retried, not an error, and not left in the thread
Langfuse traces `b376e4d8` and `2c8e76a4` (2026-10-21): LiteLLM's "Denied Financial Advice" guardrail (created in its admin UI; no committed config defines it) refused "should i invest in testla stock ?" with an HTTP 400. Three things in the app turned one policy decision into a dead session.
- **Bug 1: every 4xx was retried.** LangGraph 0.2.76's `default_retry_on` excludes only `httpx.HTTPStatusError` 4xx (checked in the installed source), and the OpenAI SDK's `BadRequestError`, `AuthenticationError`, `NotFoundError` and `UnprocessableEntityError` are not that class, so `AGENT_RETRY_POLICY` made three attempts about five seconds apart. `gateway.is_permanent_client_error` (a 4xx other than 408, 409, 425 or 429) is now refused a retry, next to the budget stop's carve-out; a 429, a 5xx and a dropped connection are retried as before. The comment above the policy said "connection error, 5xx" and the code did more.
- **Bug 2: a policy decision reached the person as an anonymous `internal` error.** `gateway.content_block` recognises the refusal by the structured fields LiteLLM sets (`provider_specific_fields.guardrail_name`, `guardrail_mode`), else by the "Content blocked" message, and never by the status alone (a malformed request is also a 400). The `agent` node turns it into the turn's answer, "I can't help with that request." (the text `reject_moderation` uses; the rule, the matched phrase and the guardrail's name stay in the gateway's log), marked with `GATEWAY_REFUSAL_KEY`. `should_continue` sends a marked message to `no_answer`, which ends the turn with no retry, no follow-up suggestions (more model calls on the same refused history) and no semantic-cache write (the refusal would be stored as the answer to this question). No new node or edge, no `STATE_SCHEMA_VERSION` bump. Any other 400 (context too long, a bad request) still raises and is reported as `internal`: those are bugs.
- **Bug 3: the refused message stayed in the thread, and the gateway scans the whole list.** "hey" was refused for an earlier message's "stock + should i", and so was every turn after it. When the guardrail refused the REQUEST (`pre_call`), this turn's message is replaced in the stored thread by a placeholder (same id, which is how the reducer replaces instead of appending); a `post_call` block refused what the model wrote, so the question stays.
- **Metrics:** `agent_gateway_content_blocked_total{mode}`, with no alert: it is the operator's own policy working. `agent_unparsed_completion_total` counts the dropped-call case below, whose cause pattern 73 fixed for the dev chat model.
- **Tests:** `tests/agent/graph/test_gateway_refusal.py` (38; 23 fail on the old code), including the real SDK exception from a `MockTransport` response and the two-turn session that used to end at the first turn. `tests/core/test_compose_worker_healthcheck.py`: every worker role sets `healthcheck: *worker-healthcheck`. Found in the same session: the app image's `HEALTHCHECK` probes the API's port, compose lets a service inherit it, and the workers only overrode `command`, so all of them showed `unhealthy` for as long as they ran. It is disabled for them, not replaced: a worker pool that picks up nothing is what the `WorkerUnreachable` alert already watches.
- **Gap: a thread whose OLDER messages already match a guardrail stays refused.** The refusal does not say which message matched, so only the message just sent is replaced. A guardrail added after a conversation was written (the session in the traces was already like this) needs a new session.
- **Gap: nothing probes a worker's liveness at the container level.** The application-level alert covers "picks up nothing"; a worker that is up but stuck on one long turn is not distinguished from a busy one.

### 73. The chat model is chosen by what it does with this app's tool calls, and a sampling option can break them
Langfuse trace `1e46b2c8` (2026-10-21): "remember this" never ran `remember`, and pattern 71 left that open ("a model or serving decision"). It was both, and it was measurable.
- **The tokens Ollama discards were finally seen.** The model's template was rendered by hand and run raw (`/api/generate`, parser bypassed; the generated token counts matched the real chat calls, 23 and 19, though my prompt was longer than Ollama's, so that is evidence the generations are the same, not proof). The dropped replies are not valid calls: `{"name": "remember", "arguments": {"content: "my favorite color is blue"}}` and `{"name": "query_employees", "arguments": {"department: "Engineering"}}`, each missing the closing quote after its key. A well-formed call (`"content": "abc"`) parsed. Ollama discards a call whose JSON it cannot read, with no error.
- **Two causes, not one.** (1) The gateway set `repeat_penalty: 1.3` (Ollama's default is 1.1), raised once to stop a repetition loop. The penalty falls on tokens already in the context, and a tool call's `":` and quote tokens are in it dozens of times, so the model drifts off the JSON. (2) `qwen2.5:3b` is unreliable at it even with the penalty gone. `scripts/toolcall_probe.py` (22 labelled prompts, the Ecorp domain's real tool schemas and system prompt, temperature 0, the options the alias sets) gives tool-needing prompts answered correctly, out of 19:

  |---|---|---|---|
  | 1.3 (the old setting) | 8 (8 replies dropped) | 11 (8 came out as text fragments) | 5 |
  | 1.1 (Ollama's default) | 13 (5 dropped) | **19** | 12 |
  | 1.0 | 15 (2 dropped) | **19** | 12 |

- **The 3b cannot be rescued by a setting.** Lowering the penalty to save its tool calls brings the loop back: at 1.1 it ran to the 2048-token cap on "list every kind of database index" with 44% of its 6-word runs repeated. The 7b ended all four open-ended prompts by itself at 1.3, 1.1 and 1.0 (at most 10% repeats). So the change is both: **`chat` and `chat-backup` are `qwen2.5:7b` at `repeat_penalty: 1.1`** (the context and output bounds are unchanged: 32000 and 2048, and the 7b has the same 32768 trained maximum).
- **Alternatives measured.** `llama3.1:8b` answered 19/19 tool-needing prompts at 1.1 and at 1.0 but called a tool on all three prompts that need none ("hi", "thanks!", "what is the capital of France?"), where the 7b answered 3/3 plainly. The `qwen3` family was not tried: its thinking mode, and how the gateway would switch it off, is a separate integration question.
- **No regression where it was checked.** `make promptfoo` (support 4/4, ops 3/3, sales 3/3) passes on the 7b as it did on the 3b. `make eval` (golden set, 5 repetitions, through a second gateway running the new config) passes the same 3 of 4 cases before and after, with the same two failures on both sides (see below). What it costs: the golden set's average latency per case went from 0.86 s to 1.92 s; generation is about 40 tokens/s against about 60; a cold load is 3.2 s (the turn timeout is 60 s); the loaded 7b at the 32000 context is 5.5 GB.

It is **not pulled or run** here: only that the alias resolves is checked. It matters only once the router is switched on, which is off by default.
- **The check that was missing is now a command.** `make probe-tools` (`scripts/toolcall_probe.py`) reads the model and options of an alias from the dev config and runs both halves of the trade-off: the tool-call probe, and four open-ended prompts that must not loop (a capped reply with at least a quarter of its 6-word runs repeated). It exits 1 on any dropped call, any loop, or under 90% of tool-needing prompts. `tests/core/test_gateway_chat_sampling.py` is the hermetic guard on the two known ways back: a `repeat_penalty` above 1.1 on a tool-bound alias, and a model that missed tool calls on the probe (the 3b and 1.5b) behind one; 5 of its 8 tests fail on the old config. `tests/scripts/test_toolcall_probe.py` pins the classification against the real reply shapes.
- **Gap: 22 prompts on one machine is a screen, not a ranking.** It separates a broken setup from a working one; temperature 0 makes one run per prompt the whole distribution, but a different prompt set, Ollama build or quantization may move the numbers. It says nothing about answer quality; `make eval`, `make promptfoo` and the deepeval tier do.
- **Gap: CI still runs the small models.** The `test-live`, `promptfoo`, `deepeval` and red-team jobs use `qwen2.5:3b` or `1.5b` on CPU runners that cannot afford a 7b, through Ollama directly, so with no gateway and (assuming Ollama's documented default of 1.1, which was measured here only as an explicit 1.1) at that penalty. By the table above they drop or miss tool calls there too (the 3b 13/19, the 1.5b 12/19). That is a plausible cause of the live tests that need the small model to chain tool calls being flaky or red; it has **not** been tested. Their model is a separate decision (a larger CI runner, or a smaller fix).
- **Gap: the `vision` alias keeps `repeat_penalty: 1.3`.** Its models cannot use tools at all (see its entry), so the cause here does not apply; it was not re-tuned.
- **Found while measuring, not fixed:** `make eval` fails two checks on both the old and the new model. The retrieval case expects a `search_docs` call, but `retrieve_context` pre-fetches the context so the model answers without one; and the grounded-claims gate reads 50% (threshold 95%) because a general-knowledge answer cites an invented `[1]`. ### 74. Strict tool schemas are a form the model is sent, not the contract the app enforces, and they are off until a provider enforces them
OpenAI-style strict function calling (`"strict": true`) makes a provider that supports it decode a tool call against the schema, so an enum can only take a real value and no undeclared field can appear. `TOOL_CALLS_STRICT` (`app/core/config.py`) makes `make_llm` send every tool that way, through `strict_tool_schema` (`app/core/tool_schema.py`). It exists, and is **off**, for the reasons below.
- **LangChain's `strict=True` does not make a tool strict-valid.** It closes objects (`additionalProperties: false`) and sets the flag, nothing else. Converting all 32 tools of the four domains found six whose optional arguments were not in `required` (`create_ticket`, `list_pending_followups`, `list_recent_incidents`, `log_incident`, `query_employees`, `search_docs`), three of them (`list_pending_followups`, `list_recent_incidents`, `query_employees`) with no `required` key at all, which LangChain's helper then leaves unclosed. `strict_tool_schema` lists every property as required (an optional one stays optional by being nullable), closes every object, and turns a non-null `default` and a string length bound into a sentence in the property's description. The result is a fixed point of the installed `openai` SDK's own converter (`_ensure_strict_json_schema` changes nothing), and `tests/core/test_tool_schema.py` checks every tool of every domain on each run, so a tool added later with the same shape fails there and not at a provider's 400.
- **The tools declare "required" themselves, and a call may still leave a nullable argument out (`ToolArgs`, `app/core/tool_schema.py`).** `search_docs`, `query_employees`, `log_incident`, `list_recent_incidents` and `list_pending_followups` declare each filter `T | None = Field(...)` (required, nullable, "Pass null for ..."); `create_ticket`'s `priority` is required too, with `normal` as its `omitted_defaults` (a closed choice has no null). `tests/core/test_tool_schema.py` fails any tool that has an optional argument, so the next one is written this way. `strict_tool_schema` still moves defaults and length bounds out of the copy a provider sees, and `args_schema` keeps enforcing the real bounds.
- **Why a call that leaves one out is accepted, measured.** The first version refused it. `qwen2.5:7b` does not follow "required": it sends only the arguments it needs (`{'query': 'support hours', 'topic': 'company'}`), so 7 of the probe's 19 tool prompts failed validation, a retry round trip each (7b 19 → 12, 3b 13 → 10, 1.5b 12 → 9). Prompting did not fix it reliably. For the 7b, a system-prompt rule with example calls gave 15, forceful argument descriptions 15, a worked example in each tool description 12, and everything stacked 18; the same texts took the 3b down to 7-8 and the 1.5b down to 7 in some variants, and combining two texts that helped alone gave a worse score than one of them (a 19-prompt screen this sensitive to wording is not a fix). So a missing nullable argument is filled with `None` before validation: 7b 19/19, 3b 14, 1.5b 9. LangChain hands the function only the keys the call contained (`BaseTool._parse_input` keeps `k in tool_input`, read in the installed `langchain_core`), so each function also keeps `= None` in its signature, and a test per tool fails when one is missing (checked by removing one).
- **`scripts/toolcall_probe.py --strict` and the default judge replies by what the app enforces:** a nullable argument may be left out, a value outside an enum or a plain required one may not.
- **Why it is off: measured on this stack, it does nothing good and something bad.** LiteLLM's `ollama_chat` hands `tools` to Ollama untouched (read in the gateway container: no `strict` handling in `llms/ollama/chat/transformation.py`) and nothing in the probe below suggests Ollama acts on it (its source was not read). With the probe (22 prompts, 19 needing a tool, `make probe-tools ARGS="--no-loops [--strict|--no-strict]"`, temperature 0), without and with the strict form, measured while the six tools were still optional:

  | model | without | with |
  |---|---|---|
  | `qwen2.5:7b` (`chat`) | 19 | 19 (twice each) |
  | `qwen2.5:3b` | 13 | 13 (5 dropped and 1 wrong tool without, 6 dropped with, not the same prompts: noise on a model pattern 73 already rejects) |
  | `qwen2.5:1.5b` | 12 | **9** |

  The smallest model, which CI's live jobs use, answers more of the prompts with prose when every argument is required. With the tools now required the strict form still costs a little on top (7b 18, 3b 12, 1.5b 8, against 19, 14 and 9 without it). So turn it on together with the change that points `chat` at a provider that enforces it, and run the probe before and after.
- **`extra="forbid"` was not added to the argument models.** `strict_tool_schema` does not need it, and it would turn an extra argument a small model invents, which is ignored today and is harmless because identity comes from `ctx` (rule 4 of `.claude/rules/side-effect-tools.md`), into a failed call. It is a separate decision.
- **Gap: `qwen2.5:1.5b` pays for the tools being required (12 → 9).** Given two required arguments it merges their names into one key (`{'department name_contains': 'Engineering'}`), two of the three prompts it lost. That is the model's limit, not something a validator can repair, and CI's small-model jobs are on this side; they were already below pattern 73's bar.
- **Gap: never run against a strict provider.** None is configured here. What is known is from the SDK's converter and the gateway's source. The length-bound and `default` rewrites follow OpenAI's list of supported keywords as remembered, not as run; if a provider accepts them, the cost is a hint the model no longer gets, not a wrong call.
- **Gap: parallel tool calls.** As remembered, OpenAI documents that strict output is not guaranteed when the model makes parallel calls, and this graph supports them (`runtime-reliability.md`). Nothing sets `parallel_tool_calls` for it. Unchecked, and to settle before the flag is turned on for such a provider.
- **Gap: the probe covers the Ecorp domain's tools** (the support, ops and sales schemas are checked for validity but not for how a model uses them), `make eval` and `make promptfoo` were not run (the default sends the same schemas as before), and CI's small models are on the `without` side of the table.

### 78. A published MCP server acts for whoever launched it, and a remote server is untrusted input
`app/mcp/` is MCP in both directions, and the same rule runs through both: the other side of the pipe is not where a trust decision gets made.
- **Bug: the model chose the tenant.** `query_employees` took `tenant` and `principal` as tool arguments, the operations tools took `principal`, because MCP has no `RunnableConfig` for a context. A desktop assistant connected to the server fills those in itself, so a page it had read or a message it was sent could name another tenant and get that tenant's rows. The repo's own rule for every other tool is to take identity from `ctx`, never from an argument the model can set. The identity is now bound when the process starts (`MCP_TENANT`, `MCP_PRINCIPAL`, `app/mcp/identity.py`; a client's `env` block, or `.env` for `make mcp-serve`), no tool exposes either name, a call that still sends them is ignored (tested), a server started without one exits before serving and says so on stderr, and a tool called without one refuses. Tests spawn the real server and check the schema on the wire and that stdout, the protocol channel, stays empty.
- **Read-only tools say so, and every call leaves one line.** Each published tool declares `readOnlyHint`, `idempotentHint` and a closed world, which is how a client decides what needs a confirmation. A stdio server is a process nothing scrapes, so it cannot export a metric; each call logs `mcp_tool_call` as JSON on stderr (server, tool, tenant, principal, outcome, duration; never an argument or a result).
- **What the model is told by a remote server is pinned.** A tool's description is text the model obeys, so it is where tool-poisoning lives, and a dependency upgrade can rewrite it unseen. `pinned` maps each expected tool to a hash of its name, description and input schema (`tool_fingerprint`); anything else is dropped (the bridge offers 19 tools, the app uses 5), a changed one is dropped and counted (`agent_mcp_tool_pin_failures_total`, alert `McpToolCatalogChanged`), and a test that imports the bridge in-process fails the same drift in CI and prints the new hashes. Annotations stay out of the hash: they are never shown to the model and never trusted.
- **What comes back is rendered, scrubbed, then bounded.** Text blocks are joined, an embedded text resource and a link are shown, an image becomes a note instead of vanishing, and a result with only `structuredContent` is that JSON. The scrub comes before the cut: cut first and a key straddling it splits into two halves no pattern recognises (tested; the reverse order leaks a fragment). The cap keeps the head and the tail (`app/core/output_limits.py`), because a failure is usually at the end of the output. A caller that parses the reply itself (the sandbox session parses JSON) passes `cap_output=False` and bounds the parsed parts, since a JSON document cut in the middle does not parse.
- **One connection per server and loop, and never a second send of a call that may have run** (`app/mcp/connection.py`). The failure modes were measured against a real server on mcp 2.3.0: a call that times out locally leaves the session usable; a server that dies mid-call fails it with `MCPError(CONNECTION_CLOSED)`; and a call sent AFTER the death fails with the very same error, before anything leaves. Under mcp 1.x the second was a different exception (`ClosedResourceError`), which is how this first told "never sent" from "may have run"; 2.x removed that difference, so the connection pings the server before a call that is not safe to repeat. A ping that finds the connection closed proves the call never left, and it is sent once on a new connection; a call that was in flight is NOT replayed (Principle IV; a test has the server run a side effect and die, and asserts it ran once; with replay on it ran twice; with the ping off, a call after an idle death fails instead of running once on the new process). The only gap is a server that dies between the ping and the call, which fails the call and repeats nothing. A read-only listing is replayed without the ping. Three timeouts in a row with no success recycle a wedged connection. One owner task enters the SDK's task-group context managers (they must be entered and exited by one task) and starts in an empty context, so it does not keep one request's trace id.
- **Gap: nothing authenticates the person who starts a published server.** Over stdio that is the machine's owner. A networked transport would need the identity from a verified credential on each connection (OAuth 2.1 resource-server behaviour, audience-checked tokens, no token passthrough) and is not built. The servers speak only stdio and have no flag that turns another transport on.
- **The app is on mcp 2.x because `opensandbox-mcp` 1.1 is.** Through 0.1.1 the bridge did `from mcp.server.fastmcp import FastMCP`, which mcp 2.x removed (checked in a real environment: it could not import), so the whole app was held on 1.x, the maintenance-only line, for a subprocess it only talks to over stdio. 1.1 requires `mcp[cli]>=2,<3`, imports `MCPServer`, and has a `--use-server-proxy` flag. Measured before moving: an mcp 2.3 client (`ClientSession` + `initialize()`) lists the real 1.1.1 bridge's 19 tools, the same 19 as 0.1.1; three of the five pinned fingerprints are unchanged and the other two (`command_run`, `sandbox_create`) changed only in the sentence that describes the return value, with identical input schemas, so the pins were updated after reading the diff rather than blindly; the `Execution` model `sandbox_session` parses (`exit_code`, `logs.stdout/stderr[].text`) is field-for-field the same in SDK 0.1.16 and 1.1.1. The SDK's `Client` class was not used, and the reason changed once the bridge moved to 2.x: it now connects cleanly (it probes `server/discover` and settles on protocol 2026-07-28, about 0.3 s, nothing on the child's stderr, checked against the real 1.1.1 bridge and this repo's servers), but that revision REMOVES `ping` (`send_ping()` answers `MCPError(-32601)`), and the no-replay guard in `app/mcp/connection.py` rests on the ping. `Client(mode="legacy")` keeps the ping and only reproduces what `ClientSession` + `initialize()` does. Adopting `Client` means choosing another liveness probe first; `tests/mcp/test_connection.py` fails if the connection ever ends up on a revision without the ping. `tests/core/test_mcp_sdk_pin.py` fails if the bridge on the path ever needs an SDK the app is not on.
- **The server and both sidecar images are on the same 1.1 line as the SDK and the bridge, and the whole path was run together.** The Python SDK talks to the server's lifecycle API and to the sandbox's execd, and upstream supports a server and an SDK on one release line only ("±1 minor warns"); since 1.1.0 every artifact ships at one version from one tag. `opensandbox-server` is `1.1.1` (not `1.1.0`: that wheel does not import, the FastPath gRPC stubs were left out of it), and `execd` and `egress` are `release-1.1.1` pinned as `name:tag@sha256:...` with the digests from the release's signed BOM (both checked by pulling them). The existing TOML loads unchanged under 1.1.1's own config loader. Verified live, in an isolated compose project with a throwaway key and nothing else touched: `pytest -m sandbox` (the catalog, a real sandbox, its reuse) passed 4/4 on four runs, and a probe ran a command as the non-root `sandboxuser`, wrote a file and read it back, ran numpy and pandas, and confirmed the sandbox has no network. `tests/core/test_sandbox_release_line.py` fails when the SDK, bridge, server or either image drift apart, and when an image loses its digest. Not exercised: the egress sidecar (`sandbox_create` passes an image, metadata and a TTL and never a network policy, so nothing starts it; the pin is checked, not run), and `[docker] publish_host`, new in 1.1.1, which can keep the tokenless execd port off public interfaces; it is left at its default because whether this server still reaches sandboxes with a loopback bind was not tested.
- **The wrapper script is gone.** The app launches the packaged CLI, `python -m opensandbox_mcp --transport stdio --protocol http --use-server-proxy --domain D`, under its own interpreter (proven by the live run above). Launching the CLI directly means a release that renames or drops a flag would break the launch and `load_sandbox_tools()` would degrade quietly to no sandbox tools, so a test asks the installed CLI's `--help` for every flag the launch passes, and CI's `docker-build` job runs the real loader in the built image.
- **Gap: a lost in-flight call is a failed tool call, and the model may issue the command again as a new one.** `idempotent()` keys on the `tool_call_id`, which a new call does not share; the `outward` approval gate in front of it is what stands there. Not measured: whether the bridge's in-memory registry of connected sandboxes grows over a long-lived process (a process used to live for one call).
- **Not touched, still open (specs/009):** `read_sandbox_file`'s old failure to read back a file it just wrote (A6) is gone on 1.1.1, but the prompt advice that works around it is unchanged; the sandbox's network and resource posture (A2) and the crawler's redirect handling (A1) are as disclosed. `outputSchema`/structured output was not added to the published servers: their tools answer in prose for the model, and wrapping prose in `{"result": ...}` adds nothing.
- **Use when:** an MCP server is started by someone other than the person it acts for, or a tool catalog comes from code you did not write.

### 79. A call is built for the server's prompt cache: nothing that changes per turn goes in a system message, and a call that needs no tools sends none
Langfuse traces `889b5405` and `475b073a` (2026-10-24), asked "why is this so slow": 26.8 s and 40.1 s for turns whose answers took seconds to write.

### 80. A stopped turn is taken out of the thread, because the model reads the thread and not the click
Trace `d6a00248` (2026-10-24): "run it through a script and count db_timeout" was stopped with `POST /chat/cancel`, then "Check our API docs page ..." was sent. The model was shown both messages with nothing between them, answered the older one, and paused for approval to run the script the person had just stopped. The stop was only accounted for (`_record_unfinished_turn`); the thread kept the question.
- **Fix:** `runtime/cancelled_turn.discard_cancelled_turn`, called on `TurnCancelled` only, removes the turn's messages (`RemoveMessage`) with `aupdate_state(as_node=START)`. A timeout, an error or a closed connection keeps the question, so "try again" has something to retry. If a TOOL had already run in the turn, the turn stays and is closed with an assistant line, `[The person stopped this request before it finished.]`: its result is a fact the model must keep, and forgetting a filed ticket invites filing it again under a new call id, which the exactly-once guard cannot catch.
- **Read in the installed LangGraph 0.2.76, not assumed:** `update_state` without `as_node` raises "Ambiguous update" after a run that stopped part-way; it applies the writes of tasks that had already finished; and the next turn's input discards the tasks left pending. ## Extending Further

### Exactly-once side effects: how the gaps closed

Two kinds of duplicate: a **replay** sees the same `tool_call_id` twice; a **re-ask** arrives under a new
`tool_call_id`, which nothing keyed on the id can recognize. The layering is summarized in the
[README](README.md#safety-model); each row here is a defect found and closed.

| Gap | Fix |
|---|---|
| A tool call runs twice (a reclaimed `resume`) | `app/core/tool_idempotency.py::idempotent` wraps every `mutating`/`outward` tool, keyed by `tool_call_id` in `tool_call_dedup` (`13-`). A second call returns the cached result. Resuming re-invokes pending calls under their **original** ids, so reclaiming a `resume` is always safe. Fails open (`agent_tool_dedup_degraded_total`) |
| A worker dies mid-turn; a restart would re-ask the LLM for new ids | `queue.py::reclaim_stale_entries` (`XAUTOCLAIM`) runs in both workers. `_classify_reclaimed_turn` reads the checkpoint (never re-running anything): no `HumanMessage` yet → rerun; own `HumanMessage` checkpointed and unfinished → **continue** the run (`astream_events_continue_turn`), even after a write, since no new id is minted; finished, approval-paused or unreadable → dead-letter. Retries are capped by `MAX_AUTO_RECLAIM_RETRIES`; `agent_worker_job_reclaimed_total{queue,outcome}` separates `retried` from `dead_lettered` |
| A finished zero-tool turn is reclaimed before its ack | `_turn_already_completed` refuses it (a rejected, tagged answer is not a finished one); a tool-call check alone re-ran it and double-recorded its cost |
| Ingest jobs on reclaim | Idempotent by construction (`_content_point_id`, pattern 24), so retried unconditionally |
| A client resubmits the same message | `claim_or_get_existing_submission` reuses the first attempt's `request_id` within `CHAT_SUBMIT_DEDUP_TTL_SECONDS`. This exposed a bug: results streams were deleted when any reader saw the terminal event, unsafe once two readers share one, so they now rely on the TTL. `release_submission_claim` undoes a claim whose publish failed |
| A tool times out but its write lands | `MutatingToolTimedOut` steers the agent to verify with a read-only tool first. `asyncio.wait_for` cancels the awaiting task, not necessarily the write, and "retry" would be a fresh id |
| The dedup claim races (`result IS NULL` → run again) | `add_note`/`remember` point ids are `uuid5` of `tool_call_id`; `create_ticket`/`log_incident`/`add_followup` carry `tool_call_id UNIQUE` + `ON CONFLICT DO NOTHING` (`14-`) |
| An append to a text column has no row for `ON CONFLICT` | `15-` makes each append its own row (`support_ticket_comments`, `crm_lead_notes`); flattened text is computed at read time, so `tools.py` didn't change. `find_or_create_lead`'s upsert is naturally idempotent and needs no key |
| Nobody ever publishes (no worker, or a poisoned dedup claim) | `read_results` bounds the wait for the **first** event only (`first_event_deadline_seconds`), so long ingest jobs aren't cut short |
| One bad upload aborts the batch or orphans a blob | `POST /ingest/upload` returns per-file errors and deletes a blob that failed to publish |
| `tool_call_dedup` grows forever | `scripts/tool_call_dedup_sweep.py` (`make tool-call-dedup-sweep`) |
| `usage_ledger` grows forever | retired: the table is frozen, nothing writes it. The same question for the events is `make usage-events-sweep` (pattern 63) |
| Telegram redelivers after a restart | Durable offset in Redis (pattern 42) |

**Deliberately not built:** a business-key rule ("one open ticket per tenant + requester + subject") for two
*different* ids used for the same request. What counts as "the same ticket" is a product decision;
`MutatingToolTimedOut`'s steering is the general mitigation until a domain needs one.

### Next PR: the LangGraph upgrade (decided, not started)

`requirements.txt` pins `langgraph>=0.2.20,<0.3` (0.2.76 installed). The next PR moves it to **1.0.1**, the highest release this stack can
use, and is deliberately its own PR: it is the only change in this series with a real compatibility risk.

- **Why 1.0.1 and not 1.2.x.** LangGraph 1.0.3 and later need `langchain-core` 1.x. The Langfuse **v2** SDK imports `langchain.callbacks` and
  `langchain.schema`, which langchain 1.x removed, so it needs `langchain` 0.3, hence `langchain-core<1`, hence LangGraph 1.0.1 at most. Going further is a
  ladder, not a bump: Langfuse **server** v3 (ClickHouse, Redis, S3 and a worker, where `docker-compose` runs `langfuse/langfuse:2`), then the Langfuse SDK v3,
  then langchain 1.x, then LangGraph 1.2.x.
- **What 1.0.1 buys.** It clears the import-time "incompatible versions of langgraph and checkpoint-postgres" warning. It has no `Overwrite`, so
  `concat_or_reset` (the `subagent_spend` reducer) stays. That is the whole benefit, which is why it is the user's call whether it is worth the risk.
- **What to verify, none of it assumed.** (1) A thread **paused** under 0.2.76 resumes under the new version (pause under the old code, resume under the new, as was
  done for #170's `STATE_SCHEMA_VERSION` check). (2) `tests/agent/graph/test_checkpoint_across_a_topology_change.py` still passes: it pins that a renamed router hides a
  mid-flight node, and LangGraph is the thing that decides that. (3) The `saver.lock = asyncio.Semaphore(...)` workaround in `runtime/core.py` is still needed or can go.
  (4) `interrupt`/`Command(resume=...)`, `add_messages` replacement by id (retry artifacts and legacy healing rely on it) and parallel fan-out (the `finish` step) behave as before.
  (5) `make test-integration` and `make test-live`, not only `make test`. (6) `aupdate_state(..., as_node=START)` in `runtime/cancelled_turn.py` (80) still discards a stopped turn and still lets
  the next turn run: `tests/agent/runtime/test_cancelled_turn.py` pins it, and it was read in 0.2.76 only.
- **Deploying it:** stop the workers and let in-flight turns finish first (pattern 16): a turn left mid-flight by the old library cannot be assumed to resume.

### Not built

- **A fallback node** for the primary LLM path.
- **A vision model that also does tool calling** (44). Small local vision models do one or the other; the `vision` alias is a slot, not a verified default.
- **Image-aware moderation, and Telegram/CLI image input.**
- **Crash-restart and autoscaling for workers.** `--scale` works and workers handle `SIGTERM`, but nothing restarts a crashed one or scales on queue depth.
- **A Telegram webhook.** Long-polling needs no inbound port; production would use `setWebhook`.
- **Real authentication.** Pattern 17's `SecurityCtx`/`Policy` is the isolation structure; header extraction isn't authentication.
- **Per-action authorization within a tenant.** Every principal has the write capability the gate allows at all; a `Policy` reading `ctx["claims"]` would live here.
- **A multi-domain runtime** (partly done, pattern 49). The API routes per request via `X-Domain`, but one process still builds one graph. Serving several would need a per-domain graph registry (the system prompt is no longer a per-thread concern, so that part is already done).

### Known gaps

From reviewing the as-built system against the constitution; each notes how it was established, and a fix PR
deletes it from this list.

- **The shipped proxy does not authenticate** (*read from `deploy/caddy/Caddyfile`*). It neither sets nor strips `X-Tenant-Id`/`X-Principal-Id`, so a caller can name any tenant. Isolation then guards against bugs, not against a caller who sets another tenant's header. Put an authenticating gateway in front.
- **The ops domain is global** (*read from code*). `ops_incidents` has no tenant dimension by design, any caller can name the domain, and nothing authorizes which tenants may use it. Principle I has no carve-out for it.
- **Approvals are unattributed** (*read from code*). Decisions are counted by outcome only (no approver, time or action), so the gate is enforced but not auditable, and the principal is whatever header the caller set.
- **The `tool_call_dedup` lookup isn't tenant-scoped** (*read from code*). It assumes provider ids are globally unique. Adding a tenant predicate changes what a collision means (a miss ⇒ a second write), so it needs a decision.
- **A residual duplicate window for team-channel posts** (*read from code and the spec*). If a second run finds the first's dedup record still in flight, it runs the call. Row-backed writes are protected by uniqueness; the three tools that also post to a channel (sales handoff, support escalation, ops `post_to_team_channel`) rely on the conversation lock and on reclaim waiting longer than a turn, so a second run can post twice. The write itself is unaffected; the post is best-effort by design (`app/domains/notify.py`).
- **Nothing schedules `make tool-call-dedup-sweep` or `make usage-events-sweep`** (*read from code*), so those rows accumulate until someone runs them.
- **Memory deletion has no entry point** (*read from code*). `delete_memories` is built and tested, but nothing calls it; retention is enforced at read time only.
- **Tenant isolation is only partly proven against real backends** (*read from tests*). Documents and the cache's tenant axis hit real Qdrant/Redis; memories, relational stores, sessions and the cache's principal axis rely on hermetic tests.
- **`reclaim_stale_entries` is tested only against a fake** (*read from tests*), hand-written and not paginated like real `XAUTOCLAIM`; no integration test covers it.
- **The answer cache key ignores conversation context** (*read from code, not reproduced*). The key is the last human message, so a follow-up like "be more detailed" can hit an answer cached for a different conversation of the same caller. Bounded by tenant+principal scope and the TTL: wrong context, not a leak.
- **A refused resume emits an error with no `code`** (*read from code*). `astream_events_resume` yields `{"type": "error", "content": "checkpoint_lost: …"}` outside the envelope, so a client can't switch on it (pattern 30).

**The key insight:** LangGraph lets you make every step of the pipeline explicit and controllable. That is
what separates it from "just LLM + tools."
