# Contract: the billing port (spec 011, widened by spec 013)

> **Living copy** (spec 011 D13). This is the version to read and edit. The original, `specs/011-billing-module-boundary/contracts/billing-port.md`, is the historical record of the decision it was written for and is not updated. A path in the text is relative to `packages/billing/` unless it names the agent application (`app/...`), which hosts this package in this repository.

The port is **shaped as the service API** (D18) so that a network implementation can satisfy it later. Spec 013 widened it from the two operations spec 011 gave it to the four a host needs once billing owns the billing half of its meter (marked ●); the rest are contract only (○) and are built by the roadmap ([`ROADMAP.md`](ROADMAP.md)). Every operation is tenant-scoped, carries an idempotency key where it writes, and states what it does when billing cannot be reached. Types are plain: strings, `Decimal`, dataclasses. The one exception is the caller's connection (the in-process form only), because the record, the charge and the export row are atomic with the caller's own write.

| | Operation | Idempotency key | Atomic with the caller? | When billing is unreachable |
|---|---|---|---|---|
| ● | `record_usage_in(conn, usage: Usage) -> Recorded` (`credit_billing/usage.py`): rates the cost, records it under `(tenant, event_id)`, debits the wallet, queues it for export | `(tenant, event_id)` (a replay returns `Recorded("duplicate")` and does nothing) | **yes**, in the caller's transaction; the debit and the queuing each in a savepoint of their own | never raises: counted (`billing_event_write`, `credit_debit` or `export_enqueue`) and paged; the caller's own record is unaffected |
| ● | `admit(tenant, *, reserved_usd) -> Admission` (`credit_billing/admission.py`): the credit gate | none (read) | no | `CREDIT_CHECK_FAILURE_POLICY` decides (`open` default: `degraded`, counted and alerted; `closed`: `unavailable`) |
| ● | `credit_summary(tenant) -> CreditSummary \| None`: the balance and whether the gate enforces; None when credits are off or the tenant has no wallet | none (read) | no | raises, so a status endpoint says so instead of reporting "no wallet" |
| ● | `account_balance(tenant) -> Balance \| None` | none (read) | no | raises |
| ● | `credits_for_cost(cost_usd, credits_per_usd, markup) -> Decimal` | none (pure) | n/a | n/a |
| ○ | `reserve(tenant, amount, *, key, ttl)` / `capture(hold, actual, *, key)` / `release(hold)` | `key` | n/a | a hold expires on its TTL |
| ○ | `grant(tenant, credits, *, key, source, …)` / `adjust(…)` | `key` | n/a | caller retries with the same key |
| ○ | `checkout(tenant, product, *, key, …)` | `key` (provider-side idempotency) | n/a | caller retries |

`Usage(tenant, event_id, kind, cost_usd, model=None, tokens=None)`: `cost_usd` is the caller's figure (`None` is unpriced, never zero); `event_id` must be stable across retries and, if a usage-billing provider is enabled, unique across tenants (the provider deduplicates on it alone). `Recorded(status, credits, debit)` with status `recorded | duplicate | off | failed`. `Admission(status, available, reserved)` with status `allowed | exhausted | unavailable | degraded`; `reserved_usd` is an async callable, awaited only for a tenant that has a wallet.

## Idempotency semantics
A key stands for ONE request (spec 012); a usage record's key is `(tenant, event_id)` and a repeat is a harmless duplicate whatever else differs, because the record is a fact about what happened, not a request that can be asked twice with other terms. The wallet debit under the same id still compares its request, so a replay that rates differently is refused there. The transaction stores a normalised description of the request (`credit_transactions.request`) and a reused key is compared with it: the same request returns the existing transaction (`status="duplicate"`) and changes nothing; a DIFFERENT request raises `IdempotencyConflict`, naming each field that differs, and changes nothing. That is what a service API called by arbitrary clients needs, and what Stripe's does (research R7): a remote implementation maps the exception to a 409-style response. Which fields identify a request is an explicit, validated choice per call (`compare=`; the default is every field and the kind is always compared); a transaction written before the column existed has no stored request and behaves as it always did.

## Errors
`BillingNotConfigured` (no connection supplied), `InvalidSignature` and `InvalidPayload` (webhook), `IdempotencyConflict` (a `ValueError` subclass: a key reused for a different request), and the existing `ValueError`s for a negative or empty debit. A network implementation maps these to status codes; it adds no new meaning.

## Where the pieces live (D19)
- **The contract** is `src/credit_billing/port.py`: `BillingPort`, the in-process implementation `InProcessBilling` and the plain types. A network client would implement the same protocol.
- **The host's one seam** is `app/billing_integration/port.py`: it holds the implementation in use (`billing`), exposes the operations as functions, and importing it wires the package. Its `record_usage_in` is also the second line of defence: a fault the package did not foresee is counted on the package's own `billing_event_write` path and swallowed, because an exception there would roll back the caller's own record.
- **What the host may import:** outside `src/credit_billing/` and `app/billing_integration/`, nothing under `app/` or `scripts/` imports `credit_billing`, and nothing there names a rate, a markup, the gate's or the export's settings, or a package table (`tests/billing/test_billing_core_boundary.py` scans for all three). `app/billing_integration/` is now only the port and the webhook route; the export, the wallet reconciliation and the billing-event retention are the package's own commands.
