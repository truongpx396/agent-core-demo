# Patterns of the billing package

Architectural patterns of `credit_billing`, each with the real failure that motivated it (constitution Principle VIII, "Self-contained packages").
They were written in the agent app's `GRAPH_PATTERNS.md` while billing was part of the app; they moved here with the code (spec 011 PR C, D14, D25).

**Numbers.** A pattern keeps its ORIGINAL `GRAPH_PATTERNS.md` number (52, 54, 65, 66, and the notes on 59 and 60), so earlier references to it still resolve; a pattern
number is never reused or shifted. New patterns of this package are numbered **B1, B2, B3, ...**. A cross reference such as "pattern 58" points into the agent app's
`GRAPH_PATTERNS.md` unless it says otherwise. How the application integrates this package (charging on the event, the gate, usage export, reconciliation) is in the
application's `BILLING_INTEGRATION.md`; this file is only about the package itself.

**Paths.** The entries below were written before the move. A path such as `app/billing/credits.py` is now `src/credit_billing/credits.py` in this directory, and
`postgres-init/20-credit-wallet.sql` is `src/credit_billing/sql/20-credit-wallet.sql` (the application keeps a byte-equal copy).

## Patterns

### 52. An app-owned credit wallet, and why the provider does not hold the balance
Neither Stripe (credit grants apply to an invoice only when it finalizes) nor Polar ("doesn't block usage if the customer exceeds their balance") can answer "may this request run now?", so the real-time balance lives here (`app/billing/credits.py`, `postgres-init/20-credit-wallet.sql`) and the provider owns only the money. Design in `specs/010-credit-billing-readiness/`.
- **An append-only ledger, with the guards in the database.** Transactions and entries refuse UPDATE and DELETE by trigger; a lot can change only its `remaining`; composite foreign keys `(lot_id, tenant)` and `(transaction_id, tenant)` mean an entry cannot reference another tenant's lot, so a cross-tenant move fails in Postgres rather than in code that might share the bug. `UNIQUE (tenant, idempotency_key)` makes a replayed grant, debit or expiry insert nothing. **Each of eight schema mutants fails the intended test on a fresh container.**
- **Opt-in per tenant.** A tenant is on credit billing only if it has a `credit_accounts` row. No account means never debited and never gated, so no existing tenant can be put into debt by shipping this.
- **A debit is never refused for a short balance.** The model call it pays for has already happened, so refusing would only lose the fact: the shortfall is booked on the tenant's overdraft lot, counted (`agent_credit_overdraft_total`) and repaid first by the next grant. Stopping the spend is gating's job, before the call.
- **Exact credits.** `NUMERIC(18,6)` and `Decimal`. A float is read through its shortest repr, so `0.0000005` rounds half up to `0.000001` instead of down because its binary form sits just below the half (a mutant that reads the binary value fails two tests); integer credits would overcharge every small call.
- **I assumed the per-tenant advisory lock prevented lost updates. The mutation run showed it did not matter for that**: the row locks on the lots already stop it, and removing the lock failed *no* test except one I then wrote for what it does uniquely buy, the canonical state (a debit racing a grant ends as a serial run would, never a debt next to live credit; removing the lock fails that stress test 3 of 3 times). The module docstring said the wrong reason until then.
- **Expiry is a decision, enforced in code** (`EXPIRY_REQUIRED`): promotional and subscription credits must expire; paid credits do not unless asked, since many jurisdictions restrict expiring a prepaid balance. An expired lot is never consumed even before the sweep books it, so the available balance is right the instant it expires.
- **The model has no path to a balance.** A structural test (not a list of names) fails if any module that defines or serves an agent tool imports `app.billing`; a granted credit is an operator action or a verified webhook, never a tool call.
- **The debit now runs in the event's transaction, and the gate reads the wallet before a turn** (pattern 53). **Not built:** `adjust` (with the operator CLI) and `clawback` (with refunds), both thin variants of the same debit path.

### 54. A webhook is a stranger's claim: signature, then the app's own tables, then once
A payment provider's webhook says a payment happened. It must never decide **who** is paid or **how much**, because the endpoint cannot carry the app's tenant identity and anyone who finds it can post to it (`app/billing/`, `postgres-init/22-billing.sql`, `POST /billing/webhooks/{provider}`; decisions D12, D13 in `specs/010-credit-billing-readiness/`).
- **A claim has nowhere to live.** `BillingEvent` has no `tenant` and no credits field. *Who* comes from `billing_customers`, a link the app wrote itself at checkout; *how much* comes from the server-side `credit_products` catalog. A payload that names another tenant and a billion credits is grant-neutral because there is no field to read them from, which is stronger than a rule that says to ignore them. The contract suite posts exactly that payload and asserts the grant goes to the linked tenant for the catalog's amount. No link means **quarantine**, never a default tenant.
- **The adapter port is a contract, not a convention.** One suite (`tests/billing/contract.py`) is run against every registered adapter, in a pure half (forgery, replay window, unknown type is `IGNORED` not an error, buyer details never stored) and in the integration tier through the real inbox and wallet. Registering an adapter without a harness fails a test, so a provider cannot skip it. The in-repo `fake` signs and parses its own payloads, so the whole path is proven without a sandbox account; **no real provider adapter exists yet**.
- **Exactly once, by five independent keys** (constitution IV): the inbox `PRIMARY KEY (provider, event_id)` (twenty concurrent deliveries of one event are one grant: the second INSERT blocks on the first's transaction, then finds a finished row); the grant and the inbox status are **one transaction**, so there is no "granted but not marked applied"; the wallet's own `"{provider}:{event_id}"` key outlives a swept inbox row; a unique index `(tenant, provider, external_ref)` so **one payment is credited once even when a provider describes it in two events with different ids** (the app checks first and ignores the second; the index is the backstop for a race, and the loser fails loudly and is retried); and a refund is keyed by the **payment**, not the event, so a payment is taken back at most once.
- **Refund policy is a decision (D12), and what is undecided is never guessed.** A full refund claws back what the grant still holds **or spent**, but not credits that already left by expiry (taking those back again would book debt for credits the customer no longer has); spent credits become debt, the gate refuses usage until the next grant repays it, and this is **not** counted as the wallet running dry (`agent_credit_overdraft_total` is only for ordinary usage). A refund before its purchase is held (the provider is told 503) then quarantined at a deadline. **A chargeback and a partial refund are quarantined and alerted**: reporting a partial refund as a full one would take back every credit, and as ignored would keep them all.
- **Fails loud on the path that hides money.** `quarantined` means a customer paid and nobody is retrying, so it pages (`BillingWebhookQuarantined`); `failed` pages too (`BillingWebhookFailing`), because a sustained database fault would otherwise show only in a provider's dashboard. A failing apply is recorded in its **own** transaction (the failed one rolled back, and with it every trace) and the Nth failure quarantines the event, so a poison event is not retried for ever. The stored reason is a **class name**, never an exception's text (a driver error can carry a host or a credential).
- **An unauthenticated route, built like one.** Unknown provider is a 404 counted under a **fixed** label (a caller-chosen string would let a stranger mint unbounded metric labels); the body is capped **before** it is read (a declared length is refused outright, and an undeclared one is cut off while streaming); a bad signature is a 400 that **stores nothing, not even an inbox row**, and says nothing about why; a provider enabled with no secret stops the process from starting (settings refuse to load, the lifespan builds the adapters), and secrets are `SecretStr` so they never reach a repr; the rate limit is per source address, never keyed on a header the sender controls. **PII is kept out by whitelist**: the inbox stores only the normalized fields, never the raw body.
- **Bug this prevented / found while writing it:** the first mounted-routes test asserted on `app.routes` and failed although the router **was** mounted, because newer FastAPI wraps included routers in `_IncludedRouter` and does not flatten them. The webhook is `include_in_schema=False`, which also hides it from the OpenAPI-based check, so the guard now proves the mount **by behaviour** (a request through the real app reaches our handler, which counts it; a framework 404 would count nothing).
- **Verified:** 45 real-Postgres tests (every contract scenario for every adapter, the concurrency cases, the atomicity cases, the schema guards, retention) and the hermetic tests pass. **Mutation check: 29 mutants, all caught** (27 in code, plus dropping the terminal trigger and dropping the one-grant-per-payment index in the database). One test overclaimed ("refused without reading a byte") and was reworded to what it can observe.
- **Gaps (disclosed):** no real provider adapter (Stripe first, then Polar, PayPal last, D13). An event stuck in `received` or `failed` whose provider **stops redelivering** is not noticed until someone looks: nothing polls the inbox (PR 6's reconciliation is the detector). Partial refunds and chargebacks need a policy. The per-source rate limit is one global ceiling behind a proxy, since every request shares its address. Nothing schedules `make billing-inbox-sweep`. Checkout (the code that writes `billing_customers`) is not built: tests and operators link customers through `store.link_customer`.

### 65. The Stripe adapter: verified against Stripe's own library, then against Stripe, and what neither could show
Two wire formats and no business rule: a Checkout Session going out, a signed webhook coming in (`app/billing/providers/stripe.py`, specs/010 T029a). It declares `CHECKOUT` only (spec D16, prepaid packs), so the export outbox stays off and Stripe is never told what was consumed. The contract suite passed it unchanged, which proved the adapter honours the port and nothing about Stripe; the rest of this entry is what was done about that.
- **The signature is checked against an oracle, not against itself.** The known-answer headers in `tests/billing/test_stripe_adapter.py` were generated by Stripe's own Python library in a throwaway environment, so an adapter and a harness that misread the documented scheme the same way cannot both pass. Rules mirrored from the official verifier: any `v1` may match (several while a secret is rolled), the fake `v0` scheme is ignored (a correct MAC under the `v0` label is refused), the MAC is checked before the window, and only a STALE timestamp is refused, not a future one (a captured delivery can only be in the past; a symmetric check would reject real deliveries whenever this clock runs behind).
- **Then against Stripe.** `make test-provider-sandbox` (marker `provider_sandbox`, manual, never CI, a live-mode key FAILS the run before it creates anything) starts a real `stripe listen` forwarding to a local socket and hands the exact signed bytes to `parse_webhook`. A real delivery verifies with the secret the CLI printed; the same bytes are refused when one byte is added, under another secret, under only `v0`, or one second past the window; Stripe really does send `t`, `v1` AND `v0` on test events. A real `checkout.session.completed` and the real `charge.refunded` for the same payment normalize to a purchase and a refund that share one `payment_ref`; a 300 refund of 1000 is a partial refund and the remaining 700 is the full one. The Checkout request is accepted and the session has the shape `tests/billing/fake_stripe_api.py` assumes, and the same file's behaviours (idempotent replay, a different body under the same key refused) are asserted against Stripe, which is what keeps the fake honest.
- **The real run found what no document says.** With Managed Payments on (the default for a new account) Stripe refuses a Checkout line item whose Product has no `tax_code` (HTTP 400). That is catalog setup, not something the adapter can fix, so it is in the runbook (`infra/README.md`) and the adapter's docstring, and the error now carries Stripe's `param` (the NAME of the field it objected to, validated against `[A-Za-z0-9_.\[\]]{1,100}`) so a 400 points somewhere. Stripe's own `message` is still never repeated: a 401 quotes a key fragment.
- **Hard to get right: a refund is a partial one unless Stripe says otherwise.** `charge.refunded` fires for a partial refund too; only `refunded: true` (a literal true, not `"true"`, not `1`) is a full refund, because reporting a partial refund as full would take back every credit (D12). A JSON `true` is a Python `int`, so an amount of `true` would read as one cent: booleans are refused as amounts.
- **A paid-only grant.** A delayed payment method completes the Checkout Session UNPAID; only `payment_status: paid` grants, and `checkout.session.async_payment_succeeded` is the event that grants when the money finally arrives. Subscription and setup sessions are ignored, not granted.
- **The existing wallet tests now run against both adapters.** The real-Postgres webhook tests are parametrised by the harness, so every guarantee they hold (one delivery is one grant, a refund finds its own tenant's grant, a redelivery after the inbox row is swept still cannot grant twice) is shown through Stripe's real parser too. That exposed five tests that hard-coded `'fake'` in SQL or built a second tenant under the default provider; they use the world's provider now.
- **Verified:** 110 adapter tests (known-answer headers, every malformed-header shape, the full event table, the request on the wire, error classification, the capabilities it does not claim); the contract suite runs a Stripe harness beside the fake (24 parametrised cases); 34 real-Postgres webhook cases run through Stripe; 16 against the real sandbox. **Mutation check: 41 mutants against the hermetic tests, all caught after three tests were strengthened (the first run let `v0` through, a dispute reading a customer it does not have, and a boolean amount); 10 against the sandbox tier, 9 caught.** The survivor is a completed-but-UNPAID session, which Stripe's sandbox cannot produce; the hermetic suite kills it. The tier's own rails are pinned hermetically (`tests/core/test_provider_sandbox_tier.py`, 20 tests: the default run excludes it, no CI job selects it, every module is marked, a live or publishable key FAILS rather than skips, the CLI's signing secret and keys are redacted); 10 mutants, all caught, after the first version let a guard that SKIPPED a live key pass (a `Skipped` raised inside a test reports the test as skipped, so `pytest.raises(Failed)` never went red).
- **A session this app created, paid for real.** `tests/provider_sandbox/test_stripe_paid_checkout.py` has the adapter create the session, headless Chromium (Playwright, already a dev dependency) pay it with Stripe's test card, and Stripe deliver the real completion: it is a `CREDITS_PURCHASED` for the customer the adapter was told to bill, `product_ref` is the Price id the adapter put in `metadata.product_ref` (what a hand-made session lacks), `payment_ref` is the PaymentIntent, and the real refund of that payment names the same one. Two things only a real payment showed: `amount_total` includes tax (a $5.00 Price is 550 under Managed Payments' 10% VAT), and a buyer who pays in the localized currency (VND) still gets an event in the session's own currency, the local amount arriving separately in `presentment_details`. 6 tests against the real sandbox; 4 adapter mutants, all caught. It depends on the markup of Stripe's hosted page (a `data-testid` and field ids), so a redesign can break it without the adapter being wrong.
- **Gaps (disclosed):** the sandbox tier's OTHER purchase events (the refund tests that need no browser) come from `stripe trigger checkout.session.completed` (a guest checkout with no `customer` and no `metadata.product_ref`, which this app quarantines). **Nothing calls `create_checkout`**: there is no route that starts a purchase, so today a pack is bought only from code. The catalog and the customer link are SQL (no CLI). The constant-time compare and the check order (MAC before window) are not observable from outside, so no test can fail on them; they are as documented, not as proved. Polar (T029b) and PayPal are not built.

### 66. The Polar adapter: a header is the event id, a secret can mean two keys, and a call with no idempotency is made safe by looking first
The second real adapter (`app/billing/providers/polar.py`, specs/010 T029b), same shape and same promise as Stripe's: `CHECKOUT` only (spec D16), a signed webhook in and a Checkout out, no business rule. The shared contract suite passed it unchanged; what is particular to Polar was settled against its docs, **Polar's own Python SDK as the oracle** (polar-sdk 1.0.2, in a throwaway environment) and the real sandbox.
- **The event id is a header, not in the body.** A Polar body is `{type, timestamp, api_version, data}`; `webhook-id` is the dedupe key (Polar's SDK guidance calls it "a durable deduplication key") and it is covered by the MAC. The grant's own key is `"{provider}:{event_id}"`, so this choice is the exactly-once story for Polar; the order id as `payment_ref` is the second line behind it.
- **A secret can mean two keys, and the adapter tries both.** Polar's docs: a secret created before 2026-09-08 is used as its own UTF-8 bytes, a later one is Standard Webhooks with the base64 remainder decoded; a secret does not say which. The sandbox's `polar listen` secret was 32 characters with no `whsec_` prefix and verified under the raw key. The adapter mirrors the SDK (`_signing_keys`), compares in constant time against every signature under every key without short-circuiting, and ignores any signature version but `v1`.
- **Polar's window is symmetric; Stripe's is not.** The SDK refuses a timestamp 301 s in the future as well as 301 s in the past (and accepts exactly T±300); that is mirrored, where the Stripe adapter deliberately does not refuse a future-dated one.
- **No idempotency, so look before creating.** Polar's checkout docs mention none, the SDK's guidance says to reconcile at the application level before retrying a mutation, and a real sandbox run proved a sent `Idempotency-Key` is IGNORED (same body and key, two sessions). The contract demands that the same key twice is the same session, so the attempt's key is stored in the session's metadata and `create_checkout` first lists the customer's newest 100 sessions for the product and returns the match: an open or already-paid one is returned, an expired or failed one (unpayable, so it cannot double a purchase) gets a fresh session under the same key. **A search that fails or cannot be read creates nothing**, because creating blind after a failed look is exactly how a retry buys twice.
- **Only a positively one-time, paid order grants; a refund is dropped only when positively a renewal's.** `order.paid` grants only for `billing_reason == "purchase"` and `status == "paid"` (anything else, including a missing field, grants nothing). `order.refunded` is a FULL refund only for the exact status `refunded` (not `REFUNDED`, not `true`); a refund whose reason is unknown is processed (a quarantine for a person is a cheaper mistake than a silently kept credit), and `refund.created`/`refund.updated` are ignored because the order event already carries the refund (acting on both would reverse it twice).
- **There is no dispute event to map.** Not in the docs, not in the SDK, not in `polar trigger --list`; a Refund's `dispute` object exists only for a dispute Polar PREVENTED. So a chargeback is invisible to the wallet until it appears as a refund. Disclosed in the runbook.
- **Tests that are not the author's own opinion.** The signature vectors (new-style, legacy-style, rolled) were generated by the Standard Webhooks library and each verified under Polar's SDK at the instants used; the payload fixtures (`tests/billing/fixtures/polar_*.json`) were generated by `polar trigger <event> --json --seed 7`, so the adapter reads full real-schema Orders, buyer name, address and email included, and a seeded purchase and its refund share one order id.
- **The sandbox tier now guards the developer's own listener.** `polar trigger` (like `stripe trigger` and every real refund) is delivered to EVERY listening session of the account, so running the tier while a developer's own `polar listen` forwards to their local app would push sample events into that app. The tier now skips when another `stripe listen` / `polar listen` is running (`PROVIDER_SANDBOX_SHARE_LISTENER=1` accepts it), in EVERY module and not only the ones that start a listener: creating a customer, a product or a checkout through the API emits a webhook to every listening session too (a first version guarded only the delivery tests and the checkout tests fed a developer's listener regardless), and `POLAR_ENVIRONMENT` must be `sandbox` or the run FAILS before any request. It also found that `polar listen` is block-buffered when piped: its "ready" lines appear only after the first event, so readiness is proved by an actual delivery.
- **Verified:** 195 adapter tests; the contract suite runs a Polar harness beside the others (24 parametrised cases, unchanged); 34 real-Postgres webhook cases run through Polar (one existing test hard-coded Stripe's made-up event name and now compares what the delivery carries); 46 hermetic tests pin the sandbox tier's rails; 7 real-API checkout tests and 25 delivery tests (22 passed, 3 skipped for Polar's own sample bug) pass against the Polar sandbox (the response shape the fake assumes, that `Idempotency-Key` is ignored, replay, per-customer scoping, a wrong token, a bad product id naming `query.product_id`). **Mutation check: 61 mutants against the hermetic tests, all caught after one test was strengthened (the first run read `net_amount` instead of `total_amount` without a test noticing, because the fixture made them equal); 11 against the tier's rails, all caught.** One real Polar-signed delivery (a `customer.created` sample) was verified end to end through the adapter by a one-off script: it verifies, carries `v1` only, is refused for one extra byte, another secret, another event id, a `v2` label and either side of the window, and accepted at T+300 and T-300.
- **The delivery half has now run against the real sandbox (2026-10-09, with no listener running): 29 passed, 3 skipped in 42 s.** A real Polar-signed delivery verifies, is refused when altered / under another secret, event id or version / outside T±300; a purchase sample and its full refund share one order id; a partial refund is not a full one; 8 other event types are ignored. **The 3 skips are Polar's fault, not the adapter's:** `polar trigger subscription.created`, `subscription.cycled` and `product.updated` build samples that Polar's own API rejects (`...product.external_id: Field required`), reproducible with no code of ours, so nothing is delivered. The first version waited 90 s for each and blamed the adapter; `send` now reads the CLI's refusal, fails at once for an event the adapter must handle and skips (with Polar's words) for one it must only ignore, so a Polar fix un-skips them by itself.
- **A Polar order this app created, paid for real.** `tests/provider_sandbox/test_polar_paid_checkout.py` has the adapter create the session, headless Chromium (Playwright) pay it on Polar's hosted page with Stripe's test card, Polar deliver the real events through `polar listen`, and the order be refunded through `POST /refunds/`. The real `order.paid` is a `CREDITS_PURCHASED` for the customer the adapter was told to bill and the product it put in the session; `payment_ref` is the order id the API reports and the order's `checkout_id` is the session this app made; the real full refund names the same order; and the whole real lifecycle (checkout, customer, order and refund deliveries) grants exactly once and reverses exactly once, although `order.created` and `order.updated` of the purchase say `billing_reason: purchase` too. A second `create_checkout` for the same attempt AFTER payment returns the paid session, the "already paid is returned" rule, here run against a paid session for the first time. 10 tests, about 26 s per run against the real sandbox. **Mutation check: 7 adapter mutants, 6 caught** (`order.created` also grants; purchase `payment_ref` from the checkout id; `product_ref` from the customer id; refund `payment_ref` from the checkout id; a paid session treated as dead; a full refund read as partial). **The survivor reads `net_amount` for `total_amount`**: the real order had `tax_amount: 0` (a $5 buyer in California), so the two are equal and only the hermetic fixture, which makes them differ, can tell. Facts only a real payment showed: a US buyer must give a billing address (street, postal code, city, state) and the card, expiry and CVC live in ONE Stripe Elements iframe; the success redirect carries a `customer_session_token` (a bearer credential for the buyer's portal, so the test never prints the URL); **and the sandbox API is rate-limited**. Polar documents 100 requests a minute for the sandbox; a token that ran sixteen paid checkouts in about 80 minutes was answered `429` with an EMPTY body and `Retry-After: 3570` (an earlier, shorter block had cleared by itself). The 429 surfaced as a fixture ERROR on the refund call, which a `failed`-only reading of pytest's output does not count (the summary says `10 errors`): five runs of a first mutation batch ended with no verdict for that reason (their output was not kept, so the 429 is confirmed only for the run whose log was). What a run costs in API calls is not measured (the hosted page makes calls of its own), so why the limit was reached is a guess. The helper now says `HTTP 429, the sandbox rate limit; retry after N s` (pinned by 5 hermetic tests; removing the branch turns 3 red) instead of `HTTP 429 None field=None`.
- **Gaps (disclosed):** the delivery tests above (which need no browser) still use Polar's sample events; only the paid-order test below uses a real order. That test depends on the markup of Polar's hosted page and on the sandbox's rate limit, so it is manual and must not be looped. Concurrent `create_checkout` calls with one key can each create a session (only an unpaid session results). The search covers the newest 100 sessions of a customer and product. The token's minimum scopes are not verified. Nothing calls `create_checkout`; the catalog and customer link are SQL. PayPal is not built.

### B1. A schema that evolves by editing idempotent scripts needs a record, a lock taken first, and a clock on every wait
The package's two schema scripts could only be applied by `psql`, once: by a container's init on a fresh volume, or by an operator by hand. They open with `\connect appdata`, a psql meta-command, so no driver could run them; nothing recorded what had been applied; nothing could answer "is this database current?"; and two deploys starting together could collide. For one app on one laptop that is tolerable. For a service that deploys on its own cadence against a database that already holds money it is not, and it was the first prerequisite listed in `design-note.md` section 6. `credit-billing-migrate` and `credit_billing.migrate` (spec 012 PR A) are the answer.
- **The model is Flyway's repeatable migration, because that is what the scripts already are.** They are idempotent (`CREATE ... IF NOT EXISTS`, `CREATE OR REPLACE`) and are edited in place when the schema evolves (pattern 60 is about re-applying them). A changed checksum therefore means "apply again", not "refuse": refusing would make every comment fix a deploy blocker. A shipped script is `pending` (never recorded), `applied`, or `changed`; a recorded script this version does not ship is `unknown` and never fails a check, so rolling back to an older package is not blocked by a newer one's records. Flyway's own documentation states the condition this relies on: the author must keep a repeatable script safe to apply any number of times, and a test applies each shipped script twice.
- **Adopting a database the host initialised needs no special case.** The host's init created the schema and recorded nothing, so every script is `pending`; applying an idempotent script to a database that already has it changes no row, and then it is recorded. A test dumps every wallet row before and after and compares them.
- **The order inside one script's transaction is there because of measured failures, not taste.** (1) `SET LOCAL lock_timeout` first, because it bounds the advisory-lock wait too: the PostgreSQL 16 documentation never says so, and an experiment did (a second session gave up with `55P03` after 0.51 s). (2) The advisory lock before anything else: eight connections running `CREATE TABLE IF NOT EXISTS` on one table at once produced **216 errors in 40 rounds** (`DuplicateTable`, `DuplicateObject`, `UniqueViolation`), so `IF NOT EXISTS` is not a concurrency guard, and since the scripts themselves are full of it the lock has to cover them, not only the record table. (3) The record table. (4) The check inside the lock, so a runner that waited finds the work done and skips it. (5) The script. (6) The record.
- **A wait that ends by timeout is a clean rollback; a wait that ends by the deadlock detector is not.** The same reasoning as pattern 60: the detector picks a victim among unrelated sessions, so every wait here has a `lock_timeout` (default 10 s, configurable) and the error says what was waited for and that running again is safe. A held `ACCESS EXCLUSIVE` lock on `credit_transactions` stops the run in about the configured second with the record untouched, and the same run succeeds once it is released.
- **The migration lock is the two-integer advisory form.** PostgreSQL documents that key space as not overlapping the single-bigint form, and the wallet already uses the bigint form per tenant (`hashtextextended(tenant, 0)`), so no tenant name can collide with a migration. It is a transaction-level lock: a killed process or a dropped connection cannot leave it held.
- **One transaction per script, with the error raised from inside the block.** The script and its record commit together or not at all (PostgreSQL has transactional DDL). The connection provider's rollback only runs for an exception thrown into its `async with`, so every error is raised there; a test makes the second script fail after a `CREATE TABLE` and finds neither the table nor a record, with the first script still recorded.
- **`\connect` is removed, and nothing else is.** `schema.executable` strips exactly `\connect <database>` and raises on any other line that starts with a backslash: dropping a `\set` or `\if` silently would change what the script does.
- **Found while testing it.** `22-billing.sql` references `credit_lots` from `20-credit-wallet.sql` and cannot run alone, so the numeric order is a dependency (a test says so). And `schema.scripts()` sorted names as text, which would put `100-` before `22-`; it now sorts by the integer prefix and refuses a name that is not `<number>-<words>.sql`.
- **The checksum is over the bytes as shipped**, `\connect` line included, so it equals `sha256sum` of the file and of the host's byte-equal copy.
- **Verified:** 67 hermetic tests (a fake database that models the provider's commit-or-rollback transaction, so the statement order, one transaction per script and every rollback are pinned) and 17 real-Postgres tests (a blank database, adoption, a tampered checksum, a newer version's record, five rounds of four concurrent runners, the key space, a busy table, a held advisory lock, a script that fails midway, the command as a real process including exit statuses 3 and 4). **Mutation check: 24 mutants, all caught, and an identical-text control survived** (no lock, lock after the record table, no in-lock re-check, no `lock_timeout`, record before script, a swallowed script error, `status` creating the table, a checksum of the stripped text, `changed` read as `applied`, unknown failing the check, a zero-millisecond floor, a connection error echoing its message, an applied script re-applied, a lock timeout not translated, no validation, the single-bigint lock, `--check` ignoring `changed`, wrong exit statuses, a `--check` listing on stderr, `\connect` kept, meta-commands dropped silently, text ordering). The six lock-related mutants were also run against the real-Postgres file alone and each fails there too.
- **Gaps (disclosed):** repeatable scripts only. A change that cannot be written idempotently, or that needs a data backfill, needs immutable versioned migrations, which are not built (the record table does not preclude them). No downgrade. A checksum is about the script, not the live schema, so a database altered by hand is not detected. Re-applying a changed script to a busy production table waits up to the lock timeout per DDL statement and then gives up cleanly; it does not schedule itself for a quiet moment. Nothing runs the tool automatically (a service shell may choose to). A role without DDL rights surfaces as `MigrationFailed` with the database's own first message line. PostgreSQL 14 or later (the scripts need `CREATE OR REPLACE TRIGGER`).

### B2. A key that names a request must remember the request
The wallet's unique key `(tenant, idempotency_key)` made a replay insert nothing, which is right for a retry and wrong for a DIFFERENT request that reuses the key: a caller that asked for 600 credits under a key that had granted 500 was told "already applied", and its 600 was lost without a trace. For a financial record that is the worst failure mode, because it looks like success. `credits._begin_transaction` returned the existing transaction without comparing anything; it was disclosed in the design note (section 6) and in PR C's body, and spec 012 PR B closes it.
- **The transaction stores the request, as JSON, in a nullable column.** JSON and not a hash, because the error must say WHICH field differs; nullable because a row written before the column existed has an unknowable original request and the table is append-only by trigger, so it is never backfilled and a reused key on it keeps the old behaviour (a plain duplicate) for ever. The value is the one the CALLER passed, normalised (amounts fixed-point, instants in UTC, numbers without trailing zeros), not what Postgres stored after rounding: the pricing columns round on storage, so comparing the stored columns would have raised a conflict on a request that was identical.
- **Which fields identify a request is an explicit, validated choice per call; the default is all of them; the kind is always compared.** A global "compare everything" would turn two working callers into failures, and "compare nothing" is the old gap. A webhook grant leaves out `expires_at` (it is `now + days` computed in the handler, so any replay computes a later instant); a webhook clawback compares only the kind (its key names the PAYMENT, and the amount an event asks for is what it read from the lot, so two events for one refund can differ there). An unknown field name raises `ValueError` before a single statement runs, so a typo cannot silently compare nothing.
- **Both narrowings were reproduced, and the honest size of the hazard is small.** Reading `webhooks._process` showed that the inbox claim (one event) and the payment's lot check (one payment) answer a replay BEFORE the wallet is reached, so a replayed key is reached only when both miss. The tests make them miss on purpose and failed red, with `failed`, on the strict default and pass with the narrowing: this layer is defence in depth, and a defence layer must not fail on its own. A grant whose catalogue amount changed between two attempts under one event is a real conflict: it is quarantined at once as `idempotency_conflict` (the webhook table already defines quarantine as "retrying cannot fix it"), not retried as `failed` until the attempt limit.
- **`reason` and `actor` are compared in the default.** Stripe compares the whole request; and a different reason under a reused key means the audit text the operator just typed was not recorded, which "already applied" would hide.
- **The operator command's relative expiry can never retry exactly.** `--expires-in-days` is recomputed on every run, so a retry a minute later differs by a minute and would conflict. The command gains `--expires-at` (ISO 8601 with an offset; a time with no offset is refused, because a guess about the zone is a lot that expires hours early or late) and a conflict message that prints the exact `--key ... --expires-at <first instant>` to repeat the first request.
- **The column is added behind a catalog check, not `ADD COLUMN IF NOT EXISTS`.** The plain statement takes ACCESS EXCLUSIVE on the table even when the column is there (measured: it waits behind any open reader), `credit_transactions` is the table every debit writes, and `migrate` re-applies the script whenever its checksum changes. A test holds a read open, re-applies the shipped script under a 500 ms `lock_timeout`, passes with the guard, and fails with `LockNotAvailable` when the plain statement is put back.
- **Deploy order is a hazard, named.** Code that writes `credit_transactions.request` against a database without the column fails every keyed write at the INSERT (a debit is swallowed and counted by the charge path as `CreditDebitFailing`; a grant fails). So `credit-billing-migrate` runs BEFORE the new code, and `--check` is the gate. A test builds a database from the pre-change script (kept as a fixture), records its checksum through the tool as a deployed service would, upgrades, and finds the column nullable JSONB, every old row intact, old keys still plain duplicates, and new writes recording their request.
- **Verified:** 65 hermetic tests (vocabulary pinned to the contract, normalisation, which fields are compared, the refusal before any statement, the error's text, a fake that models the unique key, the operator command's flags and messages) and 36 real-Postgres tests (each field of grant and debit changed alone is refused naming exactly that field with the wallet snapshot unchanged; identical retries are duplicates; clawback and both adjustments; the stored JSON shape; the expiry sweep; legacy rows; the upgrade; six rounds of two simultaneous first uses have exactly one winner; a conflict never shows another tenant's request; the three webhook call-site tests; the command end to end including the exact retry). **Mutation check: 27 mutants, all caught, and an identical-text control survived** (comparison skipped; the kind not compared, by default and narrowed; a field dropped from the vocabulary; a legacy row raising; no validation; the request not stored; the lookup not tenant-scoped; the error not a `ValueError`; numbers and instants not normalised; the log carrying values; `compare` dropped in clawback and in a positive adjustment; the pricing left out; the webhook clawback strict; the webhook grant comparing the expiry; a grant conflict not caught; the quarantine reason changed; the command exiting 1; no hint; the two expiry flags combinable; a time with no offset accepted; `--expires-at` ignored; the column added with a plain `IF NOT EXISTS`; the guard inverted; the column TEXT).
- **Gaps (disclosed):** rows written before the column keep the old behaviour for ever. No new metric: a conflict is visible through each caller's existing signal (the charge path swallows it and counts it under the generic `credit_debit` degraded counter, with `error_class=IdempotencyConflict` in the log; a webhook grant conflict is a `quarantined` outcome, which already pages; the operator command exits 2) and through the `credit_idempotency_conflict` log event, which carries field names and never values, because a counter needs an alert threshold and there is no evidence for one yet. Keys are never pruned (a ledger keeps them; Stripe prunes after 24 hours). `compare=` is an escape hatch that can hide a real difference if misused; it has two call sites, each with a comment saying why, and a name outside the vocabulary is refused. The strictness on `reason` can annoy an operator who corrects a typo: the message says a different request needs a new key.

### B3. The package owns the billing half of a meter: one plain hand-off, in the caller's transaction, that cannot cost the caller its own record
The wallet became a package in spec 011, but what FED it stayed in the agent, welded to the agent's `usage_events` table: the rating (`CREDITS_PER_USD`, `MARKUP`), three credit columns that a second script added to the agent's table, the debit in the same transaction, an export outbox with a foreign key into that table, a 294-line export worker, and a reconciliation that mixed a check the agent owns (do my events agree with the LLM gateway?) with one billing owns (was every event worth credits charged?). On the turn path the agent also carried the credit gate, its rate and its failure policy. A second project reusing the package would have rewritten all of it, and the agent core knew what a credit, a rate and a wallet were. Spec 013 moves it, in one change.
- **Two stores, one flow, no shared table.** The agent's `usage_events` stays: its dollar caps and `GET /usage` read it with low latency and its columns (model alias, tokens, principal, thread) are the agent's. The package gets its own `billing_usage_events`, keyed `(tenant, event_id)`, holding only what billing needs (cost, credits and the rate that produced them, a model and a token count a provider is told). After inserting its own row the agent makes ONE call (`record_usage_in(conn, Usage(...))`) on the same connection, only when its row was newly inserted. A replay finds its own event already there and hands over nothing, so the agent's primary key is the first idempotency layer and the package's `(tenant, event_id)` and the debit's key are the second and third.
- **The call cannot cost the caller its own record, so it never raises.** The body is one savepoint; the debit is a savepoint inside it; so is the export row. A fault in the debit undoes only the debit and the event is kept WITH its credits (the missing charge is visible, `credit-billing-reconcile` lists it, and the key IS the event id so it can be replayed); a fault in queuing undoes only the queuing; a fault in the record undoes what this call wrote and is counted `billing_event_write`. Invalid input (a blank id, a negative or NaN cost) is counted and logged by field name rather than raised, for the same reason: an exception would propagate into the caller's transaction and roll back its own event. The host's port wrapper is a second line for a fault nobody foresaw. Every degraded path has an alert (`BillingEventWriteFailing` is new; a test fails if the code can count a path nobody alerts on).
- **When nothing is billing, nothing is written.** No rate and no enabled provider that bills on usage means no statement at all, so a deployment that never set billing up does not need the tables and pays one list lookup per call.
- **The single unique constraint is the whole duplicate story.** `PRIMARY KEY (tenant, event_id)` is the only unique index, because a second one makes `ON CONFLICT` unreliable under concurrency (two writers of one event can collide on the index that is NOT the arbiter and get a `UniqueViolation` instead of a no-op: found on the agent's table by a test failing 3 runs in 40). A test pins it. The tenant is part of the key and of the outbox's composite foreign key, which replaces the tenant-match trigger the agent's table needed: an export row can only carry its own tenant's event by construction.
- **Rating belongs to billing; the cost belongs to the caller.** The package rates from a cost the caller supplies because only the caller knows its model prices. The cost is rounded to twelve places FIRST and that figure is stored and multiplied, so a row reproduces its own credits exactly, and an unpriced call has NULL credits (unknown is never free).
- **The credit gate moved with it** (`admit(tenant, reserved_usd=...)`): enforcement, the rate, the markup and the failure policy are billing's; the caller supplies its in-flight holds as a callable that is awaited only for a tenant that has a wallet. With enforcement off nothing is read. The refusal vocabulary (`ErrorCode.INSUFFICIENT_CREDITS`, `GET /usage.credits`) stays in the agent: it is the API's contract with its clients.
- **The checks split along who can know.** The package checks billing against itself (`credit-billing-reconcile`: every event worth credits has a debit). It cannot check that every usage the caller metered reached it, because a record never handed over is invisible; the agent's own comparison with the LLM gateway is that detector and stays the agent's (renamed `usage-reconcile`, with its old `CREDIT_RECONCILE_*` variables still accepted).
- **Names were kept on purpose.** Metrics, alerts and dashboards move under their old names (`agent_credit_*`, `agent_usage_export_*`, `agent_cost_governance_degraded_total{path}`), so nothing an operator watches changed; renaming is a service feature with a migration. The host carries copies of the package's alerts and dashboard because Prometheus and Grafana read fixed paths there, and a test fails if a copy drifts.
- **Deploy order, again:** run `credit-billing-migrate` BEFORE the agent version that calls the package. A missing table is counted and paged, never fatal, but the usage is not recorded meanwhile. The agent's old credit columns and `usage_export_outbox` stay in an existing database, unused; events before the cutover are not copied, and unsent rows of the old outbox are not drained by the new worker (drain first if a usage-billing provider was ever on).
- **Found while testing it.** The package's savepoints are the outermost block when the connection has no open transaction, and psycopg then COMMITS at exit: a test that expected `rollback()` to undo a recording found the row committed. The host always has its own insert first; the contract says to call it after the caller's own statement, and a test calls it that way. A first draft stored the agent's cost as the quantised Decimal; every existing assertion on the agent's float cost failed, which was the signal that the agent's table did not need to change.
- **Verified:** hermetic tests moved with the code and widened (recording, admission, export verdicts, the wallet check, retention, the three commands, settings, metric paths and outcomes, the port, the schema) and real-Postgres tests (recording and its one transaction, 20 concurrent writers of one event, 50 concurrent events, the savepoint around the debit, the schema's guards, the outbox's tenant constraint, the export worker, retention, the wallet check, the upgrade of a database that has only the wallet and the inbox). In the agent: the hand-off through a stub implementation of the port, the whole path through the real package, and a scan that fails if a rate, a markup, the gate's or the export's settings or any package table is named outside `app/billing_integration/`. **Mutation check: 39 mutants, all caught, and an identical-text control survived** (a duplicate still charged; the debit outside its savepoint, by the hermetic file and by the real-Postgres file; no outer savepoint; nothing-is-billing still writing; an unpriced call worth zero; the key without the tenant, in the statement and in the table; the debit key not the event id; the cost not rounded first; a failure to queue raised; a negative, non-finite or blank figure accepted; the gate's hold read eager, enforcement-off still reading, the closed policy ignored, an exactly used-up balance served, a missing wallet gated, a refusal not counted; retention without the unfinished-export guard (both files), without its floor, pairing an export row by event id alone, or without the delete permission; the wallet check ignoring the wallet's start, the tenant in the debit lookup, or reporting zero-credit events, or reading an empty window; no append-only guard, no tenant-pairing foreign key, credits allowed without a rate; in the agent: a fault let through the hand-off, duplicates handed over, an unavailable gate serving the turn, a degraded one unmarked, an exhausted one without its figures, `/usage` always enforced, the model not the resolved one). One mutant (a negative cost accepted) first SURVIVED: with a rate set the multiplication rejected it anyway, so the check was never what stopped it; a test with no rate now pins the check itself.
- **Gaps (disclosed):** a billing write that fails after the caller's record committed is counted and paged but no later check can find it (see B3's split above); `event_id` must be unique across tenants if a provider is exported to; no backfill of events before the cutover; the store is in-process, not a service (the network form, an ingest endpoint and a late-event policy are the roadmap's).

## Notes on patterns that stay in the agent app's `GRAPH_PATTERNS.md`

Patterns 59 and 60 are general lessons that billing happened to teach, so the application's file keeps a generic version of each. What was specific to billing is

### 59 (billing specifics, as originally written). A settings error must not print the secret it rejected
Adding the Stripe and Polar credential settings (`STRIPE_API_KEY`, `POLAR_ACCESS_TOKEN`, specs/010 T029; the adapters that read them are not built) raised the question of what a rejected one looks like. Pydantic's `ValidationError` prints the raw offending value (`input_value='...'`), a `Settings()` error is raised at import time, and the output goes to a terminal or a container log. Checked, not assumed: with `STRIPE_API_KEY` set to a publishable key the startup error repeated the key whole, and so would a credential pasted into the wrong variable.
- **The same leak already existed, one variable over.** A malformed `BILLING_WEBHOOK_SECRETS` (`{"fake": {"nested": "whsec_..."}}`) echoed the entire JSON, signing secrets included. Both are closed by one line, `hide_input_in_errors=True` on `Settings`: the error still names the field and the rule and no longer repeats the value. A test per path (a rejected Stripe value, a malformed secrets map) fails without it; each was checked against the mutant that removes it.
- **Credentials are `SecretStr`, and a blank is "not set".** `STRIPE_API_KEY=` left in `.env` with no value arrives as an empty string, which would otherwise be a key that is empty and fail the prefix check with a confusing message. Only a blank is touched before wrapping; a real value is never inspected in the clear. The one mistake worth catching at startup is the publishable key (`pk_`), the first one on Stripe's API keys page, which cannot do anything on a server.
- **Polar defaults to its sandbox**, so nothing reaches production unless it is asked to. There is deliberately no "usage event name" setting (a first version had `STRIPE_METER_EVENT_NAME` and `POLAR_USAGE_EVENT_NAME`): the billing model is prepaid packs (spec D16), so nothing is sent to a provider as usage and nothing needs a Stripe Meter or a Polar event. A setting that nothing reads is a promise the code does not keep, and a test pins its absence.
- **A warning that can go stale is pinned.** `.env.example` tells the operator not to enable `stripe` or `polar` in `BILLING_PROVIDERS` until the adapters are registered, because only `fake` is and an unregistered name makes the API refuse to start. `test_the_warning_in_env_example_is_still_true_while_no_adapter_is_registered` fails the day an adapter is registered, as the prompt to rewrite the comment (it did, when Stripe's landed: pattern 65; it now guards `polar`).
- **Verified:** 17 hermetic tests; **mutation check: 8 mutants, all caught** (errors echoing the input, a publishable key accepted, any key accepted, a blank read as an empty key, Polar defaulting to production or accepting any environment, either credential stored as a plain string).
- **Gaps (disclosed):** nothing reads these settings yet, so a wrong key is only caught by its prefix, not by Stripe or Polar; that is the adapters' sandbox run. `hide_input_in_errors` is class-wide, so every other settings error also stops quoting its value (the field name and rule remain). `deploy/env/prod.env.example` was not given these entries: production credentials are a later decision.

### 60 (billing specifics, as originally written). A test that re-applies a migration to a shared database must be the one that gives up
`test_the_script_can_be_applied_twice` (migration 22) failed about one parallel run in seven, and in one full integration run the victim was an unrelated webhook test that failed with `DeadlockDetected` instead of its injected `RuntimeError`. It predated the work that found it (#139). Three tests re-apply migrations 21, 22 and 23 to the database the other xdist workers are writing to, and re-running DDL is not harmless there. Measured on a real Postgres rather than assumed: a no-op `ALTER TABLE … ADD COLUMN IF NOT EXISTS` takes an **ACCESS EXCLUSIVE** lock, `CREATE INDEX IF NOT EXISTS` a **SHARE** lock and `CREATE OR REPLACE TRIGGER` a **SHARE ROW EXCLUSIVE** lock, all on tables other tests hold row locks on.
- **Why the wrong test failed.** A concurrent transaction that holds a lock on one table and waits for another forms a cycle with the script, and Postgres aborts whichever session's `deadlock_timeout` (1 s here) runs its check first. That is the session that began waiting first, so it was the unlucky DML test, not the DDL one. Catching and retrying inside the DDL test would not have helped: the victim was somebody else.
- **The fix makes this session always give up first.** `tests/integration/schema_reapply.py::reapply` sets a `lock_timeout` (300 ms) shorter than `deadlock_timeout`, so the script abandons a wait and rolls back before any deadlock check can run; that dissolves the cycle, the other transaction continues, and the idempotent script is tried again with jitter. A `DeadlockDetected` is deliberately not retried: with the timeout in place it cannot happen, and if it does the assumption is wrong and the test should say so. A test asserts the timeout stays below `deadlock_timeout`.
- **The cycle is built on purpose, not hoped for.** `test_a_lock_cycle_with_another_transaction_never_makes_that_transaction_the_victim` takes a lock the script needs, waits until the script is actually blocked on it (read from `pg_locks`), then asks for a lock the script already holds. Without the timeout that is a deadlock within a second.
- **A hang is the worst way for a test to fail.** The first mutant run hung (with the timeout removed, the "never released" test waits forever) and my harness timed out, leaking a container. Every re-apply in the tests is now bounded by `asyncio.wait_for`, so a regression is a failure with a name, not a stalled CI job.
- **The same cause wore a second, misleading face.** In a later full run on another branch the failure was `test_the_database_itself_refuses_a_second_grant_of_one_payment` with `DID NOT RAISE UniqueViolation`, which looks like a missing unique index. It was not: `webhooks.process_event` never raises (a failure is recorded and returned as `"failed"`), that test discarded `deliver()`'s outcome, the deadlock had killed the FIRST grant, and so the second one "succeeded". Fifteen tests set the stage with a bare `await deliver(...)` and could fail the same way. They now go through `setup_deliver`, which asserts the delivery did not fail (and says to look at the inbox row), with a test that it does.
- **Verified:** 8 real-Postgres tests of the helper, and the three existing tests moved onto it. **Mutation check: 5 mutants, 4 caught** (no `lock_timeout`, a timeout longer than the deadlock check, no retry, giving up silently); the fifth, also retrying `DeadlockDetected`, is **equivalent** once the timeout is in place (nothing can deadlock), and is not counted as a gap. **16 of 16 parallel runs of the four affected files were clean** (108 tests each), against about one failure in seven before.
- **Gaps (disclosed):** the cycle test depends on migration 22 taking `credit_lots` before `billing_webhook_events`; if that order changes the test no longer builds the cycle (it still passes, and the mutant check is what would notice). Other tests that run DDL against the shared database (none found besides these three) are not covered unless they use the helper; `.claude/rules/testing.md` now says so. `lock_timeout` bounds this session only: a test that holds a lock for tens of seconds would still make the re-apply fail after its 60 tries.
