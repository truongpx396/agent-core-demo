# tests/containers.py's own cross-worker container reuse needs a real file
# lock, not a threading.Lock (workers are separate PROCESSES) — `filelock`
# is already a transitive dependency pinned in requirements-lock.txt
# (currently 3.32.4, pulled in by fastembed/huggingface_hub), so it's
# deliberately NOT re-pinned to a different version here: doing that
# once produced a real `pip install` dependency conflict (two different
# pins for the same package in one resolve) rather than a silent
# downgrade — caught in CI, not locally, since installing
# requirements-lock.txt and this file as two SEPARATE `pip install`
# invocations (as done manually while building this) doesn't trigger the
# same one-resolve conflict a single combined install (what CI actually
# runs) does.
